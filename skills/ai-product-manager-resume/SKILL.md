# AI 产品经理满分简历 Skill

## 目标与边界

把候选人的真实经历转化为招聘方容易识别、可追问、可验证的 AI 产品经理能力证据。目标是提高岗位匹配度和表达质量，不承诺“满分”、面试或录用结果。

默认求职方向：AI 产品经理实习生 / AI 应用产品 / AI 工作流产品。若用户提供了具体 JD，以 JD 为准。

## 必须遵守的原则

1. **真实优先**：不虚构公司、岗位、职责、用户规模、转化率、收入、实验结果、模型能力或项目上线状态。
2. **数字可追溯**：每个数字都要能回到简历、项目记录、数据截图或用户明确确认的材料；无法核实的数字标记“待核实”，不得润色成事实。
3. **区分状态**：明确区分已上线、已交付、原型 / Demo、设计方案、待验证假设。不能把设计目标写成已验证效果。
4. **保留原结构**：默认沿用用户原简历的栏目顺序、版式层级和整体风格；未经用户明确同意，不重排成另一套模板。优先在原有栏目内优化内容。
5. **岗位定制**：每次定制必须先读取目标 JD，提取岗位目标、职责、硬技能、业务场景和关键词，再映射候选人证据。
6. **隐私保护**：对外展示或写入公共仓库时，不复制手机号、私人邮箱、身份证号、住址等个人信息。
7. **不堆 AI 名词**：只有能说明使用场景、输入输出、决策逻辑、边界和验证方式时，才保留 RAG、Agent、工作流、Prompt、模型等术语。

## 工作流程

### 第 1 步：收集材料

优先读取：
- 最新版简历（作为版式与经历事实基线）
- 目标岗位 JD（必需；没有时先产出通用版并标注未定制）
- 项目 PRD、原型、产品链接、GitHub、飞书文档、数据记录、实习证明或可公开作品
- 用户补充的职责边界、个人贡献、协作角色和实际结果

建立“证据台账”，字段包括：经历 / 项目、时间、角色、本人负责事项、问题与用户、采取的动作、产出物、结果数字、证据来源、核验状态、可公开程度。

### 第 2 步：拆解 JD

按以下维度形成岗位画像：
- 产品工作：需求分析、用户研究、竞品分析、PRD、原型、流程设计、需求优先级、迭代复盘
- AI 能力：LLM 应用、Prompt、RAG、Agent、工作流、工具调用、评测、幻觉与安全边界
- 数据能力：指标体系、SQL / Excel、漏斗、留存、转化、A/B 测试、数据分析
- 业务能力：目标用户、使用场景、业务链路、增长、商业化、跨团队协作
- 交付能力：从问题定义到方案、原型、测试、上线 / Demo、复盘的闭环

提取 JD 原词和同义词，分为“必须出现”“有证据再出现”“不匹配不硬塞”三类。

### 第 3 步：岗位—经历映射

制作匹配表：
| JD 要求 | 候选人经历 | 证据 | 匹配程度 | 需要补充 |
|---|---|---|---|---|

优先选择最能证明岗位能力的经历，不按时间堆砌所有经历。每项核心能力至少有一条真实证据；没有证据就列入补充清单，不得凭空补齐。

### 第 4 步：重写经历

每条经历优先使用“背景 / 目标—行动—结果（STAR）”结构，并尽量体现产品经理思考：

- **问题**：谁在什么场景遇到什么问题，现有方案哪里不足？
- **目标**：希望改善什么用户行为或业务指标？
- **分析**：如何调研用户、竞品、数据或业务流程？
- **方案**：做了什么产品决策，为什么这样设计？
- **落地**：本人具体负责什么，如何协作、推进和验证？
- **结果**：交付物、数据变化、验证结论是什么？数据来源是什么？

推荐表达模板：
“面向【目标用户】在【具体场景】中的【问题】，通过【调研 / 数据分析】定位【关键原因】；负责【本人动作】，设计 / 推进【产品方案】，交付【可核验产物】；最终【真实结果及口径】。”

避免“负责相关工作、提升用户体验、赋能业务、效果显著”等无证据空话。

### 第 5 步：AI 产品项目专项表达

描述 AI 项目时，必须尽量交代：
1. 用户与任务场景；
2. 输入资料 / 数据来源；
3. 产品流程与关键交互；
4. 模型、Prompt、RAG、Agent 或工具调用分别承担什么作用；
5. 失败处理、人工兜底、隐私和数据保护；
6. 评测方法、测试样本、通过标准；
7. 当前真实阶段：构想 / PRD / 原型 / Demo / 内测 / 上线；
8. 本人贡献与可展示证据。

对 Agent 项目，重点讲清“资料—任务—执行—复核—提交”的真实闭环，不把普通聊天包装成 Agent。对工作流项目，讲清触发条件、节点、输入输出、异常分支和结果验证。

### 第 6 步：量化与真实性检查

对每个数字逐项追问：
- 统计对象是什么？
- 统计周期是什么？
- 基线和结果分别是什么？
- 计算口径是什么？
- 数据来自后台、表格、平台截图还是估算？
- 是个人贡献还是团队结果？

没有可靠来源时，改写为可核验的交付物或定性结果，并标注“待补证据”。不得把相关性写成因果关系。

### 第 7 步：简历质量评分（100 分）

仅作为内部诊断量表，不代表招聘方真实评分：

- JD 匹配度：20 分
- 经历证据与真实性：20 分
- 产品思维与问题拆解：20 分
- 结果与数据表达：15 分
- AI 技术理解与应用边界：10 分
- 结构、可读性与重点突出：10 分
- 细节一致性与格式：5 分

每项给出得分、扣分理由和可执行修改建议。证据不足时不得给满分；先补证据，再润色。

### 第 8 步：交付与复核

默认输出：
1. **岗位画像**：JD 的核心要求和关键词。
2. **匹配诊断**：优势、差距、证据缺口。
3. **逐段修改稿**：按原简历结构逐段给出可直接替换的内容。
4. **证据核验表**：数字、奖项、项目状态和链接的核验结果。
5. **最终简历**：尽量保持原版式，导出前检查单页 / 多页排版、字体、对齐、断行和链接可点击性。
6. **面试追问清单**：针对每条核心经历准备事实依据、决策理由、失败案例和复盘。

最终复核：
- 是否保留原简历结构？
- 是否每条核心经历都体现本人贡献？
- 是否所有数字都有来源和口径？
- 是否区分团队成果与个人成果？
- 是否区分 Demo 与正式上线？
- 是否覆盖 JD 的核心关键词但没有生硬堆砌？
- 是否存在夸大、重复、空话、错别字或隐私泄露？

## 交互方式

一次只追问一个最关键的缺失信息。若用户已经上传简历或 JD，先读取材料，不重复要求用户粘贴。若 JD 尚未提供，先完成通用诊断，并明确指出定制版还缺目标岗位信息。

## 输出语气

专业、具体、自然，不写空泛口号，不使用“完美简历”“包过”等保证性措辞。用招聘方能理解的语言表达产品能力；技术词汇必须配合业务场景解释。
