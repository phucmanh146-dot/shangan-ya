## 一、原来的三人分工

- A：诊断研究。回答“现在缺什么、依据是什么”，输出诊断、来源、差距、成员能力和未知项。

- 三人最终都通过 `p1/integration` 联调，再决定是否进入 `main`。

## 三、队长分支：现在视为“本分支完成，可交队友评审”

### 已完成

1. **统一项目状态与版本**
   - SQLite 保存项目、版本、历史记录。
   - 乐观版本检查，旧请求不能覆盖新状态。
   - 新诊断到来后会标记旧计划过期。

2. **A 的诊断接收层**
   - 校验来源、成员、gap、材料版本、未知项。
   - 校验 gap 对来源/成员的引用关系。
   - 支持更细的材料位置、原因、适用条件、验证方法等字段。

3. **B 的计划接收层**
   - 校验 task、gap、成员、来源、估时、依赖、时段冲突。
   - 支持 `micro_steps`：改哪里、做什么、为什么、输出、自检、失败下一步、能力依据。
   - 支持计划版本、预览 diff、用户确认后采用。

4. **执行闭环**
   - candidate / scheduled / in_progress / blocked / pending_review / completed 状态。
   - 开始、恢复、卡住、临时变化、锁定、提交、退回、验收通过。
   - “提交”只进入 `pending_review`，不能直接伪造成完成。
   - 逐条验收条件可保存证据，任一不通过不能 completed。

5. **成果与版本保护**
   - 保存 artifact_id、artifact_version、实际用时和证据。
   - 新排程不能覆盖已开始、已完成、待验收或锁定任务。
   - 锁定时段不能被重排删除。

6. **周期和突发重排**
   - 支持容量、可用时间、占用、截止日、缓冲等约束。
   - 先预览，再采用。
   - 支持撤销最近一次计划采用；已有新进度后禁止回滚覆盖成果。

7. **总调度路由**
   - A 诊断后进入 B。
   - B 失败可从 B 重试，不丢 A 已保存结果。
   - 新材料可触发重新交 A，旧计划不直接覆盖。
   - 服务重启后可从保存阶段继续。

8. **页面与接口**
   - `team.html` / `team.js`。
   - 后端 `/api/agent/team` 相关接口。
   - `run_handoff(researcher, planner)` 提供服务端真实 A/B 接线口；Demo 只作为人工夹具，不冒充真实 AI。

### 本分支不再继续单独实现的内容

以下不是“队长分支还没写完”，而是**必须等待/依赖队友或三人联调**：

- 真实 A 模块本身：仓库当前 A 分支没有独立新增实现。
- 真实 B 模块合入总控：B 已有实现，但尚未通过 `p1/integration` 接进队长总控。
- A 对新成果的真实复核算法与真实搜索/模型质量。
- B 根据 A 的真实 gap 生成真实行动卡后的三人联调。
- 视觉求助结果与具体 `gap_id/task_id/action_id` 的自动关联。
- 多人账号身份认证与权限隔离。
- `p1/integration` 的冲突处理、合并后回归测试和最终发布验收。

因此：**队长分支自身交付完成；项目整体未完成。**

### P0｜B 对接 A 的真实 Diagnosis

B 不再重新做“判断差距”，只消费 A 的 gap。

验收：同一个 `gap_id` 能生成原子任务，并通过 B 自己的测试。

### P0｜队长负责联调，不再新增平行功能

队长分支当前冻结功能范围，只做接线与修冲突：

`A -> team_orchestrator.diagnosis -> B -> team_orchestrator.propose -> 用户 apply -> 执行 -> submit -> A 复核 -> B 局部重排`

验收：不手工复制 JSON，函数/接口真实串通。

### P1｜合入 `p1/integration`

建议顺序：
1. 先合 A；
2. 再合 B，处理公共 `learning_agent_server.py` / `p1-contract.md` 等冲突；
3. 最后合队长总控；
4. 跑完整回归；
5. 再做真实案例。

如果实际冲突情况不同，以 Git 三方合并结果为准，不机械覆盖公共文件。

### P1｜真实闭环验收

至少跑一个真实项目：

1. 输入真实目标与材料；
2. A 输出带来源的 gap；
3. B 输出具体操作卡；
4. 队长采用计划；
5. 用户执行并提交新成果；
6. A 对新成果复核；
7. 未通过的 gap 回 B 局部重排；
8. 通过的 gap 才关闭；
9. 插入一次突发事件，验证只局部调整；
10. 刷新/重启后状态仍在。

## 七、原来 vs 现在，最大的变化

原来：三个人只有职责定义和共同开发基线，真实 Diagnosis / Plan / Feedback 尚未接通。

现在：
- **队长**已经把“接收、保存、预览、执行、证据、验收、重排、恢复”的总控底座完成；
- **B**已经有独立规划/容量/联合排程实现，但还没在三人集成分支证明真实接线；
- **A**从仓库角度仍停在共同基线，是当前最先要补的环节；
- **p1/integration** 仍没有吸收两条已领先分支，所以“个人分支有成果”不等于“三人项目已经完成”。

最终完成标准只有一个：**真实 A + 真实 B + 队长总控在 `p1/integration` 跑通同一个真实项目闭环并有证据。**
