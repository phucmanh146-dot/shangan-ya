# 三人进度看板与高含金量 Agent 技术栈差距

更新：2026-10-13。目标不是展示“有三个 Agent”，而是让三个人的真实交付、执行阶段、卡点和证据可追踪，并把项目从可运行原型推进到可复现、可评测、可恢复的 Agent 系统。

## 1. 三个 CC 窗口如何记

每个项目固定有 A / B / C 三条角色通道。真实执行窗口可调用 `POST /api/agent/team/cc-register` 获得独立 `window_id`，随后用 `POST /api/agent/team/cc-heartbeat` 上报阶段、状态、当前工作项和 blocker。看板 `GET /api/agent/team/cc-board?id=<project_id>` 汇总所有窗口。

如果真实窗口没有上报，系统只显示 `source=derived` 的流程推导状态；不得把 derived 写成“窗口在线”或“队友已完成”。真实心跳超过 5 分钟后不再标 active。

状态：`unhandled` 未处理、`active` 执行中、`blocked` 卡住、`waiting_review` 待复核、`done` 完成、`idle` 空闲/等待。`blocked` 和 `unhandled` 自动进入全局提醒。

## 2. 当前三人放行标准

| 角色 | 现在已有 | 不够的地方 | 下一步放行条件 |
| --- | --- | --- | --- |
| A · 诊断/复核 | 真实文件、版本、SHA256、位置、诊断/复核适配能力 | 不能只写“建议加强调研”；A本人独立交付与真人 V2 复核证据仍弱 | 每个 gap 有文件版本、原文位置、当前证据、目标判据、适用性；unknown 不猜；V2 逐条件 pass/fail/unknown |
| B · 行动/排程 | planner、容量、依赖、局部重排、保护任务 | 不能所有任务都是“搜资料→分析→修改”；另一人照卡执行证据不足 | 每一步有位置、动作、原因、产物、自检、失败下一步、能力依据；另一成员无需问作者即可开始并留下实际耗时 |
| C · 队长总调度 | 状态、版本、预览采用、B 接线、文件证据、A 适配、失败恢复基础 | 不能只把 A/B 串起来；共同分支和真人闭环仍需收口 | 按状态决定下一步；未确认计划不生效；错误版本拒收；失败/重启可恢复；只重排 remaining issues |

## 3. P0：现在必须补的技术层

1. **真实闭环**：真实 V1 → A 诊断 → B 行动卡 → 另一成员实改 V2 → A 复核 → B 只重排剩余问题。没有这一条，工程再多仍可能被评为 Demo。
2. **Tool Contract**：把 `read_artifact`、`diagnose_gap`、`check_capability`、`generate_micro_steps`、`review_artifact`、`replan_remaining` 定义成明确输入/输出和失败语义，而不是一个 Prompt 同时做全部工作。
3. **Tracing**：保存模型调用、工具调用、handoff、人工确认、失败和重试；评委能从最终任务反查为什么这样判断。
4. **Evals**：至少记录引文错误、漏检、误放行、首次照做成功率、返工次数、实际耗时、调用次数和人工介入。未测收益不写“提升 xx%”。
5. **Human-in-the-loop**：计划、复核、目标变化和高影响调整先预览再确认。
6. **Failure recovery**：错误版本、模型格式错误、外部工具失败、进程重启后保留原状态，不整套重来。
7. **CC 进度心跳**：真实 A/B/C 工作窗口接入本次新增的注册/心跳接口；看板能区分 reported 与 derived。

## 4. P1：主链稳定后补

- **MCP / Tool 标准化**：GitHub、网页检索、桌面、文件等外部能力走统一适配层。
- **来源 provenance**：官方规则、本人材料、参考案例、建议分层；搜索摘要不冒充正文已读取。
- **Observability**：把成本、调用数、失败类型、重试和人工介入次数放进同一执行记录。
- **多用户/公网**：当前核心仍是本机回环服务；若比赛需要公开体验，再验证账号、项目隔离、部署和恢复。
- **安全边界**：外部工具调用保留最小权限、人工确认和来源限制。

## 5. P2：暂时不要为了炫技堆

- 没有大量历史知识检索需求前，不急着上向量数据库。
- 没有明确模型瓶颈前，不急着微调。
- 当前自研状态机可满足主链时，不为名词强制迁移 LangGraph；复杂度真实增加后再迁移。
- 不再增加无关 Agent 角色。先把 A 诊断、B 行动、C 调度的边界做深。

## 6. 看板验收

打开 `/team-progress-dashboard.html`：

- 每个项目至少显示 A/B/C 三张卡；每张卡有独立 window id。
- 真实心跳显示 `reported`；没有真实心跳只能显示 `derived`。
- 卡住与未处理进入提醒区。
- 看板不把测试夹具、派生状态、模型自评当真人完成记录。
- 三个人最后必须能拿出各自独立交付和一次共同真实闭环证据。
