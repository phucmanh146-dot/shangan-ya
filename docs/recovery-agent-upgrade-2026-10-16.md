# 上岸鸭：受阻与中断恢复的总调度增补

## 要解决的具体问题

学生本来愿意完成重要任务，却因为不会做、等材料、临时请求或连续受挫不断切换，最后既忘了原任务，也没有交出完整作品。网络、填表、查文献只是实例。现有作品诊断、能力试做、容量排程、版本保护和新版复核继续使用。

产品定位建议：面向大学生科研与创新实践，帮助学生取舍多项承诺、解决当前卡点、保存并恢复任务现场，并按原标准检查实际成果。

专业评价中的“RAG客服、ToDo、摄像头都已有大量实践”是合理的差异化提醒。Python是实现语言，LangSmith是运行与评测工具，知识库篇数是数据规模；它们都需要转化为可检查的任务价值。关于某届比赛提供几十万篇论文的回忆，当前没有确认比赛全名、届次和原赛题，不把它作为本项目的硬要求。

## 本次实际改动

| 原有基础与缺口 | 本次补到代码的行为 | 如何检查 |
| --- | --- | --- |
| 已有文件版本、任务状态和进程恢复，缺人的返回现场 | 保存当前步骤、位置、已完成内容、未解问题、下一动作、返回条件；用原项目版本事务落库 | A暂停做B，B后找回同一动作。跨版本条件不符时拒绝恢复 |
| 已有blocked/依赖，等条件后原意图可能丢失 | 外部条件需本人确认；约定时间只提醒检查。另一个任务必须实际验收后，才触发“可以返回” | 到点不自动解决；上传或pending_review不视为验收 |
| 已有截图/录屏求助，缺前次实际结果的连续使用 | 记录尝试、观察、本人报告结果、用时和可选原文证据；现有求助自动带上同任务版本近期尝试与当前原文摘录 | 实际字节/位置/哈希可回查；旧版本尝试与当前证据分开 |
| 独立B缺步骤时会回退通用三步 | 没有明确steps/micro_steps的制作任务进入blocked，列出待补字段；不能从普通开始入口绕过 | 缺操作卡时不进入制作、不占可执行排程 |
| 已有容量、截止和依赖，新增请求默认高优先 | 保存来源、答应谁、交付、明确截止、初估和本人重要程度。候选顺序解释紧急程度、重要性、依赖及返回上下文 | 普通请求保持当前任务；更紧急/重要候选可建议切换，但必须先保存现场 |
| 临时收到的请求没有可靠交接 | 新请求先进入未绑定承诺，可编辑、交给A核对，行动卡形成后再绑定具体任务 | 收集不自动使旧计划过期；本人选择交A才刷新诊断。修改保留事件历史 |
| 连续疲惫、受挫需要不同帮助 | 记录本人反馈，缩小建议的首次投入量，提示可检查小片段与短休后的返回安排 | 同一任务的首次投入建议发生变化，不靠摄像头推断情绪 |
| 有执行/复核接口，缺运行过程证据 | 导出本项目现场、尝试、条件确认、返回与承诺轨迹 | 计数来自实际操作，未将其写成效率提升或获奖分数 |

本次候选顺序面向**当前项目、当前负责人、当前可用分钟**，是容量初筛。它不代替B已有的真实空档、多人冲突、缓冲与周期排程，也没有实现跨项目全局最优调度。未绑定承诺保留待诊断，不能直接变成已开始或已完成的任务。

## 七步主流程怎样衔接

1. 保存本轮目标、验收条件、本人任务与现有作品。
2. A定位有来源的差距，记录未知，提出当前所需的最小试做。
3. B生成具体动作，按可用时间、能力与依赖给计划预览。
4. 用户确认采用。临时请求先核对是否值得打断；卡住时记录尝试并向现有求助入口提供材料。
5. 学生实际执行，记录用时和卡点，提交确切的新版文件。暂停时保存现场和返回安排。
6. A按原验收标准读取新版，逐项给通过、未过、未知及证据，成员核对确认。
7. B只调整剩余任务。已完成、进行中、待复核和锁定内容继续受保护。

“条件满足”“尝试成功”“回到任务”“任务验收完成”和“作品全部差距解决”各自记账。

## 技术实现与数据来源

- Python本地HTTP服务，SQLite保存项目、材料字节、版本及历史。新记录在项目的`recovery`字段中保存，共用`expected_version`与原有原子事务，不创建第二份浏览器任务库。
- 现场卡记录原诊断版本和任务定义指纹。只调整日程且任务定义不变，可以继续返回；目标、材料动作或前置条件变化时，需要重新核对现场。
- 同一项目中，同一负责人默认保留一个进行中的任务。切换先存现场，其他负责人可独立推进。普通开始入口和恢复入口共用前置、能力与版本检查。
- 求助依据`project_id + task_id + action_id + input_version + locator`读取SQLite中保存的材料，并提取当前原文位置。给模型的字段为有界摘要，原文摘录最多300字、近期尝试最多2次；完整记录保留。
- 这属于按任务/版本/位置读取材料与尝试记忆。**本次未新增向量库、语义检索或跨论文推理**，不把精确位置读取包装成新的RAG算法。
- 尝试有原文证据时核对引文，否则明确为本人报告。无论哪种，都不能绕过原作品提交和复核。
- 旧的摄像头观察仍为可选能力。当前难题以任务相关的材料、错误区截图、录屏关键画面和本人反馈为输入。

主要文件：`team_recovery.py`、`team-recovery.js`、`team_orchestrator.py`、`team_rescue.py`、`learning_agent_server.py`。A输入包与队友导出包现在也携带未绑定承诺；A的诊断仍必须满足原来的实际材料与引文约束。

### 接口

所有写操作继续携带`project_id`、`expected_version`；涉及已采用计划的操作另需`expected_plan_version`。

| 方法与路径 | 用途 |
| --- | --- |
| POST `/api/agent/team/recovery-pause` | 保存现场、返回条件和下一动作 |
| POST `/api/agent/team/recovery-condition` | 本人确认条件，不能代替另一个任务的验收 |
| POST `/api/agent/team/recovery-resume` | 核对版本/前置/能力后恢复执行 |
| POST `/api/agent/team/recovery-attempt` | 保存实际尝试、观察、结果自述及用时 |
| POST `/api/agent/team/recovery-commitment` | 新建或编辑来源承诺，绑定形成后的任务 |
| POST `/api/agent/team/recovery-checkin` | 保存本人状态反馈 |
| GET `/api/agent/team/recovery-agenda?id=...&member_id=...&minutes=30` | 当前项目的候选顺序、等待项、未绑定请求和容量初筛 |
| GET `/api/agent/team/recovery-context?id=...&task_id=...&action_id=...` | 当前动作的真实材料及近期尝试 |
| GET `/api/agent/team/recovery-export?id=...` | 导出本项目操作轨迹 |

### 运行

```bash
cd learning-agent
python learning_agent_server.py --port 8901 --with-team-ai
```

打开`http://127.0.0.1:8901/team.html`。使用现有AI连接配置；未配置时实际模型求助继续明确报错。也可以不加`--with-team-ai`，通过原有JSON交接接收A/B的真实交付。
