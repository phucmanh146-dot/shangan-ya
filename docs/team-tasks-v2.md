# 三人开发任务：从模糊竞赛任务到可执行的小步骤

新旧任务逐项对比、具体交付与开工顺序见 [任务变更对照表](task-changes-v2.md)。
更新：2026-10-10。此版替代旧版以通用阶段拆分为中心的任务范围；属于开发要求，不代表新增能力已实现。PPT 是验收案例之一，产品同时面向调研、策划、数据分析、代码、答辩等竞赛任务。

## 共同目标
用户提供领到的任务、现有成果、新增资料、理想效果/参考作品、个人理解与能力、截止时间和实际空档。系统定位现状和目标之间的具体差距，解释参考做法为什么有效，再生成符合本人能力的最小可执行步骤。用户上传新成果后，系统检查哪些差距消失、哪些仍在，并更新后续指导与日程。
必须区分比赛硬性要求、用户目标、参考作品做法与系统建议。参考好看不等于符合本次比赛；不能照搬未知数据、把示例写成官方标准。

## A：材料对照、目标分析、能力诊断
分支：feature/diagnosis-research-agent
- A1 读取并定位：整理任务、现有成果、参考成果、新旧资料的版本和可读状态，定位到页/段/表格单元格/代码函数。无法读取的部分标未知。
- A2 对比变更：逐条列出新资料替换或新增了什么，影响现有成果哪个位置、哪条结论；比较数据时间、单位和样本口径，口径不同不能直接替换。
- A3 拆参考：按结构、论证、证据、表达与呈现分解参考成果；每个值得借鉴的点写“位置、具体做法、解决的问题、适用条件、我方是否需要”。推断理由标为分析，不冒充作者意图或获奖原因。
- A4 诊断个人：结合已有成果、用户解释和小样试做，区分已证明会做、自述会做、尚未验证、需要指导；让用户用自己的话解释下一步，不凭一句自述打能力分。
- A5 复核新成果：对应原缺口给出已满足/部分满足/未满足及证据，反馈给 B；正式完成由队长流程确认。
交付：diagnosis.json、材料版本清单、现状目标对照页、参考拆解页、能力证据与未知项。
验收：任一差距都能追到材料位置；任一变更都能找到影响对象；缺材料不臆造。

## B：最小步骤指导、针对性学习与时间安排
分支：feature/action-planner-agent（本轮用户）
- B1 将每个差距转为操作链，保留 A 的证据、目标位置和原因。禁止只输出“收集资料、优化内容、制作初稿”。
- B2 每一步必须写：输入版本、打开的文件/工具、具体位置与对象、单一动作、动作原因、预期变化、输出、检查方式、失败后怎么办。没有足够信息时先补充或试做，不编造按钮和内容。
- B3 按能力调整颗粒度：会做的可合并；不会的拆成能试做的小步，附针对当前缺口的资料位置与练习。用户解释或试做不通过则补指导，不展开无关系统课程。不强制每步固定分钟数。
- B4 按依赖、用户选择与真实空档排程，分别估计学习、操作、等待、反馈修改；保留缓冲，标明估时依据及不确定性。
- B5 新资料/新成果到来时，依据 A 的影响范围更新相关步骤；保护已完成、进行中与锁定安排，有冲突先展示再确认。
- B6 用户卡住时提供下一项可尝试操作及成功标志；时间不足展示具体取舍和影响，不自动删除必交项或延长官方截止。
交付：plan.json、可展开的小步骤任务卡、当日安排、变更前后对照、卡点指导记录。
验收：另一成员按一张卡独立产出可检查的小成果；不能仅以字段齐全或任务数量判断通过。
现有规则排程和通用阶段拆分可复用；领域级精细指导仍为待开发/验收内容。

## 队长：材料入口、交互执行、版本与联调
分支：feature/orchestrator-agent
- C1 提供分别上传原任务、当前成果、参考成果、新资料的入口，显示版本、用途和读取失败；保存用户理解、能力证据、官方/内部 DDL 与空档。
- C2 将 A 对照结果和 B 操作卡接到同一条任务：用户能展开“为什么这样改”、查看对应材料位置、选择今天做哪一步。
- C3 提供提交小成果/截图、我不理解、操作失败、实际用时与临时占用入口，按问题调用 A 复核或 B 补指导。
- C4 采用与撤销保存版本，防旧结果覆盖新文件；区分提交、待验收、已验收。进度以有证据的验收为准。
- C5 联调同一真实案例，并换一种非 PPT 任务复验；保存可复现输入输出、操作记录、失败与恢复证据。
交付：统一操作页面、版本与执行记录、联调证据包。
验收：从上传到逐步修改再到复核重排连贯完成，刷新后可恢复，失败可见。

## 三人交集与交接
| 交接 | 内容 | 责任 |
|---|---|---|
| 队长 → A | 原任务、各类材料与版本、用户目标/理解/时间 | 队长保持原文，A 判断可读与证据 |
| A → B | 具体位置、现状、目标、差距、原因、能力证据、影响范围 | A 解释为什么，B 决定如何一步步做 |
| B → 队长 | 操作卡、检查方式、依赖、日程、假设与待确认项 | B 生成草案，队长展示并保存用户选择 |
| 新成果 → A → B | 成果版本、检查结果、仍存差距 | A 复核，B 更新受影响指导，队长确认正式状态 |

## 一张小步骤卡的内容
task_id / gap_id / input_version / owner / target_locator / action / reason / expected_change / output / self_check / failure_next / capability_basis / estimate / dependency / deadline。
定位字段通用：PPT 页与对象、文档段落、表格工作表与单元格、代码文件与函数均可。小步骤和上层交付物关联，不把每次鼠标点击当独立里程碑。
示例（待真实材料替换）：核对某页图表引用的新旧数据的单位和统计周期 → 留下一行核对记录 → 口径相同才更新图表 → 根据图表重新检查标题结论。未知页码不得写成真实位置。

## 本轮验收与 DDL
上版 10 月 11–12 日的时间是针对旧范围的建议，未获队员确认；新增精细诊断与指导后，不再作为本版交付承诺。官方比赛截止仍待提供。
| 顺序 | 可检查的交付 | 截止安排 |
|---|---|---|
| 1 | 三人选定一组真实输入、参考目标、验收人与可用时间 | 建议 10 月 10 日 20:00 前确认范围；尚非已认领 DDL |
| 2 | A 交出一处具体差距及依据，B 为其交一张可执行操作卡 | 基于三人确认的工时确定内部交接时间；目前待确认 |
| 3 | 队长接通上传、指导、提交、复核与保存 | 在官方截止前预留实际反馈与修复窗口，日期待确认 |
| 4 | 换一种非 PPT 竞赛任务复验；插入新资料和临时占用 | 记录通过/失败及修复负责人；未通过不计完成 |
禁止为显得精确编造日期。排期确认后必须写完整日期、时刻、时区、负责人和依赖；容量不足先协商范围。

共同通过标准：能解释当前差距、参考为什么有用、自己会什么、下一步具体做什么；用户完成小步后能提交证据得到针对性反馈。至少覆盖参考不适用、数据口径不同、资料不可读、不会操作、新资料影响旧结论、当天排满等情形。
