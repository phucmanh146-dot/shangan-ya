## 1. 我们要做成什么

服务于已经领到竞赛任务、持有部分成果、却不知道如何达到目标的成员。产品应能回答：当前作品哪处不足，依据是什么；本人哪项能力已证明、哪项尚未验证；下一步具体改哪里，做完交什么，怎样检查；有新材料或突发占用时，余下步骤怎样调整。

首轮选一处可定位、可核验的关键差距，让成员真正完成一次修改并提交新版，再给出有证据的复核。继续用第二种交付物复验；PPT 只是例子，产品不能写死为 PPT。优先支持可提取文字的 PDF、Markdown/TXT、CSV；不能可靠读取的部分保留未知。

借鉴“练习后反馈”的设计，把能力诊断变成实际试做，把完成进度绑定到新成果。是否优于普通一次性规划，要用同输入的对照结果验证，尚未测得的效果留空。

## 4. 交集在哪里，沿用什么接口

| 交接 | 交接对象 | 约束与责任 |
| --- | --- | --- |
| 队长 → A | 同一项目的任务、材料用途与版本、目标、解释/试做、空档 | 队长保留输入；A 判断真实可读位置与证据，不凭材料名称猜内容 |
| A → B | 兼容 `Diagnosis`：sources、artifact_versions、gaps、member_profiles、unknowns | A 提供材料证据与试做判断；B 引用真实 gap/source/版本。试做细表可先以证据附件交付，新结构化字段需共同约定 |
| B → 队长 | 兼容 `Plan`：tasks、micro_steps、acceptance_criteria、time_blocks、unscheduled | 复用 `steps` 与状态；不改变 schema_version 0.1。队长校验格式、引用和版本，不据此保证内容真实可执行 |
| 新成果 → A → B → 队长 | 成果版本、原 gap/task、逐条复核、剩余问题、影响范围、日程草案 | A 判断内容；B 给剩余动作；用户确认安排、验收者核对证据。正式状态由总控保存 |

优先复用总控 `/api/agent/team` 的 create、diagnosis、propose、apply、feedback，以及服务端 `run_handoff(data, researcher, planner)` 和现有总调度适配入口，详见 [队长交付](captain-delivery.md)。`expected_version`、`expected_plan_version` 按各接口现有约定传递，冲突需刷新。

精细任务在 `feedback` 以 `action=approve` 正式通过时，须提交与 `acceptance_criteria` 顺序和数量一致的 `criterion_results`；每项包含原条件 `criterion`、布尔 `passed` 和非空所见证据 `evidence`。全部通过才可 completed；失败走 reject 退回。A 的复核建议不能省略这一步人工验收，也不能自行覆盖任务状态。

细动作字段必须与 [契约第 7 节](p1-contract.md) 对齐。当前总控只确认引用已登记，材料本身的真实性与位置需 A 检查。A 自动复核、试做专用字段、报告自动生成与扣子平台桥接均是待实现/联调项；本文件不引入可直接调用的新 HTTP 端点。暂用人工复核或证据附件时，在运行记录标清人工环节，不据 `mode=live` 声称已自动验真。

## 5. 一个足够具体的验收例子

以下是人工构造样例，不是用户上传的数据、真实页码或比赛要求；实际开工必须换成真实输入。

假设当前报告“测试结果”段写 7/10＝70%，同口径最新 CSV 给出 18/30＝60%，参考作品明确列出样本数和来源。目标是让报告结论与已核实的最新数据一致，且成员能解释计算与适用范围。

| 环节 | 做什么 | 留下什么 / 怎样检查 |
| --- | --- | --- |
| A 定位并核对 | 找出报告位置和 CSV 行列，核对时间、问句、样本范围与单位；解释参考标样本数的适用性 | 一条带来源的差距；口径不同先停替换，转为补核对 |
| A 试做 | 请成员计算 18÷30，并说明这个比例能支持什么结论 | 保存答案；计算失败与范围解释失败分开，不直接断言“能力差” |
| B 最小指导 | 不会计算先示范计算过程并给一道同类复算；会计算就直接记录分子、分母与结果 | 一张练习/计算卡、一份可复算记录；实际数字以材料为准 |
| B 修改指导 | 分开执行数字修订、相关措辞修订、补样本量和已知来源、另存新版本 | 每步有明确位置、输出、自检；缺日期写待补充，不填假日期 |
| A 复核与总控验收 | 检查新版数字、结论范围、样本与来源；逐条展示证据再人工通过/退回 | 新成果与版本、review、验收记录；留错数字的副本不能通过 |
| B 弹性调整 | 插入临时占用，仅移动还没完成且允许调整的动作 | 保留已完成计算与修订；列出剩余空档和风险，用户确认后采用 |

第二场景可换成另一种竞赛交付物，例如 CSV 结果表的计算与来源核对；位置和检查随真实材料改变。不能把每种任务都套成“第几页 PPT”。

## 6. 三小时容量内怎么开工

沿用 v4 的临时容量假设：全队合计每日 3 人时，三个 45 分钟产物块＋45 分钟机动；不是默认每人各 3 小时。各模块实际耗时需用首例校准，不能把下列交接点当完成时长承诺。

| 先后接点 | 当前先交的最小结果 | 等待时可以独立做什么 |
| --- | --- | --- |
| 开工 | 队长选一组可读的真实输入与一项目标条件；核对适用比赛规则 | A 准备读取与试做模板；B 用明确标 Demo 的输入检查契约 |
| 第一次交接 | A 先交一条真实 gap 和试做证据，B 先交一张能执行的卡 | A 继续补来源；队长检查接收与预览；不等整份“大报告” |
| 第一次成果 | 用户按卡留下一份新版，A 逐条复核，队长保存人工验收 | B 根据实际卡点修正下一步与估时 |
| 核心通过后 | 加突发占用、第二种交付物和普通规划对照 | 再按 v4 扩展案例与试用，不先做平台迁移或全格式自动编辑 |

某天排满就把尚未完成的块移到截止前的真实空档，保留已交产物。机动耗尽时优先保留一个真实流程、证据与成果复核，后移第二场景和平台桥接；容量仍不足则写清未完成及取舍。官方 DDL、内部完整时间与每个人可用时段以实际确认结果为准；v4 的日期是建议，不替队友认领。
