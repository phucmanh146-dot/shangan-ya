# 队长与两位队友：一步一步把 Agent 接起来

仓库：[phucmanh146-dot/shangan-ya](https://github.com/phucmanh146-dot/shangan-ya)

共同开发入口：[p1/integration](https://github.com/phucmanh146-dot/shangan-ya/tree/p1/integration)

依据：用户上传的三人协作手册第 4-12 页，以及 2026-10-08 的最新说明。我们参考上岸鸭产品思路，沿用原设计者的 PRD 开发自己的三人项目。参考主页中的人和团队不作为我们的成员或履历。

你不需要一开始懂全部代码。每轮只处理一个小交付，按“操作 → 看结果 → 留证据 → 再继续”的顺序走。

## 1. 先认清五个东西

| 名词 | 大白话 |

| 分支 | 从同一份项目开始的一条工作线；一条分支包含整个项目 |

4. 点 `docs`，打开本指南和 `p1-contract.md`。
5. 记住你自己的分支，开发时切换到它。

| 谁使用 | 分支 | 提 PR 时的 base |
| --- | --- | --- |
| 队友 A：诊断与资料研究 | `feature/diagnosis-research-agent` | `p1/integration` |

`main` 当前保留原部署包；新代码在联调分支中。旧 `develop`、`feat/brain898` 是上次协作设置的遗留分支，本轮从上表分支开展工作。分支名不会自动限制谁能修改。

## 3. 邀请真实队友加入

队长已经提供一位队友的准确联系邮箱。该邮箱仅用于私下核对和邀请，不写入公开仓库。A/B 对应哪位真实成员，需要认领后明确记录，不能从参考截图推断。

1. 队长打开仓库 **Settings → Collaborators**。
2. 先检查已有成员和待处理邀请。之前文档曾错误地把截图账号当成队友，应核对并处理这条旧邀请。
3. 点 **Add people**，输入队友确认的完整 GitHub 用户名；也可按页面支持的方式输入其邮箱。
4. 核对匹配结果。查不到时，让队友发自己 GitHub 主页的完整链接；不要选择相似用户名。
5. 点 **Add … to shangan-ya** 发出仓库邀请。
6. 队友使用自己的账号打开通知或邀请邮件，点接受。
7. 队长回到协作者列表，确认是已加入，不是 Pending。
8. 用同样步骤处理第二位队友。

建立分支不等于完成邀请。账号尚未核实、邀请未发送、待接受和已加入是不同状态。当前公开文档不声称这两位队友已经加入。

官方说明：[邀请个人仓库协作者](https://docs.github.com/articles/inviting-collaborators-to-a-personal-repository)。

## 4. 第一次把代码放到自己的电脑

如果使用 GitHub Desktop：

1. 用自己的 GitHub 账号登录。
2. 点 **File → Clone repository → URL**。
3. 填 `https://github.com/phucmanh146-dot/shangan-ya.git`，选择保存目录，点 **Clone**。
4. 点 **Fetch origin**。
5. 点 **Current branch**，选上表中自己的分支。
6. 确认当前分支名称正确，再打开编辑器。

已有本地项目时先查看 Changes；有修改先保存或提交，再 Fetch 和切换。不要重新建同名分支覆盖旧工作。

### 先把已有模块跑起来

Windows 用户在项目目录打开 PowerShell，一行一行执行：

```powershell
cd learning-agent
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe learning_agent_server.py --port 8901
```

然后在浏览器打开 `http://127.0.0.1:8901/learning-agent.html`。终端保持打开。

成功标志：页面能打开，后端健康接口 `http://127.0.0.1:8901/api/agent/health` 返回 JSON。模型字段仍显示未配置时，按[模块 README](../learning-agent/README.md)接入后再验一次真实调用；不能把页面打开当成 AI 已经可用。

如果报错，复制完整报错并记录停在哪一步，再处理这一项。视频生成另需 FFmpeg、Pillow 和中文字体，具体见模块说明。

### 对照参考 PR：环境为什么还要单独配置

用户提供的参考图是一条“添加可复现的团队环境和代理设置指南”的 PR。我们借鉴其协作方式，不引用或修改对方的私有代码。

| 跟随 Git 的内容 | 每人需要在本机配置的内容 |
| --- | --- |
| 源代码、依赖清单、配置示例、启动说明、测试 | Python 环境、模型地址与授权、搜索授权、本机数据、可选视频工具 |

本项目的 `.env.example` 用于说明配置项，不应假设复制成 `.env` 就会被程序自动加载；按模块 README 使用后端环境变量或现有 AI 设置入口。先确认基础服务，再确认模型调用，再确认检索，最后验收图片和视频。每一步分别留下结果。

## 5. 三个人各负责什么

| 负责人 | 负责 | 第一份交付 | 队长怎么检查 |
| --- | --- | --- | --- |
| A | 规则、材料、案例、成员访谈和差距判断 | 页面可查看的诊断包，至少一条有证据的差距和一条未知项 | 点开来源能找到对应内容；材料不足如实说明 |
| B | 将差距转为任务、学习顺序、估时、依赖和日程 | 用 A 的诊断包生成任务，再分别给 30 分钟和 90 分钟的安排 | 每项任务能追溯 gap；无时间冲突；排不下明确列出 |
| 你 | 公共入口、调用顺序、数据保存、求助、变更与联调 | 输入材料后能看到诊断、任务、执行状态；刷新后仍在 | 状态可追溯；失败显示原因；旧版本不覆盖新状态 |

A 回答“缺什么、为什么”；B 回答“先做什么、何时做”；你负责把它们接起来，并保存事实与反馈。A 负责能力访谈和缺口判断，B 负责把能力缺口排成最短补齐路径。

每个人需要同时交付自己模块的接口、必要页面和验收证据。AI 辅助工具可以帮忙写和检查，但成员本人需要能解释输入、输出与限制。

## 6. 你作为队长，按这个顺序推进

### 第 1 轮：只打通一次交接

1. 打开 `docs/p1-contract.md`，三人一起看字段含义。
2. 请 A 用同一个小案例写出诊断包；所有示例明确标为 Demo。
3. 请 B 用 A 的诊断包生成一个任务，保留 `gap_id` 与诊断版本。
4. 你把两个结果接到页面上，显示任务的来源、第一步和完成标准。
5. 刷新页面确认数据仍在；给一次错误输入，确认能看到具体失败原因。
6. 保存一张流程截图、一份输入输出和运行记录，作为本轮验收证据。

通过标志：数据是程序传过去的，不需要人把 A 的结论重新复制给 B。

### 第 2 轮：接真实材料、真实搜索与真实模型

1. 选一份可读的实际材料或公开链接。
2. A 返回来源、原文位置、要求与未知项。
3. B 根据成员能力和时间生成计划。
4. 你检查运行记录，确认实际调用了模型与搜索，结果有真实内容。
5. 关闭或模拟某项服务失败，再检查页面是否显示失败和恢复入口。

通过标志：能够解释每条关键结论来自哪里。只有示例数据时仍标 Demo；真实调用未经本轮验收不写“已打通”。

### 第 3 轮：执行、困难求助和局部重排

1. 用户选一项今日任务，B 排入可用时段。
2. 用户完成第一步，记录产物、实际用时和证据。
3. 用户上传报错截图或录屏，系统给出操作与成功标志。
4. 用户输入临时安排；B 返回受影响任务、调整前后和理由。
5. 用户确认采用，你保存新版本；撤销时保留版本记录。
6. 再上传新成果，让 A 复核对应缺口是否缩小。

通过标志：已完成任务和锁定日程不被重排；旧版本提交被拒绝并提示刷新；看不清的画面不编造细节。

### 第 4 轮：换一个人、换一个目标再跑

1. 更换目标或比赛，检查有没有沿用写死的要求。
2. 更换成员能力与可用时间，检查路线是否合理变化。
3. 用一份不存在或无法读取的资料，检查未知项是否保留。
4. 让截止前容量确实不足，检查是否提示取舍，而不是排出冲突。
5. 在新环境按启动文档复现，保留日志与截图。

通过以上检查，再准备 `p1/integration → main` 的发布 PR。“完整 Agent”以可复现的验收为标准，不承诺无缺陷或自动获奖。

## 7. 队友怎样提交给你

1. 在自己的职责分支完成一个小任务。
2. 本机启动并验证；留下实际结果。
3. 在 GitHub Desktop 的 Changes 里只选择本次相关文件。
4. 写清 Summary，例如 `feat: 诊断报告增加原文来源`。
5. 点 **Commit to 当前分支**，再点 **Push origin**。
6. 到 GitHub 点 **Pull requests → New pull request**。
7. **base 选 `p1/integration`；compare 选自己的职责分支。**
8. 填写目的、改动、验证步骤、证据与已知限制，然后创建 PR。

| 谁 | 创建 PR 的入口 |
| --- | --- |
| A | [诊断研究 → 联调](https://github.com/phucmanh146-dot/shangan-ya/compare/p1/integration...feature/diagnosis-research-agent?expand=1) |

## 8. 你在哪里监督，怎样合并

打开[待处理 PR](https://github.com/phucmanh146-dot/shangan-ya/pulls)。每次按相同顺序：

1. 看标题和 Conversation：是否只解决本轮的小任务？
2. 看 Files changed：哪些文件变了，有没有覆盖别人的公共字段？
3. 看 Checks 或运行记录：检查是否真的执行、结果是什么？没有 Checks 不能当作通过。
4. 启动该 PR 的版本，照作者给的步骤操作一次。
5. 对照任务卡检查产物和失败场景。有问题写明“哪一步、实际结果、期望结果”，要求队友继续修改原分支。
6. 核对 base 为 `p1/integration`，问题解决后再 Merge。
7. 你本人写的 PR 交给另一位队友审查。

Approve 是评审意见；Merge 才会合进代码。当前“队长检查后合并”是团队约定，本轮没有配置平台强制分支保护。

我可以在对话中结合代码、日志和截图逐项检查，指出下一步；持续后台监控需要另外配置自动化，本说明不表示已经开启。

## 9. 合并后，另外两人怎样同步

1. 先保存或提交自己的修改，确认正在自己的功能分支。
2. Fetch origin。
3. 将最新 `p1/integration` 合进自己的分支，再继续工作。
4. 有冲突时联系改动相关的人，一起判断，不能整份覆盖。

命令参考，当前分支必须是自己的功能分支：

```bash
git status
git fetch origin
git merge origin/p1/integration
git push
```
