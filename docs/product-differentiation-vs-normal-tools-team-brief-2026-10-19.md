# 上岸鸭与普通 ToDo / 学习助手的差异化设计（团队执行版）

日期：2026-10-19  
项目定位：面向大学生竞赛、科研与创新实践的资料驱动执行智能体。

> 核心主张：上岸鸭不是再做一个会聊天、会总结、会列计划的助手，而是把用户手里的真实项目材料转成有证据定位的微动作，并跟踪到真人完成新版本、独立复核和剩余问题重排。
>
> 以下是产品差异化设计和待验证假设，不代表已经证明行业首创。团队必须用真实竞品和用户试验验证。

## 1. 普通产品通常停在哪，上岸鸭必须多走哪一步

| 对比维度 | 普通 ToDo / 日程工具 | 通用 AI 学习助手 / RAG 问答 | 常见陪伴型/监督型工具 | 上岸鸭要做出的区别 |
|---|---|---|---|---|
| 输入 | 用户手动写任务 | 问问题、上传资料后获取答案 | 提醒、打卡、状态信号 | 读取真实项目材料，并锁定版本与具体位置 |
| 问题诊断 | 用户自己判断 | 模型概括问题，可能停留在建议 | 根据停顿或规则触发提醒 | 每条 gap 绑定当前证据、精确位置和来源证据 |
| 任务拆解 | 待办标题/子任务 | 通用步骤或长篇方案 | 监督用户完成既定任务 | 每个微动作都有输入版本、目标位置、产出、自检、失败下一步和来源 |
| 完成判定 | 用户勾选完成 | 模型根据对话推测 | 打卡或行为信号 | 必须有真实 V2 产物，并由独立环节按原始标准复核 |
| 中断恢复 | 回看日程/手动改计划 | 重新问一遍或翻聊天记录 | 提醒继续 | 恢复项目、版本、具体位置、尝试记录、卡点和下一动作；版本冲突时暂停确认 |
| 失败处理 | 用户自己重排 | 继续生成建议 | 再提醒一次 | 区分缺资料、动作不明确、工具失败、用户暂离；缺证据就 blocked/unknown |
| 结果证据 | 勾选状态 | 聊天答案/摘要 | 打卡记录 | 保存“目标→证据 gap→参考来源→行动卡→执行人→V2→复核→剩余问题”完整证据链 |

这张表是设计目标，不应未经实测就断言所有竞品都缺少这些能力。竞品分析必须用具体产品、具体版本和官方文档逐项核对。

## 2. 五项创新：每一项都要有可现场展示的证据

### 创新 1（主创新）｜人做、模型验：真实成果闭环

**一句话**：不把 AI 说“完成了”当成完成；只有真人产出新版本，并按原始标准复核，才进入通过状态。

流程：真实 V1 冻结 → A 给出带证据位置的 gap → B 生成有依据的微行动卡 → 队友不靠口头解释盲执行 → 形成真实 V2 → A 按原标准标记 pass/fail/unknown → B 只重排未通过项。

**和普通任务管理的区别**：普通产品往往以勾选或用户自报结束；本项目要求把完成状态绑定到可检查的作品版本与复核证据。

**现场证明材料**：V1/V2 真实文件、至少 3 条带精确位置的 gap、对应行动卡、执行人和实际耗时、A 的逐条复核及剩余问题。

**验收门**：任意抽取一条任务，能从 V2 反查到原始目标、问题位置、来源依据、行动卡和复核结论。缺任一环不得宣称闭环完成。

### 创新 2（主创新）｜任务现场恢复：不是恢复聊天，而是恢复工作位置

**一句话**：用户中断后，系统要说清“你正在改哪个版本、上次停在哪、尝试过什么、下一步做什么”。

保存项目 ID、作品版本、当前定位、已完成步骤、尝试过的动作、卡点、下一动作和返回条件。恢复前校验版本；材料变了或证据不够时要求用户确认，不静默续做。

**和普通历史记录的区别**：只保存对话不能确保知道用户当前正在编辑的文件版本、具体段落或代码位置；本项目要恢复的是可执行工作现场。

**现场证明材料**：中断前快照、重开后的恢复卡、版本变化场景、恢复日志。

**验收门**：模拟关页、换会话、更新文件后，系统能恢复正确项目和位置；若无法确认必须明确提示，而不是编造恢复成功。

### 创新 3（支撑创新）｜论文卡点多讲法转换，再回到原文验证

**一句话**：不是只把论文变成摘要或视频，而是针对同一处难点切换解释方式，随后用理解检查和实际动作验证是否推进。

流程：定位原文段落/公式/图表 → 生活类比、分层解释或图解 → 标出解释与原文事实的边界 → 一个理解检查 → 回到原文完成下一动作。

**与普通总结工具的区别**：摘要可读不代表理解；上岸鸭要求讲解结果对应原文，并记录用户能否解释或操作。

**证据**：同一原文的两个解释版本、原文定位、理解题及真实作答/操作。

**验收门**：不能仅凭用户点击“看完”或模型输出摘要标记“已学会”。

### 创新 4（支撑创新）｜5 分钟冷启动：先做出一个真实小产物再诊断

**一句话**：用户说“不知道怎么开始”时，先选一个尽量可在 5 分钟内启动、并能产生可见产物的动作，用实际试做识别卡点。

例子：找到一条论文原文证据、复现一个最小命令、修正一处 PPT、核验一个数据来源。5 分钟是启动目标，不承诺所有任务都能在五分钟内完成。

**与普通计划生成的区别**：不是再列十个子任务，而是观察第一个真实动作在哪里失败，并据此调整后续步骤。

**证据**：试做前判断、产物、实际耗时、失败位置、调整后的下一步。

**验收门**：必须记录真实试做结果；不能只生成“建议从第一步开始”。

### 创新 5（支撑创新）｜用户确认式低打扰分流

**一句话**：任务停滞不自动等于懒惰或疲惫；先询问原因，再选择解释、排障、保存现场或休息。

分流：听不懂→换讲法；工具/网络失败→排障或替代路径；临时有事→保存现场并记录返回条件；疲惫→由用户决定休息或继续。

**与普通提醒/摄像头监督的区别**：不靠单一提醒重复催促，也不未经同意推断用户情绪；由用户确认原因后选择下一条路径。

**证据**：同一任务停滞时，四种用户选择对应不同处理动作和状态记录。

**验收门**：系统的分流必须与用户选择一致；没有证据不得声称准确识别疲劳或情绪。摄像头和被动状态识别不作为比赛版主链路。

## 3. 真正能让评审看出区别的演示脚本（3–5 分钟）

1. 打开真实 V1：选团队正在做的 PPT、报告或代码，不使用虚构预置材料。
2. 展示证据 gap：指出具体页/段/代码位置，并打开外部参考原文定位；说明只借鉴方法，不照搬内容。
3. 展示行动卡：每一步包含 action、reason、expected_change、output、self_check、failure_next、source_refs；缺失时系统应阻塞，不输出通用三步冒充落地方案。
4. 盲执行：另一位队友只看行动卡，实际修改文件，记录用时与卡点。
5. 独立复核：A 对 V2 按原始标准给 pass/fail/unknown，展示对应证据。
6. 局部返工：B 只调整未通过项，已完成和锁定任务不被覆盖。
7. 现场中断恢复：保存任务现场，换会话/重新打开，再展示项目、版本、位置和下一动作是否正确恢复。

如果真人 V2 或独立复核还没完成，演示要明确标记“当前阶段/待验证”，不能讲成已经通过。

## 4. 竞品调研怎么做，避免只写口号

每个竞品单独建一行，记录：产品名、官网/官方文档、检索日期、版本/套餐、输入方式、是否绑定真实文件版本和精确位置、是否有证据化诊断、是否生成具体微动作、是否恢复工作现场、是否独立复核真实产物、失败是否阻塞、官方原文定位、可借鉴机制、与上岸鸭的差异和未证实点。

建议覆盖普通待办工具、通用 AI 文档助手、Agent 执行工具、学习类 AI 助手。不要用“竞品都做不到”代替逐项核验。

## 5. 团队分工与依赖

### A 同学｜竞品证据与 gap 诊断
1. 不重复已经完成的全网抓取；从已有资料中补齐至少 3 个相近产品/公开标杆的官方来源和原文定位。
2. 将普通产品与上岸鸭逐项比较；没有证据的功能标“未核实”，不要写“竞品不支持”。
3. 针对冻结的真实 V1 产出至少 3 条 gap：版本、精确定位、当前证据、参考来源、参考定位、提取的方法、不复制的内容。
4. 收到 V2 后按冻结标准复核 pass/fail/unknown。

**交付**：竞品差异矩阵、gap 清单、复核记录。  
**验收**：队友可以根据原文定位复查每条结论；只有首页链接或搜索摘要不算充分证据。

### B 同学｜行动卡与失败路径
1. 只处理 A 已核验的 gap。
2. 每个微步骤必须有 input_version、target_locator、action、reason、expected_change、output、self_check、failure_next、capability_basis、source_refs。
3. 不同材料类型采用不同操作：PPT、论文、调研数据、代码/接口不可一律套模板。
4. 缺少材料、定位或操作依据时标 blocked/unscheduled，不回退成通用三步。
5. A 复核后只重排未通过项，不覆盖已完成、进行中、待复核和锁定状态。

**交付**：真实行动卡、状态变化日志、失败分流样例。  
**验收**：没听过口头讲解的队友也能开始执行，失败时知道下一步做什么。

### C／队长｜真实闭环、集成和评审呈现
1. 冻结真实 V1 和原始验收标准。
2. 把 A 的 gap、参考原文和 B 的行动卡接成可追踪链路。
3. 安排另一位队友盲执行，记录真实 V2、用时和卡点。
4. 收集 A 的复核，检查是否只调整剩余问题。
5. 用真实中断场景测试任务现场恢复。
6. PPT 主讲 I1/I2；I3–I5 作为支撑创新。把“已实现、已测试、真人已验证、待验证”四种状态分开写。

**交付**：V1/V2 对照、端到端证据链、恢复测试记录、演示脚本和 PPT。  
**验收**：任何核心主张都能指向可打开的真实证据，而非只指向文案。

**执行顺序**：C 冻结 V1/标准 → A 竞品证据与 gap → B 行动卡 → 队友盲执行 V2 → A 复核 → B 局部重排 → C 汇总演示与数据。
