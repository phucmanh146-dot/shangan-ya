# 三人协作总调度｜队长总控

> 目标：把 A 的“差距诊断”、B 的“行动排程”和队长的“总控集成”连成一条真正可执行、可复核、可调整的 Agent 工作流。

## 1. GitHub 协作入口

- 仓库：`phucmanh146-dot/shangan-ya`
- 队长总控分支：`feature/orchestrator-agent`
- A 同学分支：`feature/diagnosis-research-agent`
- B 同学分支：`feature/action-planner-agent`
- 联调分支：`p1/integration`
- 最终发布：`p1/integration -> main`

GitHub 分支代表职责边界，不代表成员账号已经自动绑定。A/B 两位同学的真实 GitHub 用户名仍需以实际邀请和 PR 提交账号为准。

## 2. 三个人的区别

| 角色 | 核心问题 | 主要输入 | 主要输出 | 不负责什么 |
| --- | --- | --- | --- | --- |
| A 同学｜诊断与研究 | “现在到底差在哪里？” | 比赛要求、评审标准、现有成果、试做样本、资料来源 | 客观现状、差距矩阵、能力判断、优先级、根因、给 B/总控的接口信息 | 不负责完整排程，不负责全局状态保存 |
| B 同学｜行动与排程 | “知道差距后，具体怎么做、什么时候做？” | A 的差距包、成员能力、空闲时间、依赖关系、截止日期 | 原子步骤、学习补齐、估时、依赖、日程、局部重排方案 | 不重新定义差距，不负责最终总验收 |
| 队长｜总调度与集成 | “三个人的结果怎么串起来并真正跑完？” | A 的诊断、B 的计划、用户选择、执行反馈、截图/录屏、成果版本、突发安排 | 统一入口、状态流转、任务版本、困难救援、交接、验收、复核触发、最终闭环 | 不替 A 做完整研究，也不替 B 做全部细排程 |

## 3. A 同学当前已做内容（根据其交付文档纳入总调度）

A 同学当前模块是“差距分析 A 方案”。它提供任务名称、评审/交付标准、现有成果客观现状、先试做小样本、突发扰动预案等输入，并生成标准化 Markdown 差距分析报告。

A 的报告需要至少包含：

1. 任务总览与目标交付标准；
2. 现有成果客观事实；
3. 先试做样本，用来判断真实能力上限；
4. 差距矩阵：现状、目标、差距、判断依据、P0/P1/P2/P3 优先级；
5. 根因：信息缺失 / 能力短板 / 逻辑结构 / 素材误用；
6. 突发扰动预案，明确不可延期与可延期事项；
7. 给 B 的接口：每个差距必须能继续拆成“改哪里、交什么、怎样算完成、卡住怎么办”；
8. 给总控的接口：保存诊断版本，新成果提交后重新触发 A 复核。

### A 当前边界

A 目前不负责 B 角色 UI、完整任务排程、复核 UI、AI 自动填充矩阵、自动导入导出。因此队长总控不能把“A 已生成报告”误判为“项目已经跑通”。

## 4. 总调度主流程

### 阶段 0｜接收目标
队长建立项目实例，保存：项目目标、比赛/任务名称、截止日期、成员、现有材料、当前版本。

### 阶段 1｜派给 A：诊断
A 读取规则和材料，先确认事实，再要求最小试做样本，判断当前能力，输出 `Gap Package`。

**A -> 总控必须交付：**
- `task_id`
- `target_rule`
- `current_facts`
- `trial_evidence`
- `gap_items[]`
- `priority`
- `root_cause`
- `risk_rule`
- `source_links[]`

### 阶段 2｜派给 B：行动计划
总控把 A 的每一条 `G-xxx` 差距交给 B。B 不能只写“继续学习/继续优化”，必须拆成原子动作。

**B -> 总控必须交付：**
- 对应 `gap_id`
- 改哪里
- 做什么动作
- 交什么产物
- 预计多久
- 依赖什么
- 怎样算完成
- 卡住怎么办
- 能否延期
- 推荐执行日期

### 阶段 3｜队长总控排队
总控根据 P0/P1/P2/P3、截止日期、成员空闲时间、依赖和突发安排，生成“今天做什么 / 本周做什么 / 暂缓什么”。

原则：P0 不因普通突发随意延期；突发情况只重排受影响部分，不整套推翻。

### 阶段 4｜执行与困难救援
成员执行时上传截图、录屏、文字报错或中间成果。总控先绑定当前 `task_id + gap_id + action_id`，再决定：
- 直接给下一步；
- 退回 B，把动作拆得更小；
- 退回 A，说明原能力判断可能有误；
- 标记外部依赖并局部重排。

### 阶段 5｜成果提交
“做完”不等于“完成”。提交产物后先进入 `待验收` 状态，并保存版本号和证据。

### 阶段 6｜A 复核
A 对照最初目标、差距项和新成果重新判断：
- 差距是否缩小；
- 哪些要求已满足；
- 哪些问题仍存在；
- 是否出现新差距。

不合格：回到 B 生成下一轮动作；合格：总控关闭该差距项。

### 阶段 7｜总体验收
所有 P0 关闭、关键 P1 达标、证据完整后，队长总控才把项目标记为“阶段完成 / 可交付”。

## 5. 三人交接协议

总控不接收只有自然语言大段描述、无法定位责任的结果。A/B 的结果必须能落到统一 ID：

`project_id -> task_id -> gap_id -> action_id -> artifact_version`

这样才能知道：
- 这个任务为什么产生；
- 是 A 发现的哪条差距；
- B 为它拆了哪些动作；
- 谁在什么时候执行；
- 上传了哪个成果；
- A 复核结果是什么；
- 下一步是否需要重排。

## 6. 总控页面应该新增的三块

### A 输入卡
显示 A 同学的差距报告：目标、现状、试做证据、差距、优先级、根因、来源、突发规则。

### B 行动卡
按每条差距显示 B 的执行步骤、负责人、预计时间、依赖、完成标准、卡点预案和日程。

### 队长总调度卡
统一显示：
- 当前项目阶段；
- A/B 是否已交付；
- P0/P1 未关闭数量；
- 今日执行项；
- 待验收成果；
- 卡点与突发事件；
- 下一位应该接手的人；
- 最新版本与上一个版本差异。

## 7. 队长与 A/B 最关键的区别

A 的价值是“判断对不对”；B 的价值是“行动能不能做”；队长的价值是“整个系统能不能持续跑通”。

所以队长总调度不是第三份重复的任务清单，而是负责：**接收 A -> 调用 B -> 保存状态 -> 处理执行 -> 触发复核 -> 局部重排 -> 最终验收。**
