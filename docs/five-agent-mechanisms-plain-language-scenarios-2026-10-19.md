# 给队友看的白话技术拆解：寄存器、循环、上下文、工具调用、跨对话记忆

日期：2026-10-19
项目：上岸鸭——面向大学生竞赛、科研与创新实践的资料驱动执行智能体
对象：不懂 Agent、RAG、状态机或后端开发的队友。先看场景，再看术语。

## 先记住一句话

上岸鸭不是把五个技术名词放进 PPT，而是让一个第一次做竞赛项目、遇到困难又中断的学生，第二次打开时不用重新解释一遍，就能从原来的文件、原来的问题、原来的下一步继续做；做完后还有证据证明作品真的改好了。

- **寄存器（任务状态存档）**：记住当前工作现场。
- **循环机制**：决定继续、换方法、求助还是停止。
- **上下文管理**：决定本轮给模型看哪些必要材料。
- **工具调用**：让系统实际检索、读文件、保存、检查，而不是只说建议。
- **跨对话记忆**：新对话回来时先确认项目，再接回正确存档。

这些机制都可以用现有工作流平台搭出来。差异不是“我们也有”，而是具体存什么、如何转、何时停、怎样证明成功。

## 场景：给竞赛 PPT 第 3 页补一个有来源的竞品对照项

当前文件：参赛方案_v1.pptx。第 3 页“竞品对比”表格第 2 行缺少来源。队友不懂“证据链”是什么意思。

1. 系统锁定版本和位置：参赛方案 V1，第 3 页，竞品对比表第 2 行。
2. 不直接生成整篇 PPT，而是给一个 5 分钟动作：“打开已抓取的官方产品说明，找到一个明确写出的功能，把功能名称和原文出处填入第 2 行。”
3. 用户点“看不懂”。系统解释：“证据链就是别人点开来源后，能检查你这句话有没有依据。”随后请用户复述或填一格。
4. 用户仍然卡住。系统记录用过什么解释、试过什么、卡在哪里；类似帮助最多两轮，之后停下来问原因，不无限循环。
5. 用户说“不知道该搜什么”。工具将大白话转成检索词，在已接入资料中查找，最多返回 1–3 条来源和精确位置；没找到就明说，不编造。
6. 用户填完一格，产生参赛方案 V2。复核环节按原标准检查：功能描述是否准确、来源是否能打开、原文是否支持结论。
7. 用户关掉页面。第二天说“继续昨天那个”，系统先确认项目，再显示“做到哪、完成了什么、下一步 5 分钟做什么”。

下面按这一个场景解释五个机制。

## 一、任务状态寄存器：不是芯片寄存器，是应用的“存档点”

### 原理
CPU 寄存器是计算机硬件中保存少量即时数据的部件。本文的“任务状态寄存器”是借用这个比喻，指应用层结构化状态记录，不是直接操作 CPU 寄存器。它可以存放在 SQLite 数据表或其他持久化存储中。

把它想成游戏存档：记录正在第几关、拿到了什么、失败过什么、下一步去哪，而不是让用户自己翻一大段聊天记录。

### 具体存什么

| 字段 | 白话解释 | 本场景的例子 |
|---|---|---|
| project_id | 哪个项目 | 人工智能应用创新大赛 |
| member_id | 谁在做 | B 同学 |
| task_id / micro_step_id | 哪个任务、哪一个小动作 | 补竞品对照表第 2 行 |
| artifact_version | 正在处理哪版文件 | 参赛方案 V1 |
| locator | 文件的准确位置 | 第 3 页，竞品对比表第 2 行 |
| acceptance_criteria | 怎样才算合格 | 有官方来源、原文支持表述、链接可打开 |
| blocker | 卡在哪里 | 不懂“证据链”，不知道检索词 |
| attempted_actions | 已试过什么 | 看过官方说明首页；第一次解释仍没懂 |
| next_action | 回来后第一件事 | 找官方功能说明并补一格 |
| return_condition | 什么情况下回来 | 用户休息后确认，或收到队友提供的来源 |
| state_kind | 用户本次选择的状态 | “看不懂”或“有点累”，仅本次状态 |
| commitment | 对谁承诺交什么 | 周三前把第 3 页交给队长 |
| timestamps | 开始、暂停、恢复时间 | 记录实际时间，不用预估冒充实际 |

### 真实行为
用户 15:02 点“有点累”：系统保存当前项目、版本、第 3 页第 2 行；记录已完成第 1 行、未完成第 2 行缺来源；记录下一动作；显示 5 分钟休息选项。15:07 到点不代表用户已经回来。系统必须等用户实际确认，不能伪造“已恢复”。

### 验收标准
- 关页面、刷新或服务重启后，恢复同一项目、版本、位置和下一动作。
- 文件版本改变时先提示确认，不能接到过期位置。
- 一次“累了”不变成永久标签。
- 重复点击暂停不生成多个休息会话。
- 恢复页用三行说明：做到哪、完成了什么、下一步做什么。

### 常见误解
- 错误：寄存器就是记用户等级、积分或学到第几课。
- 正确：上岸鸭关键是存当前工作现场和证据位置。
- 错误：数据库有任务表就等于恢复完成。
- 正确：必须实测关页再打开，核对版本、位置和下一动作。

## 二、循环机制：不是无限让 AI 重试，而是知道何时换法、求助或停止

### 原理
循环就是“做一次—看结果—决定下一次”。要分成三种：

1. **工具循环（模型内部）**：模型调用搜索或文件工具，检查结果，再决定下一步。
2. **人类动作内循环**：给用户一个 5 分钟小动作，检查是否真的做了；没做或没懂，就换解释、拆小或求助。
3. **作品验收外循环**：V1 → 行动卡 → 真人执行得到 V2 → 按原标准复核；没过的部分才回去修改。

### 本场景怎么转
**工具循环：** 第一次搜索“证据链”结果太泛，就改成“官方产品说明 + 功能名称”。第二次拿到官方原文后停止。如果仍找不到、网页打不开或达到调用上限，就报告“未找到”，生成求助卡，不无限重试。

**人类动作内循环：** 系统给动作“把官方功能名称和原文出处填进表格第 2 行”。用户没动手或点“看不懂”，就换成一句话解释或半填空例子。再试一次仍失败，停下来问：“你是看不懂概念、找不到材料、工具报错，还是现在不想继续？”随后按用户选择分流。同类帮助建议最多两轮，不能反复播放同一段解释。

**作品验收外循环：** B 按行动卡修改出 V2；A 用最初冻结的标准逐条检查。来源可打开且原文支持结论，该项通过；链接失效或原文不支持，该项未通过；证据不足标“未知”。未通过的项才重新出卡。所有判据通过并经人工确认，才结束本轮。

### 三种循环的继续、换法、停止

| 循环 | 继续 | 换策略 | 停止 |
|---|---|---|---|
| 工具循环 | 获得新证据 | 查询过宽、结果不相关、工具失败 | 证据够用、工具不可用或到调用上限 |
| 人类动作内循环 | 用户完成 5 分钟动作 | 没做、听不懂、同一错误再出现 | 同类帮助连续无效（建议两轮），问原因、求助或暂停 |
| 作品验收外循环 | 仍有未通过判据 | 针对失败项重新出卡 | 全部通过且人工确认；或明确标记阻塞/延期 |

### 为什么重要
计划不是结果。真正的结果是用户是否产出新版本，以及新版本是否满足原标准。模型说“完成了”、用户点“我懂了”，都不能代替真实产物和复核证据。

### 验收标准
- 每轮保存输入、输出、状态变化和停止原因。
- 同一工具同样参数重复调用会被拦截或要求改变策略。
- 失败不计成功；未运行、运行失败、结果未知要区分。
- 复核不通过时只重排剩余问题，不覆盖已完成或锁定内容。
- 自动化测试通过不等于真人 V1→V2 闭环通过。

## 三、上下文管理：不是把所有资料塞给模型，而是只带“这一步需要的材料”

### 原理
模型每次回答都需要看一份输入材料，这就是本轮上下文。把整个项目聊天、几十份文档、所有旧计划都塞进去，关键要求可能被淹没，还可能混淆新旧版本。

像考试：不是把整个图书馆搬进考场，而是把本题要求、对应页面、评分标准和相关证据放在眼前。

### 每次按这个顺序装材料
1. 角色：当前是 A 诊断、B 规划，还是 A 复核。
2. 本轮目标和原始判据：这一步解决什么、怎样才算通过。
3. 当前作品片段：明确版本和位置，不混入其他版本。
4. 寄存器存档点：当前任务、位置、卡点和下一动作。
5. 近期失败记录：试过哪些解释/查询、哪些没用，避免重复。
6. 用户当前选择的状态：“看不懂”或“有点累”，按本轮选择处理。
7. 参考资料：优先 1–3 条最相关来源，写清出处和位置。
8. 输出要求：动作、理由、预期变化、产物、自检、失败下一步和来源定位。

### 同一段材料为何需要不同上下文？
- 用户选“看不懂”：装入原文段落、卡住的术语、之前没听懂的讲法；按一句话版、类比、图解/例子逐级讲解，再问一个小问题。
- 用户选“真的累了”：装入存档点、当前动作、休息选项和返回条件；不要再塞一大段专业解释。休息后确认，再回原位置。

### 证据规则
- 摘要必须能追溯到原记录或原文位置。
- 压缩只影响本轮输入，不得覆盖或篡改原始证据。
- 检索负责找材料，不能代替确认版本和任务状态。
- 资料不支持结论，就写“未找到/证据不足”，不靠常识编成确定答案。

### 验收标准
同一个问题分别选择“看不懂”和“有点累”，系统应分别走讲解路径和暂停/接续路径，而不是同一段长答案换个标题。

## 四、工具调用：让模型实际做事，并记录成功、失败和证据

### 原理
模型能理解和生成文字，但不天然拥有本地文件、数据库、网页或计时器的操作权限。工具调用就是把操作交给真正能执行的程序，再把结果交回模型判断。

模型说“请查官方说明”不等于查过；模型写“已保存”不等于文件真的保存成功。

### 本场景中的工具

| 工具 | 实际动作 | 成功证据 | 失败处理 |
|---|---|---|---|
| 资料检索 | 搜赛事通知、官方说明、教程 | 来源链接、原文片段和定位 | 记录查询词和失败原因，改查询或生成求助卡 |
| 文件读取 | 读取指定版本、页/段/代码行 | 文件版本、定位、读取结果 | 文件不存在或权限不足就阻塞，不假装读过 |
| 版本保存 | 保存实际修改后的 V2 | 新版本 ID/路径/时间 | 保存失败则保留 V1，报告错误 |
| 状态写入 | 保存暂停、尝试、返回条件、下一动作 | 数据库记录并读回核验 | 写入失败要提示，不能只在聊天里说“记住了” |
| 复核流程 | 按原判据检查 V2 | 每项 pass/fail/unknown 和证据 | 缺证据标 unknown，不自动通过 |
| 计时/提醒 | 记录休息时间、发送用户同意的提醒 | 事件记录/发送状态 | 计时结束不代表用户已返回 |

### 完整例子：用户问“这个竞品功能是真的吗？”
1. 把问题转换成可检索关键词。
2. 调用检索工具读取官方页面。
3. 返回原文、链接、日期和定位。
4. 核对原文是否支持这句话。
5. 支持就生成带来源的表格内容；不支持就不写成事实。
6. 记录查询和工具状态，供后续复核。

### 为什么失败不能算成功？
网页超时，但模型仍生成一段看似合理的描述，队友就可能把错误内容放进 PPT。因此每次调用都要记录输入、结果、错误、证据和状态。只有拿到符合要求的真实结果才算成功。

## 五、跨对话记忆：不是只记“你是谁”，而是确认后继续未完成的事

### 原理
用户今天在一个对话里做 PPT，明天新开对话只说“继续昨天那个”。如果系统只记得用户是大学生、喜欢哪种讲解方式，却不知道具体项目，就可能接错任务。

接续必须先匹配项目，再匹配准确存档点。不确定时先问一句，不猜。

### 具体场景
用户第二天说：“继续昨天那个。”

系统先确认：“你要继续人工智能应用创新大赛 PPT，对吗？上次停在参赛方案 V1 第 3 页竞品对比表第 2 行；已完成第 1 行，下一步是找官方功能说明并补上来源。要从这里继续吗？”

用户确认后，检查当前文件是否仍是 V1。如果已经有 V2，先询问接哪一版；原来源失效就重新检索；然后给一个 5 分钟动作。

如果用户说“不是，是蒙牛商赛”，系统切换项目，不把竞赛 PPT 的位置混过去。

### 该记什么、不该记什么
应记：未完成任务、承诺对象和截止时间、项目 ID、作品版本和定位、下一动作、曾经有效或失败的帮助方式。

不应：把一次“有点累”永久标成“这个人总是疲惫”；未经确认把一个项目的计划套给另一个项目；材料版本变了还按旧位置执行；凭模糊记忆声称保存成功。

### 验收标准
- 新对话只说“继续昨天那个”，系统先提出项目和存档点供确认。
- 确认后恢复正确版本、位置和下一动作。
- 用户否认时切换项目，不串任务。
- 证据过期时先重新核对。

## 六、五个机制如何串成一条链

以“给竞赛 PPT 第 3 页补一个有出处的竞品对照项”为例：

1. **寄存器读取**：确定项目、V1、第 3 页第 2 行、卡点和下一动作。
2. **上下文装配**：只给本轮需要的判据、当前表格、近期失败记录和来源。
3. **工具调用**：搜索官方材料并返回原文定位；无结果就报告未找到。
4. **循环判断**：结果不够就换一次查询；用户不懂就换讲法；连续两轮无效就问原因、求助或暂停。
5. **真人执行**：用户实际修改，产生 V2。
6. **外循环复核**：A 按原判据检查，给 pass/fail/unknown 和证据。
7. **寄存器更新**：保存新版本、通过项、未通过项和下一动作。
8. **跨对话接续**：第二天先确认项目，再从新存档点继续。

五个机制不是五个独立按钮：存档决定从哪开始，上下文决定看什么，工具负责实际执行，循环决定继续还是停止，跨对话记忆负责回来时接对任务。

## 七、队友分工和交付物

### A 同学：来源证据与诊断
- 提供竞品/官方材料的原文链接和精确位置。
- 每条诊断写清版本、文件位置、原始证据、问题和验收标准。
- 复核 V2 时逐条输出 pass/fail/unknown，并附证据。

### B 同学：行动卡与循环路径
- 每一步只给一个明确、可开始的微动作。
- 行动卡写清输入版本、目标位置、动作、理由、预期变化、产物、自检、失败下一步和来源。
- 设计“没做/没懂/工具失败/太累/需要求助”分流。
- 不通过时只重排剩余问题。

### 队长 C：状态集成与真人验证
- 冻结真实 V1 和原始验收标准。
- 检查寄存器是否存准确位置和下一动作。
- 组织关页重开、新对话接续、工具连续失败、V2 复核不过等测试。
- 记录真人从 V1 到 V2 的完整证据链，区分工程测试和真人效果。

## 八、交付前必须现场跑的六个测试
1. **恢复测试**：第 3 页第 2 行未完成时关页，再打开，检查是否准确恢复。
2. **版本冲突测试**：V1 存档后文件变 V2，系统必须提示确认。
3. **重复失败测试**：同一检索连续失败，系统必须换查询或停止，不能无限循环。
4. **状态分流测试**：同一任务分别选“看不懂”和“有点累”，必须走不同路径。
5. **工具失败测试**：检索或保存失败时状态必须是 failed/blocked，而不是 completed。
6. **成果复核测试**：V2 缺来源必须 fail 或 unknown；符合原判据才能 pass。

## 九、当前状态必须诚实表达

团队现有技术分析文档记录：SQLite 已有项目、版本、计划、任务和运行历史；PR #21 涉及现场恢复、尝试记录、承诺和条件返回；PR #22 涉及证据门、微动作门槛、有界循环与上下文预算，相关 70 项受控测试通过。

但受控模型回复下的工程测试通过，不等于真实模型效果稳定，更不等于真人已跑通完整 V1→V2 闭环。技术分析中记录真实诊断/复核仍有失败，真人端到端验证尚未完成。因此 PPT 要区分“已实现、工程测试通过、真人验证通过、待验证”，不能把设计方案说成已经完全落地。

## 十、队友必须能用大白话回答五个问题
1. **寄存器**：关掉网页，系统凭什么知道停在哪个文件、哪一段、下一步是什么？
2. **循环**：用户两次没做出动作，系统怎么换方法？什么时候停止？
3. **上下文**：为什么不把所有聊天和资料一次性塞给模型？本轮装了哪些必要证据？
4. **工具调用**：搜索或保存失败时，如何防止把失败说成成功？
5. **跨对话记忆**：第二天只说“继续昨天那个”，如何确认项目、版本和准确位置，避免接错？

答不出具体字段、真实操作、失败路径和验收证据，就说明还没真正理解机制。
