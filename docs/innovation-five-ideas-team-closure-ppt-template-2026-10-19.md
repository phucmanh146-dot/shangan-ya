## 一、先定创新主次：5 个方向，但 PPT 只把 2 个写成主创新

上传材料《上岸鸭避免同质化的创新点》《上岸鸭竞品拆解与过程干预方案》《溜号和疲惫识别：人脸 CV 与华为穿戴》《枯燥时的论文科普视频》共同支持以下分层。文档明确建议：主创新突出 1–2 个，其余作为支撑能力，不要把常见功能堆成五个“独立原创点”。

| 编号 | 创意方向 | 定位 | 用户可见流程 | 必须拿出的证据 | 本轮边界 |
|---|---|---|---|---|---|
| I1 | **人做、模型验：真实作品 V1→行动卡→真人 V2→按原判据逐条复核** | **主创新 1** | 上传真实作品 → A 定位差距和证据 → B 给具体微动作 → 人修改并提交 V2 → A 输出 pass/fail/unknown → B 只重排剩余差距 | V1/V2 文件、版本与定位、原始判据、逐项复核记录、人工确认、remaining issues | 不能以模型自评、打卡、按钮点击代替成果验收 |
| I2 | **停在哪、接回哪：中断现场与跨会话精确接续** | **主创新 2** | 保存项目/任务/版本/原位置/卡点/已试办法/下一动作/返回条件 → 重新打开时确认项目 → 恢复同一微动作 | 中断前后记录、重启/新会话恢复截图、恢复耗时、实际重新动手证据 | 时间到了不等于用户已返回；不确定项目时先让用户确认 |
| I3 | **论文卡点换讲法：原文可追溯的通俗讲解/类比/图解/可选短片** | 支撑 I2 的解困手段 | 用户点“听不进去” → 对当前段落换讲法 → 每条解释对应原文位置 → 用户回原段落做一个小动作 | 原文 locator、逐句对照、讲解后复述/表格一格的真实产物；如交付视频，须有可播放文件 | 首版先做图文脚本/分镜；短片可人工用剪映制作。未生成文件不得写“视频完成”；秘塔视频不假设有可调用接口 |
| I4 | **5 分钟冷启动：先做出 V0，再诊断真实能力** | 支撑 I1 | 给一个贴近真实目标的半填空样例 → 用户 3 分钟试做 → 记录做出/卡住的事实 → 第一张行动卡在 5 分钟内可启动且产出可见结果 | 试做任务、用时、V0 文件、卡点记录、微动作与 V0 的对应关系 | 不用自述“会/不会”代替试做；不能只给宏观学习路线 |
| I5 | **低打扰状态分流：先问用户，再选讲解、休息或继续** | 支撑 I2，隐私优先 | 页面行为/可选传感信号只触发一句询问 → 用户选“听不进去 / 真的累了 / 没事” → 分流并存档 → 回到同一微动作 | 状态选择、帮助方式、误提醒记录、恢复记录、用户可关闭证明 | 首版以用户主动反馈为准；摄像头/手表不是主创新，不作为 MVP 阻塞项，不自动判定情绪或学习能力；摄像头本地处理、单独同意、随时关闭才可另行试点 |

### 对外表达口径

- 主创新 1：**完成标准不是模型说“做完了”，而是真人提交的新版本按原标准逐条过审。**
- 主创新 2：**恢复的不是一段聊天，而是原项目、原材料版本、原位置和下一步动作。**
- I3–I5 是两条主创新的必要支撑，不要在 PPT 上与主创新并列争抢篇幅。
- 竞品差异必须用限定语：目前已核对的公开介绍里未看到同样的端到端闭环，不宣称“全行业绝无”。结论最终由同任务对照试用验证。

## 二、三人分工：按交接物分，不按“大家一起做”分

> 角色按仓库已有约定：A = 诊断与资料研究（资料抓取已按队长确认完成）；B = 行动卡与排程；C = 队长本人，负责执行总控与集成。真实 GitHub 账号/协作者身份以仓库成员列表为准，不在文档中猜测账号。

### A｜诊断、真实材料、换讲法内容

**不再重复做全网爬取。** 使用已经抓取的来源，补齐来源目录、原文正文、版本、locator 和读取状态。

交付：
1. 选定一份团队正在做的真实科研/竞赛材料 V1（建议选一段读不懂的论文，或真实竞赛 PPT 中一页）；记录文件名、版本、页/段/代码位置和目标判据。
2. 输出至少 3 条可追溯 gap：当前证据、目标判据、准确 locator、参考来源与参考 locator、可复用的方法、适用边界；资料不足标 `unknown/blocked`。
3. 负责 I3 的解释素材：一句话版、类比版、图解/分镜版；每个关键结论能回指原文。视频由剪映人工制作时，逐镜头核对，不得编造论文图表或数据。
4. A 复核 V2 时必须使用原判据，并输出 `pass / fail / unknown` 与证据，不因计划变更而复用旧版本结论。

验收：
- B 不问 A 口头补充，也能从 gap 找回材料位置与原文。
- 每个 gap 都能解释“差在哪里、为什么要改、用什么标准判断”。
- 无证据的内容不进入 B 的可执行任务。

### B｜具体微动作、估时与剩余任务重排

交付：
1. 只接收 A 已校验的 gap；为每个 gap 写出可执行 `micro_steps`，至少包含：`input_version / target_locator / action / reason / expected_change / output / self_check / failure_next / capability_basis / source_refs`。
2. 第一步控制在 5 分钟左右且必须产出一个看得见的小结果；估时标注依据/假设，另记实际用时，不预填节省比例。
3. 列清依赖、负责人、验收条件、失败下一步；没有 grounded steps 时保持 `blocked/unscheduled`，不得退回“打开材料→完成成果→检查”的通用三步。
4. V2 复核后只为未通过或未知的差距生成新行动卡；保留已完成、进行中、待复核和锁定任务。
5. 为 PPT 准备对照实验数据表模板，不得替团队虚构结果。

验收：
- 另一成员只看行动卡即可开始操作，不需要作者现场讲解。
- 5 分钟内能开始；操作对象、位置、产物和自检方式都明确。
- 卡住时有替代路径或求助卡；无法排程时明确显示原因。

### C｜队长：集成、版本保护、真实闭环、试用与 PPT 总控

交付：
1. 以 PR #25 `feat/captain-runtime-20261018` 为当前工程核对基准；新任务先做独立分支和 PR，不直接改 `main`。
2. 先检查 PR #21/#22 的集成状态、冲突与共同启动路径；不因测试通过就宣称真人闭环完成。
3. 提供统一真实任务、版本号和原判据；把 A gap → B micro_steps → 执行记录 → V2 → A 复核 → 人工确认 → B remaining plan 串起来。
4. 组织“另一位成员仅看行动卡”的盲交接；记录实际用时、卡点、提交 V2、复核记录与返工情况。
5. 组织 5–8 人小样本同任务对照（只报告该样本，不外推）：通用聊天、单个智能体、上岸鸭三种方式；统一任务、时间窗与判据。
6. 汇总真实截图/日志/数据并完成 PPT；所有页面区分“已实现 / 工程测试通过 / 真人验证通过 / 待验证”。

验收：
- 无 A 复核不得正式通过；旧版本结果不能放行新版本；项目不明确时必须让用户确认。
- 完整链条可回查：目标 → 判据 → V1/locator → gap → action card → 执行人 → V2 → A review → 人工确认 → remaining issues。
- 对照数据来自实际记录，零结果也如实报告。

## 三、闭环依赖与执行顺序

```text
C 选真实任务、冻结 V1 与原判据
        ↓
A 整理真实来源与材料 → 诊断 gap（带 locator / evidence / unknown）
        ↓ A 交接包通过 C 检查
B 生成 grounded micro_steps（5 分钟第一步、产物、自检、失败路径）
        ↓ B 行动卡通过 C 检查
另一位成员只看行动卡，实际修改并提交 V2
        ↓
A 按原判据复核 V2：pass / fail / unknown
        ↓
C 人工确认正确的 review_id、项目与版本
        ↓
B 只重排 remaining issues，保护已完成/进行中/锁定任务
        ↓
C 记录结果、恢复时间、返工和用户负担 → 更新 PPT 数据页
        ↺ 若未过：回到 B，只处理剩余 gap；若版本变化：重新核对，不复用旧复核
```

### 三个硬门槛

1. **证据门：** A 无真实证据/原文位置 → `unknown/blocked`，B 不可执行。
2. **行动门：** B 无绑定版本的具体微动作 → `blocked/unscheduled`，不得生成假计划。
3. **成果门：** 无真实 V2 + A 按原判据复核 + 人工确认 → 不得标记成果闭环完成。

## 五、答辩 PPT 模板（建议 16 页，数据必须等实测）

> 按已有材料中的提交结构安排：数据来源与处理、分析过程、1–2 个主创新、结果解释与风险、应用结果展示。最终页数、匿名评审、测试账号等以本届正式提交要求为准。

| 页码 | 标题 | 页面只回答一个问题 | 必放证据 / 视觉模板 | 负责人 |
|---|---|---|---|---|
| 1 | 上岸鸭：让科研任务从卡住到交付 | 我们做什么？ | 产品名 + 一句话定位；避免“全能学习助手” | C |

| 4 | 获奖作品技术拆解 | 为什么不把 RAG/多 Agent 当创新？ | 公开案例 → 常见技术积木 → 常见输出终点；区分报道原文与推断 | A |
| 5 | 上岸鸭的目标与验收 | 什么才算真的完成？ | V1、原判据、V2、逐条复核、人工确认五格图 | C |
| 6 | 创新一：人做、模型验 | 与普通生成有什么不同？ | V1 → 证据 gap → 行动卡 → 真人 V2 → 原标准复核 → remaining issues | C |
| 7 | 创新二：停在哪、接回哪 | 中断后如何恢复？ | 中断前存档字段与新会话恢复对照；展示同一个 micro_step_id/locator | C |

| 9 | 数据与材料来源 | 证据从哪来？ | 真实材料清单、官方要求、参考案例、来源定位/读取状态流程 | A |
| 10 | Agent 工作流与五个运行机制 | 如何实现？ | A/B/C 交接图 + 寄存器/循环/上下文/工具调用/跨对话记忆；机制是实现手段，不当创新点 | C |
| 11 | 真实任务演示：诊断与行动卡 | 建议是否可照做？ | 实际 V1 截图、可点击原文位置、行动卡与 5 分钟第一步 | A + B |
| 12 | 真实 V1→V2 前后对照 | 作品具体变好了哪里？ | 同一文件前后截图，标出修改处与版本号；没有真实 V2 时此页标“待验证” | 执行人 + C |
| 13 | 复核与错误控制 | 系统会不会误放行？ | 每条原判据的 pass/fail/unknown、误放行数、返工数；没有数据则列测试方案 | A + C |
| 14 | 中断接续实测 | 能否真的把人接回来？ | 触发原因、保存位置、恢复位置、重新动手时间、是否完成原微动作 | C |
| 15 | 试用对照与结果解释 | 相比基线多了什么？ | 5–8 人小样本的实际记录：V1→V2 通过条数、误放行、返回率、恢复耗时、用户负担；标明样本限制 | C（B 提供数据模板） |
| 16 | 风险、限制与下一步 | 哪些已验证，哪些没验证？ | 隐私/学术诚信/模型幻觉/错误复核/传感器误报；已实现、工程验证、真人验证分列 | C |

### PPT 统一版式规则

- 每页一个结论型标题；正文最多 3–5 个短点，优先流程图、前后对照和证据截图。
- 截图必须来自实际运行；所有示例/受控夹具标注“工程测试样例”，不能冒充真人使用。
- 统一颜色语义：绿色 = 有证据通过；红色 = 未通过/阻塞；灰色 = 未知/待验证。颜色不能代替文字说明。
- 任何数字必须附计算口径、样本数、时间范围与来源；无数据就写“尚未测量”，不画虚构趋势图。
- 竞品页面使用“公开资料中未见”而不是“竞品绝对没有”；对获奖作品的技术描述区分“报道原文”和“功能推断”。
- 演示顺序固定：真实 V1 → 点开原文定位 → 看行动卡 → 真人修改 V2 → A 复核 → 人工确认 → 剩余问题 → 中断后回到原步骤。
