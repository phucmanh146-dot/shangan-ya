### 2. A/B 阶段分

- **A：83/100（阶段性）**。优势：原件版本、locator、quote、Gap/UNKNOWN、来源追溯和复核接口；短板：语义 Gap 准确性、真实 V2、非执行者盲审。

6. ChatGPT Action、浏览器扩展真实配对及证据事件回传。
7. 用户能力与 AI 能力分开认证的真实样本验证。

所有上述事项未实测前标为 `NOT_RUN`、`BLOCKED` 或 `IN_PROGRESS`，不得用模拟案例、规则规划输出或单元测试代替。

## 二、项目应该怎样讲：一句话定位

**上岸鸭不是“帮人生成计划的聊天机器人”，而是把真实材料中的差距变成真人能执行、成果能复核、失败能恢复的多项目 Agent 闭环。**

核心链路：

```text
真实目标 + 当前材料 V1
        ↓
A：读取原件、定位证据、诊断 Gap / UNKNOWN
        ↓
C：校验来源、版本、标准与权限
        ↓
B：结合个人能力、依赖、容量生成微动作和排程
        ↓
真人执行：记录尝试、求助、实际耗时和中断
        ↓
真实成果 V2：文件版本、差异、证据
        ↓
A / 非执行者独立复核
        ↓
PASS：锁定成果；FAIL / UNKNOWN：只重排剩余项
        ↓
C：保存版本、事件、审计轨迹和恢复点
```

演讲时必须突出三个差异：
- **不是只会分析**：A 的每个 Gap 必须定位到当前材料与目标标准的具体位置。
- **不是只会排计划**：B 的每一步必须有输入版本、动作、理由、预期变化、产物、自检和失败下一步。
- **不是点完成就算完成**：真实 V2 必须由非执行者按原标准独立复核。

## 三、PPT 优化总原则

1. **先证据，后架构**：开场先展示一个真实问题、真实材料和真实差距，不要连续数页讲概念。
2. **一页只回答一个评委问题**：问题是什么、现有方案为什么不够、我们怎么做、证据是什么、效果如何。
3. **每个技术点必须对应一个可点击/可定位的工程证据**：代码文件、接口、日志、测试报告、真实产物或部署页面。
4. **把“已实现、工程 Demo、真实业务验证、规划中”四种状态分开**，用统一标签，不混写。
5. **用一条真实案例贯穿**：从 V1 输入到 Gap、行动卡、真人执行、V2 和盲审，避免 A/B/C 各讲各的。
6. **不堆技术名词**：LangGraph、BM25、向量检索、RRF、Reranker、OCR、checkpoint、幂等都要解释解决哪个具体失败。
7. **不编数据、不夸 ROI**：没有真实用户对照、独立盲审和账单，不写“效率提升 X%”“准确率 98%”“成本降低 X%”。

## 四、建议的 20 页主 PPT 结构

> 这是推荐内容结构。由于本次未取得原始主 PPT 的逐页文件内容，下面是重排方案，不声称已逐页修改原 PPT。拿到原文件后应按本结构做逐页映射与批注。

| 页码 | 页面标题 | 核心内容 | 必须放入的证据/视觉 |
|---:|---|---|---|
| 1 | 上岸鸭：让任务真正走到成果 | 项目名 + 一句话定位 + 真实项目截图 | 简洁主视觉；不要堆口号 |
| 2 | 有目标，却卡在“下一步怎么做” | 材料多、标准复杂、任务变化、执行中断、成果难验收 | 真实用户任务链或脱敏案例 |
| 3 | 现有 AI 为什么没有解决最后一公里 | 只给建议、计划静态、口头汇报、无法复核、失败后重来 | 传统聊天流程 vs 上岸鸭闭环对照 |
| 4 | 我们解决的不是计划，而是可验证执行 | V1→Gap→行动→真人→V2→独立复核→重排 | 一张完整闭环总图 |
| 5 | 一个真实项目：从原始材料开始 | 展示材料类型、版本、目标标准、输入状态 | 脱敏 V1 文件、版本号、来源清单 |
| 6 | A：把模糊问题变成有出处的 Gap | 原文定位、当前证据、目标标准、差距原因、UNKNOWN | Gap 诊断卡放大图，显示 locator/quote |
| 7 | 证据门：没有来源，不让计划进入执行 | 来源校验、版本一致、引用定位、unknown/blocked | 通过/拒绝的真实样例各一条 |
| 8 | B：把 Gap 变成真人能照做的行动卡 | 输入版本、动作、理由、预期变化、产物、自检、失败下一步 | 九字段行动卡交互截图 |
| 9 | 不是普通待办：按能力、依赖和容量排程 | 能力画像、任务依赖、估时范围、可用时间、缓冲 | 排程前后对照与 unscheduled 原因 |
| 10 | 临时中断后，系统从断点恢复 | 暂停、临时任务、恢复检查、剩余时间重排 | 中断事件时间线与 checkpoint |
| 11 | 真人执行与求助：记录真实过程 | 开始、尝试、求助、实际耗时、产物上传 | 执行日志与真实操作记录 |
| 12 | V2：成果版本，而不是“已完成”按钮 | 新文件版本、SHA256、差异、证据 | V1/V2 对比截图与版本信息 |
| 13 | 独立复核：通过、失败、未知分开判定 | 非执行者复核、逐条标准、证据引用 | 复核表与 reviewer 身份隔离说明 |
| 14 | 失败后只重排未通过项 | 保留已通过/锁定/进行中；只处理 FAIL/UNKNOWN | remaining-only 重排前后对照 |
| 15 | 技术架构：多 Agent + RAG + Runtime | A/B/C、LangGraph、混合检索、事件队列、持久化 | 简化架构图，标明数据流与接口 |
| 16 | 技术难点与工程处理 | 幂等、版本冲突、checkpoint、等待审批、故障恢复 | 对应代码路径/测试用例，不只写术语 |
| 17 | AI 能力不等于个人能力 | 每个 skill 分开认证模型与成员；AI 强不代表人会 | 双量尺矩阵与等级规则 |
| 18 | 工程验证：哪些已通过，哪些还没通过 | 测试数、E2E、模型实测、真人 V2、生产部署分层展示 | 测试报告 + NOT_RUN 清单 |
| 19 | 应用场景与推广路径 | 竞赛项目、科研论文、复杂交付等多任务场景 | 每种场景一条真实输入→输出示例 |
| 20 | 下一阶段：从工程闭环走向真实效果 | 两个真实项目、盲审、对照组、部署、指标 | 里程碑、负责人、验收门与风险 |

### 20 页中最值得做强的 5 页

- **第 4 页闭环总图**：评委必须在 10 秒内看懂产品不是普通问答。
- **第 6 页 A 诊断卡**：必须能看见原文定位、引用和目标差距，不是 AI 自己总结。
- **第 8 页 B 行动卡**：必须能看见具体动作和失败下一步，不是“提升能力、完善材料”。
- **第 12–14 页 V2 与独立复核**：这是产品可信度核心，应该成为整份 PPT 的高潮。
- **第 18 页验证边界**：主动展示已验证与未验证，反而更可信。

## 五、交互页面与 PPT 的对应关系

建议至少展示 4 个可交互页面，不要把所有页面缩成小截图。

### 页面 A：真实材料与证据诊断工作台
- 左侧：项目、V1 文件、目标标准、材料版本。
- 中间：原文/页码/段落定位。
- 右侧：Gap、证据引用、目标判据、UNKNOWN 原因。
- 交互：点击 Gap，原文定位同步跳转；来源缺失时显示 BLOCKED，不生成伪引用。

### 页面 B：行动卡与动态排程工作台
- 左侧：Gap 与负责人。
- 中间：九字段行动卡、依赖、估时、能力依据。
- 右侧：可用时间、缓冲、排程和未安排原因。
- 交互：调整成员能力或可用时间，重新预览；采用前必须显示前后差异。

### 页面 C：真人执行与成果版本工作台
- 当前任务、开始/暂停/求助/恢复。
- 真实操作步骤、实际耗时、上传产物。
- 自动生成 artifact version、文件 hash 和证据清单。
- 交互：提交成果只能进入 `pending_review`，不能直接显示“已完成”。

### 页面 D：独立复核与剩余项重排工作台
- 原判据、V1、V2、差异、证据引用。
- reviewer 与执行者身份分离。
- 逐条 PASS / FAIL / UNKNOWN。
- 交互：只有版本一致、证据充分且复核者独立才可放行；失败后只生成 remaining plan。

## 六、技术展示怎样避免“堆栈式 PPT”

| 技术 | 不要只写 | 应展示的具体问题与证据 |
|---|---|---|
| OCR / 文档解析 | 支持 PDF、Word、图片 | 页码/段落定位是否保留，解析失败如何标 UNKNOWN |
| BM25 + 向量检索 | 混合检索更准确 | 同一评测集上的 Recall@K、引用命中率 |
| RRF | 多路召回融合 | BM25、向量、融合前后对照 |
| Reranker | 重排提高质量 | 重排前后 top-k 相关性与人工盲评 |
| LangGraph / Runtime | 多 Agent 协作 | 状态节点、等待、恢复、失败路径 |
| 幂等 / 事件队列 | 高可靠 | 重复 message_id 不重复执行的测试与日志 |
| checkpoint | 可恢复 | 同一 run 的中断点、恢复点和 action ID |
| Cloud Hub / Browser Bridge | 云端自动化 | 审批前后、证据回传、失败日志 |
| AI/个人双量尺 | 个性化 | 同一任务不同能力成员的行动卡差异与最终成果 |

没有真实评测数字时，展示评测方法、样本定义和当前状态，不要自行填充指标。

## 七、80+ 冲刺路线：按验收门推进

| 优先级 | 工作项 | 负责人建议 | 交付物 | 通过标准 |
|---|---|---|---|---|
| P0 | 真实 RAG 检索与重排对照 | A + C | 固定评测集、召回结果、Reranker 对照报告 | 可复现、原文引用正确，失败样本可追踪 |
| P0 | 两个真实项目 V1→V2 | A + B | 原件、Gap、行动卡、真实 V2、版本差异 | 至少两个项目完整走完，不使用 Demo fixture |
| P0 | 非执行者独立盲审 | A（非执行者）+ C | 盲审记录、PASS/FAIL/UNKNOWN | 复核者未参与执行，逐条有证据 |
| P0 | FAIL/UNKNOWN 局部重排 | B + C | 重排前后计划与状态历史 | 已通过、锁定、执行中任务不被覆盖 |
| P1 | Railway API/Worker 生产验收 | C | 健康检查、共享数据库、重启恢复记录 | API/Worker 读写同一持久化状态 |
| P1 | ChatGPT Action / 浏览器扩展配对 | C | 配对记录、事件 ID、证据回传日志 | 真实消息能进入项目并可追踪 |
| P1 | AI/个人能力双量尺对照 | A + B | 同题不同能力成员对照报告 | AI 等级和个人等级不混淆 |
| P2 | PPT 与交互演示彩排 | 全员 | 20 页主 PPT、4 个页面、演示脚本 | 现场 5 分钟内完成一条可复现演示 |

### 真实闭环验收包必须包含

```text
case_id
V1 原件 + SHA256 + 来源
目标标准 + locator
A diagnosis + gap_id + quote
B action_plan + micro_steps
真人执行记录 + 实际耗时
V2 原件 + SHA256 + diff
独立 reviewer + 逐条 PASS/FAIL/UNKNOWN
remaining-only replan

```

## 八、答辩中最容易被问到的 8 个问题

1. **你们和普通大模型有什么区别？**  
   回答重点：不是回答更长，而是保存原件版本、证据定位、执行状态、真实 V2 和独立复核。

2. **A 和 B 为什么不能合成一个 Agent？**  
   A 对证据负责，B 对动作可执行性负责；诊断不过证据门，B 不得补造行动。

3. **怎么证明不是 AI 自己说完成了？**  
   任务提交后进入待复核，真实 V2 与证据由非执行者按原判据检查。

4. **AI 很强，是否代表用户也具备能力？**  
   不代表。模型 skill 和个人 skill 分开评级，个人等级必须来自本人真实产物。

5. **检索真的有效吗？**  
   展示固定评测集、BM25/向量/RRF/Reranker 对照、原文引用准确性；没有数据就明确说尚未完成实测。

6. **遇到临时任务、失败或断网怎么办？**  
   通过事件记录、checkpoint、幂等和 remaining-only 重排恢复；展示实际恢复日志，不只展示架构图。

7. **你们做过真实用户测试吗？**  
   只陈述已完成且有证据的案例；Demo 测试明确标注为工程验证，不能冒充真人测试。

8. **效率提升多少、商业价值是什么？**  
   先定义基线与指标：首步启动时间、完成率、V2 通过率、返工、人工耗时、模型成本。没有对照数据前不报 ROI。

## 九、提交前的 PPT 逐页自检表

- [ ] 每页只有一个中心结论。
- [ ] 每个数字有来源、口径、时间和原始证据。
- [ ] 每个“已实现”都有代码/页面/API/日志证据。
- [ ] Demo、LIVE 模型、真人成果、生产部署四种状态分开。
- [ ] A/B/C 交接边界清楚，责任不重叠。
- [ ] 至少一条真实 V1→V2→独立复核链路贯穿全篇。
- [ ] 交互页面可现场点击，不使用静态图冒充真实运行。
- [ ] 未完成项有负责人、下一动作、恢复条件和验收标准。
- [ ] 不出现未验证的准确率、效率提升、用户规模、营收或 ROI。
- [ ] 演示失败时有真实截图/日志和可复现的备用路径。

## 十、下一轮实际执行顺序

1. 先取得当前正式参赛 PPT 原文件和赛事官方评分标准，建立逐页映射表；不凭空改写原页内容。
2. 按第 4 节结构对现有页面逐页标注：保留、合并、重写、补证据、删除。
3. 优先补齐两个真实项目 V1→V2 与非执行者盲审证据，再决定第 18 页可以展示的数字。
4. 用第 5 节四个交互页面做一条真实演示，录屏并保留 run_id、artifact hash 与复核结果。
5. 最后压缩成 20 页答辩版，并另备技术附录/现场追问证据，不把所有代码截图塞进主 PPT。

**结论：** 当前仓库的工程基础已经足以支撑一份有技术深度的答辩，但冲击 80+ 的关键不是再堆新技术名词，而是把真实检索质量、真人 V1→V2、独立盲审、失败恢复和生产部署做成评委可以复核的证据。
