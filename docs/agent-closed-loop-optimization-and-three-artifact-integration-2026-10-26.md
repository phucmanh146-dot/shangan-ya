## 1. 目标：从“生成计划”变成“有证据、可执行、能复核的闭环”

产品的核心差异不应是多加一个 Agent 或多生成一份待办清单，而是：**每条改进都能从真实作品定位到证据，从证据落到具体动作，再由真人产出新版并由独立人员复核。**

```text
冻结目标标准 + V1材料版本
          ↓
A 证据诊断：gap + 原文定位 + 来源 + 事实/推断/未知
          ↓ 证据门（缺定位/来源/标准即阻断）
B 行动规划：绑定 gap_id 的 micro-step + 依赖 + 产物 + 自检
          ↓ 计划门（版本不匹配/无可执行步骤即阻断）
真人执行：记录开始/结束、实际产物、耗时、卡点
          ↓
保存 V2 + diff + 文件哈希
          ↓
A 独立复核：按冻结标准逐条 PASS / FAIL / UNKNOWN
          ↓
B 只重排 FAIL / UNKNOWN / BLOCKED 项
          ↓
C 检查状态、证据、版本与回归结果；记录下一轮基线
```

### 不允许跳过的规则

1. **来源不等于证据。** 仅有 URL 或模型摘要不能把 gap 标为 verified；必须有可回查的材料定位和支持该判断的内容。
2. **计划不等于执行。** 生成了行动卡不表示任务完成；必须有真人实际产物。
3. **V2 不等于通过。** 新版提交后先进入 `pending_review`，只有独立复核才可判定。
4. **模型调用不等于质量通过。** LIVE_MODEL、REAL_ARTIFACT、HUMAN_LOOP 分开记账。
5. **失败不能静默成功。** 缺资料、版本冲突、无效模型、执行中断都要保留明确状态和错误原因。
6. **重排不等于重置。** 不覆盖 `completed`、`in_progress`、`pending_review` 或已锁定证据；只调整允许重排的未解决项。
7. **没有证据就写 UNKNOWN/BLOCKED。** 不得用推测填补作品事实、数据或获奖结论。

## 2. 现有工程的优化落点

以下是基于当前读取到的代码和已有测试方案提出的改进点；是否需要改代码，须先用测试确认，不能仅凭文档推断实现缺陷。

| 位置 | 现有可见能力/边界 | 本轮建议 | 验收证据 |
|---|---|---|---|
| `team_orchestrator.py::validate_diagnosis` | 检查诊断结构、来源 ID、gap ID、成员关联和部分证据字段 | 为每条 gap 明确验证状态、locator、目标判据；只有真实材料定位充分时才放行 | 缺 locator、来源不支持结论、unknown 被误标 verified 的负例测试 |
| `team_orchestrator.py::validate_micro_steps` | 若提交 micro_steps，会检查输入材料版本与执行字段；字段缺失时当前函数允许未提供 micro_steps | 生产执行入口必须额外检查“行动卡是否可执行”；兼容旧计划可以保留，但旧计划应显示为不可执行/待补齐 | 无 micro_steps 的旧计划可读取，但不能进入真人执行状态 |
| `team_orchestrator.py::commit/current` | 通过 expected version 与事务阻止旧版本覆盖新状态 | 增加并发更新、重复提交、幂等性和历史记录完整性测试 | 两个相同 expected_version 的更新只有一个成功；旧结果不覆盖新结果 |
| `action_planner.py::generate` | 对缺来源、负责人、目标产物和验收标准的 gap 置 pending；缺 micro_steps 时标为待补充 | 明确分开 `candidate`、`blocked`、`ready`；阻断任务不得出现在“可执行”列表或被误计为已排程 | dashboard 与 API 返回的状态一致；blocked 原因可读 |
| 任务状态流转 | 文档要求诊断→行动→执行→复核→剩余项重排 | 先绘制代码实际状态枚举与转换表；再用表驱动测试覆盖合法/非法迁移 | 每个状态转换有调用入口、前置条件、事件记录和测试用例 |
| 证据与审计 | 当前总调度要求保存 commit、输入版本、命令、产物、复核人 | 为每轮运行生成稳定的 run_id/trace_id；日志只保存脱敏信息，不写密钥 | 同一 run 的诊断、行动卡、V2、复核可用 ID 串联 |
| 模型配置 | 已有记录显示模型尚未验证；规则规划器明确说明不伪造模型调用 | 将 demo、simulated、live 的来源标签贯穿到响应、日志与 UI | 无效配置不得返回 LIVE 成功；mock 结果有显著标签 |

### 推荐的最小数据契约

每条 gap 最少需要：

```json
{
  "gap_id": "GAP-001",
  "artifact_id": "artifact-project-a",
  "artifact_version": 1,
  "current_locator": "PPT第12页/第3段/表格第2行",
  "current_evidence": "从原件摘录或准确描述，可回查",
  "target_criterion": "冻结的目标标准或官方要求",
  "source_refs": ["SRC-001"],
  "verification_status": "verified",
  "unknowns": [],
  "acceptance_criteria": ["产物中包含可追溯的原始数据与口径说明"]
}
```

每个 micro-step 最少需要：`step_id`、`gap_id`、`input_version`、`target_locator`、`action`、`reason`、`expected_change`、`output`、`self_check`、`failure_next`、`source_refs`、负责人、依赖、预计耗时。若不需要外部来源，必须写清 `reference_not_required_reason`，不得留空假装有引用。

> 以上是推荐契约示例，不是对当前所有字段已实现的声明。合入代码前要先与实际 schema 对齐，保持向后兼容或明确迁移方式。

## 3. 三类真实作品的差异化验证

不要把三个作品都跑成“补材料—改方案—再检查”的同一套通用话术。每个作品必须由原件中的真实 gap 驱动。以下是测试方向，不是对作品现状的最终事实判定。

| 作品样本 | 重点检验的业务链 | 第一张行动卡应指向什么 | 不通过信号 |
|---|---|---|---|
| 湘匠织秀/湘秀未来 | 真实需求→访谈证据→纹样授权→报价/样品→质检→交付/结算 | 从原件中选一条可回查的需求或访谈，建立需求与产品、授权及履约证据的对应关系；若材料不支持，先列补证任务 | 输出泛化的“优化PPT/加强调研”，无法指向具体原件或真实交易环节 |
| 无界智泊 | 预约→冲突处理→入场→提前离场→结算/退款 | 选一个有版本号的状态转换，写出前置状态、操作、预期状态、异常分支和可复现日志 | 只描述功能，不提供可复现用例、状态变化或失败记录 |
| 数智助老 | 服务发起→授权→转派→响应→办结→评价/异常 | 建立 claim-evidence 表，把“响应时间/效率提升”等主张绑定到真实基线、样本和履约记录；缺数据就标 UNKNOWN | 直接复用宣传数字、把规划当已上线、把无基线的数字当效果 |

### 三个样本的执行顺序

1. **第一轮：湘匠织秀 + 无界智泊。** 两者业务链差异较大，适合验证 Agent 是否真的依据材料改变 gap、首步、产物和验收标准。
2. **第二轮：数智助老。** 作为独立复现样本，检查前两类之外的流程与效果证据能否复用同一闭环，而不是硬套模板。
3. 如果原始文件、授权或可读定位尚未拿到，对应样本先标 `blocked`；不能用文档中的示例代替真实输入。

### 差异化判定

固定同一代码 commit、相同模型/提示词配置与同一类输出要求，分别输入三个真实材料包。逐项比较：
- gap 是否绑定各自材料的 locator；
- 第一张行动卡是否对应不同业务环节；
- 产物类型是否适合该作品；
- 验收标准是否能客观判断；
- unknown 是否如实保留；
- 真人执行后是否形成不同且可检查的 V2 diff。

若只替换项目名称，其他 gap、动作、交付物与验收标准几乎相同，则 `PERSONALIZATION_FAIL`。

## 4. 工程总调度测试矩阵（可直接填结果）

| Case ID | 场景 | 输入/操作 | 预期 | 结果字段 |
|---|---|---|---|---|
| FLOW-01 | 缺来源定位 | gap 没有 current_locator | 不得标 verified；阻断或转 UNKNOWN | pass/fail/unknown/blocked |
| FLOW-02 | 来源不支持结论 | source 存在但原文不支持 gap | 不放行；记录证据不足 | 同上 |
| FLOW-03 | 缺微动作 | 只有诊断摘要，没有可执行 micro_steps | 可保存为待补充，但不能进入执行 | 同上 |
| FLOW-04 | 材料版本更新 | V1 变 V2 后继续提交旧版本行动卡 | 拒绝或要求重新诊断 | 同上 |
| FLOW-05 | 并发写入 | 两个请求使用相同 expected_version | 一个成功，另一个 Conflict；历史可追溯 | 同上 |
| FLOW-06 | 重复提交 | 同一 V2 重复提交 | 幂等或显式冲突，不生成双份完成记录 | 同上 |
| FLOW-07 | 复核待处理 | B 提交 V2，A 未复核 | 保持 pending_review | 同上 |
| FLOW-08 | 局部失败重排 | 多项中一项 fail、一项 pass | 仅重排失败/未解决项 | 同上 |
| FLOW-09 | 已完成保护 | 加入紧急任务或减少可用时间 | 已完成/待复核证据不变 | 同上 |
| FLOW-10 | 模型服务失败 | 无效模型 ID、超时或错误凭据 | 标明失败和脱敏原因，不假成功、不静默 mock | 同上 |
| FLOW-11 | 中断恢复 | 保存后重启，再读取同一 project_id | 恢复版本、状态、历史与下一步 | 同上 |
| FLOW-12 | 三样本差异 | 依次输入三个作品材料 | gap、首步、产物和标准由材料决定 | 同上 |
| FLOW-13 | 第三人执行 | 不参与编卡的人只看材料和行动卡 | 可执行；记录求助、耗时与卡点 | 同上 |
| FLOW-14 | 证据链完整 | 从最终 V2 反查 V1、gap、行动卡、复核记录 | 版本、来源、执行者、复核人均可追溯 | 同上 |

每个 case 的记录必须包括：当前 commit、输入材料版本/哈希、命令或请求、预期、实际、退出码/HTTP 状态、日志/产物路径、复核人。未实际执行的一律填 `not_run`，不得先填 pass。

| P2 | 输出逐 gap 的 micro-step，不可执行项明确 blocked | B | 行动卡、依赖图、估时依据 | ACTION_READY |
| P2 | 跑湘匠织秀、无界智泊差异化测试 | A/B/C | 输出对比表与原件定位 | PERSONALIZATION_PASS |

## 6. 三人分工和交接标准

- **A（证据诊断与独立复核）：** 冻结目标标准；定位 V1 原文；区分事实、推断、未知；提交 gap；V2 后按原标准复核。不得用模型总结替代原件。
- **B（行动规划与执行记录）：** 只消费通过证据门的 gap；每步绑定材料版本、目标位置、具体操作、产物、自检和失败下一步；记录真实耗时与卡点。不得将行动卡生成等同完成。
- **C/队长（工程与集成）：** 维护 commit/provenance、状态机、版本保护、日志脱敏、模型连通和总调度测试；抽查证据链。不得以单元测试通过推导真实作品或奖项准备度。
- **交接协议：** A 提交 gap → C 抽查证据 → B 生成行动卡 → 非编卡者执行 → A 独立复核 → B 仅重排剩余项 → C 复验并归档。
- 任一环节缺少产物、版本、定位或复核人，状态保持 `blocked`/`pending_review`，不能越级。
