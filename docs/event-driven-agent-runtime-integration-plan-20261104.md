# 上岸鸭事件驱动自主执行 Agent 集成方案

> 目标仓库：`phucmanh146-dot/shangan-ya`  
> 目标基线：`feature/agent-rag-rerank-20261102`  
> 参考工程：`KKKKhazix/agent-autoloop`（仅借鉴架构与机制，不复制其内核代码）  
> 方案版本：2026-11-04

## 1. 结论

上岸鸭不应再增加一个“每轮对话都要用户确认”的聊天入口，也不应把 Autoloop 原样作为第二套任务系统。建议在现有 Python/SQLite 项目状态、任务计划、材料版本、证据和复核流程上，增加一个**事件驱动的 Agent Runtime（自动执行运行时）**：

- 外部变化先写入事件账本，再由规则决定是否派发 Agent。
- Agent 从持久化项目状态自动构造上下文，不要求用户重新上传已登记材料或重复解释计划。
- 可安全完成的动作自动执行；只有权限不足、关键歧义、对外发布、删除/覆盖、付费或其他不可逆动作才进入人工等待。
- 一轮执行结束后释放进程；没有待处理事件时不空转、不持续调用模型。新信号到达、定时复查到期或用户回复时，再恢复原任务。
- 自动保存检查点、工具调用、产物版本、失败原因和下一步；中断后恢复原会话/任务，不创建重复任务、不重复做已完成工作。

**“不检测每一轮结果”应理解为“不让用户逐轮验收或点确认”，不是不检查工具是否成功。** Runtime 仍须验证工具调用返回、文件是否写入、版本是否变化、任务状态是否提交；用户只在真正需要决策或最终成果验收时介入。

## 2. 参考工程中值得借鉴的机制

Agent-Autoloop README/INSTALL 明确展示了以下可迁移设计：

1. **事件统一入口**：定时任务、GitHub Issue、业务报错等统一转成标准事件。
2. **规则派发**：事件类型匹配规则，路由到 Agent、工作目录和 Skill；同一对象短时间内的重复消息合并。
3. **执行后退出**：Agent 完成本轮后释放进程，不常驻消耗模型额度。
4. **等待零消耗**：需要用户拍板时保存等待状态并退出；用户回复后续接原会话。
5. **事件溯源**：只追加事件事实，状态由事件投影；记录落盘后才确认接收。
6. **指令与数据分离**：外部消息只作为数据，不得覆盖系统指令、工作目录、Agent 选择或权限。
7. **幂等与恢复**：重复事件不重复执行；续接失败时重试原任务，不新建任务重做。
8. **跳数熔断**：Agent 产生的新事件带递增深度，超过上限停止自动派发，防止自触发死循环。
9. **插件化**：事件源、Agent 适配器、通知通道、交付工具可独立替换。

参考项目的 INSTALL 明确写明目前支持 macOS/Linux、暂不支持 Windows。因此不建议在 Windows 主机上直接照搬其安装脚本；上岸鸭应在现有 Railway/Linux 服务或经验证的 Linux 运行环境中实现这些机制。不要把“参考了 Autoloop”写成“已安装并跑通 Autoloop”。

## 3. 上岸鸭现有基础与需要补齐的断点

### 已有基础（以目标分支当前可读取代码为准）

- `learning-agent/` 已有 Python 后端与 SQLite 项目状态。
- `team_dispatch.py` 已有 A→B 顺序派发、阶段状态保存和失败记录。
- `team_recovery.py` / recovery 相关模块已有任务现场、恢复摘要等能力；README 描述了 `POST /api/agent/team/recover` 的跨会话意图恢复入口。
- 计划、任务动作、材料来源、版本、证据与成果复核已有数据结构和保护规则。
- `action_planner.py` 已要求生产任务绑定真实来源、交付物、验收标准；缺少 grounded `micro_steps` 时将生产任务置为 blocked，而不是伪造可执行计划。
- 已有卡点求助、临时任务/容量变化预览和执行事件记录等功能基础。

### 当前不能据此宣称已完成的能力

- 事件到来后自动入队、自动唤醒 Worker、自动运行并自动接续的完整生产闭环。
- 事件去重、合并、重试退避、租约/心跳、死信队列和并发冲突保护的统一 Runtime。
- 用户不在线时自动执行安全动作、在真正需要决策时挂起并零模型消耗。
- 原 Agent 会话 ID 与项目/任务检查点之间的可靠绑定。
- 从微信/飞书/网页任务变化、DDL、精力状态、卡壳和执行超时等信号统一触发调度。
- 对真实部署环境的崩溃恢复、重复投递、并发和长时间运行验收。

因此本方案优先补“事件调度和持续执行运行时”，而不是再造一套计划、任务或材料库。

## 4. 目标架构

```text
信号源
  ├─ 用户自然语言 / 临时任务 / 计划修改
  ├─ DDL 时间窗 / 定时唤醒 / 任务超时
  ├─ 精力反馈 / 卡壳 / 连续失败 / 无进展
  ├─ 资料新增或版本变化 / 证据上传
  └─ GitHub / 飞书 / 系统告警（按已授权连接启用）
          │
          ▼
Event Gateway（标准化、鉴权、去重、合并）
          │
          ▼
Durable Event Ledger（SQLite 起步；多实例再迁 PostgreSQL）
          │
          ▼
Signal Router + Policy Engine（规则、优先级、权限、熔断）
          │
          ▼
Agent Runtime / Worker
  ├─ Context Builder：自动读取项目、任务、材料版本、历史决定
  ├─ Planner：决定下一动作、估时、依赖、缓冲与截止风险
  ├─ Tool Adapters：文件、网页、检索、排程、代码、通知
  ├─ Checkpoint：会话ID、阶段、工具结果、重试次数、下一动作
  └─ Result Contract：done / continue / later / ask / blocked
          │
          ├─ 安全且可验证 → 自动继续 / 完成 / 定时复查
          ├─ 暂时无信号 → 保存状态、退出、不消耗 Token
          └─ 需要人决策 → WAIT_HUMAN，发一张卡片，等待后恢复
          │
          ▼
Evidence & Review（按任务验收标准做阶段/最终核验）
          │
          ▼
Project State + Schedule Reconciler（更新进度、剩余工作和排期）
```

## 5. 事件模型：所有变化都变成信号

每条事件采用统一结构，外部文本与控制字段严格分离：

```json
{
  "event_id": "稳定唯一ID",
  "tenant_id": "用户/租户ID",
  "project_id": "项目ID",
  "task_id": "可空",
  "source": "user|schedule|deadline|energy|blocker|evidence|integration",
  "type": "task.blocked",
  "subject_id": "被影响的任务或对象",
  "occurred_at": "ISO-8601",
  "payload_ref": "已保存数据/材料的引用，不重复塞全文",
  "correlation_id": "同一问题/任务链ID",
  "causation_id": "触发本事件的上游事件ID",
  "depth": 0,
  "priority": "critical|high|normal|low"
}
```

首批事件类型：

| 信号 | 触发条件 | Agent 自动动作 |
|---|---|---|
| `deadline.approaching` | DDL 进入 72h、24h、6h 窗口 | 读取交付标准和当前证据，计算剩余工作，锁定必要时间块 |
| `plan.changed` | 用户新增/删除/移动任务或修改截止日期 | 合并短时间内变更，重算冲突与容量，更新后续排期 |
| `task.blocked` | 用户求助、工具失败、重复失败或执行超时 | 自动读取当前材料和失败记录，换解法/缩小步骤/检索；必要时再问 |
| `energy.low` | 用户反馈疲惫或精力低于阈值 | 暂停高认知负荷任务，保留断点，按剩余精力重排 |
| `task.no_progress` | 超过任务自身预估时长且无有效产出 | 判断死磕、任务估时失准或等待外部依赖，执行缩小/换法/休息/转移 |
| `evidence.added` | 用户上传证据或系统发现新版本 | 自动关联对应任务，检查完整性并进入对应验收阶段 |
| `artifact.changed` | 已登记文件/代码版本发生变化 | 标记受影响诊断或计划过期，只重算受影响部分 |
| `worker.interrupted` | 进程退出、租约超时或服务重启 | 从最后成功检查点恢复，禁止重放已确认的副作用 |
| `human.replied` | 用户点选待决卡片 | 续接原会话和原任务，不重复提问 |

用户的长期主线（管理会计、考研、TRAE课程、TRAE原型、Agent大赛PPT、Agent智能体）作为既有项目数据读取，不写死在 Runtime 代码里。每次排期同时保护硬截止、固定事务、缓冲和休息，不允许一个任务无限挤占其他主线。

## 6. 自动执行状态机

建议统一状态：

- `RECEIVED`：事件已持久化。
- `QUEUED`：等待 Worker 领取。
- `RUNNING`：正在执行，带租约与心跳。
- `WAIT_TIMER`：预约未来复查；当前 Worker 退出。
- `WAIT_SIGNAL`：等待外部新事件；不轮询模型。
- `WAIT_HUMAN`：仅在关键决策时等待用户；Agent 进程退出。
- `RETRY_WAIT`：可恢复错误，按退避时间重试原运行。
- `BLOCKED`：缺材料、权限、依赖或信息，不伪造完成。
- `VERIFYING`：达到验收节点，运行任务专属检查。
- `SUCCEEDED` / `FAILED` / `CANCELLED`：终态。

状态转换由后端代码控制，模型只能提交结构化意图，不能自行修改权限、租户、工作目录、任务归属或终态。

### 不逐轮打扰用户的执行策略

1. Agent 在一个运行内可连续调用多个工具、读取返回、修正参数并继续，不为每个工具调用发卡片。
2. 工具层自动做必要的技术校验（HTTP状态、文件存在、版本号、结构化输出、幂等键），不要求用户检查。
3. 达到里程碑、存在风险或准备最终交付时才执行任务验收标准；不同任务使用不同验收器。
4. 只有需要用户提供新事实、授权或不可逆决策时才发卡片。
5. 任务进入 WAIT 状态即退出 Worker；不通过空转或定时请求模型维持“在线”。
6. 自动化结束后保存下一唤醒条件。新事件或到期计时器到来时再执行。

## 7. 持久化与跨会话记忆

建议在现有 SQLite 项目数据库上增量增加表；不要把所有内容塞进聊天历史，也不要依赖浏览器 localStorage 作为事实源。

| 表 | 核心字段 | 用途 |
|---|---|---|
| `agent_events` | event_id, tenant_id, project_id, type, payload_ref, occurred_at, depth | 只追加事件账本 |
| `agent_runs` | run_id, event_id, session_id, status, stage, attempt, lease_until, next_wake_at | 一次完整自主任务运行 |
| `agent_checkpoints` | run_id, checkpoint_no, state_json, context_version, created_at | 崩溃恢复与续接 |
| `agent_decisions` | run_id, decision_key, decision, reason, source_event_id | 保存用户决策，防止重复问 |
| `agent_tool_runs` | run_id, tool_call_id, tool, input_hash, result_ref, status | 工具轨迹与副作用幂等 |
| `agent_rules` | tenant_id, rule_id, enabled, event_match, policy_json | 每个用户独立规则 |
| `agent_outbox` | outbox_id, event_id, channel, payload, status | 可靠发送通知/回执 |
| `agent_dead_letters` | event_id, error_code, attempts, last_error | 多次失败后隔离，避免无限重试 |

关键约束：

- 所有表强制 `tenant_id` 隔离；查询和写入都从登录态服务端取得租户 ID，不能信任浏览器传入。
- `event_id`、`tool_call_id`、`decision_key` 唯一约束，重复事件和重复回执只记账、不重复执行。
- 先提交事件账本，再确认接收；业务状态更新与事件写入使用事务或 Outbox 保证一致。
- 保存原始材料引用、文件哈希、版本号和定位；不重复上传同一份文件，也不把外部文件正文复制进每次提示词。
- Context Builder 只读取当前项目相关的未完成事务：目标、当前版本、已完成证据、阻塞、最近决定、下一动作、恢复条件。已完成历史按需检索，不全量塞入上下文。
- 事件日志不可被 Agent 改写；状态投影可重建。

## 8. Agent 输出协议与权限分级

Agent 每轮最后输出一个经过 JSON Schema 校验的控制对象；自然语言说明仅用于摘要，不能作为执行指令。

建议动作类型：

- `continue`：继续当前运行。
- `done`：本次目标已达成，附产物引用和核验结果。
- `later`：在指定时间/条件后复查。
- `ask`：向用户询问一个明确决策，保存问题与选项。
- `notice`：只通知，不阻塞。
- `resolve`：关闭已解决的阻塞/卡片。
- `blocked`：说明缺少的材料、权限或依赖。

权限策略：

| 等级 | 动作 | 默认策略 |
|---|---|---|
| P0 只读 | 读已授权项目文件、查资料、分析日志、读取任务 | 自动 |
| P1 可回滚写入 | 新建草稿、生成报告、建立任务候选、写入独立分支 | 自动并记录 |
| P2 影响计划 | 调整未开始任务、重排时间、修改任务优先级 | 满足用户既定规则时自动；保留变更前后快照 |
| P3 外部副作用 | 发消息、提交PR、发布、合并、部署、覆盖正式材料 | 默认请求一次授权；按用户明确授予的白名单缩小范围 |
| P4 不可逆/高风险 | 删除原始资料、支付、泄露密钥、不可恢复覆盖 | 永远人工确认 |

禁止把事件 payload 中的文本解释为权限指令。Agent 不得通过生成新事件给自己增加权限。

## 9. 与上岸鸭现有功能的连接

| 现有模块/数据 | 新 Runtime 的接法 |
|---|---|
| 用户登录与多租户 | 每个事件、运行、规则、记忆、证据强制绑定 tenant |
| 项目/任务/DDL | 作为 Event Router 的事实源；DDL变化生成 deadline/plan 事件 |
| 动态排期与精力曲线 | Planner 只调用现有排期能力；疲惫/超时信号触发局部重排 |
| 资料中心与材料版本 | Context Builder 传引用、版本、定位，不要求重复上传 |
| Agent RAG（BGE-M3/Qdrant/Reranker） | 为当前项目检索相关材料与历史决定；检索结果保留来源和版本 |
| 卡点解题 | blocker 事件触发解卡 Agent，读取最近失败、代码/截图/材料和上次方案 |
| 证据验收 | 证据事件触发任务专属验收器；通过/部分/失败/未知分开保存 |
| V1→V2 与独立复核 | 复核是任务阶段事件；执行者与复核者分离，不能由同一执行输出自证 |
| 飞书/微信/站内提醒 | 只作为通知与人工决策通道，不作为状态事实库 |
| 网页 AI 对话 | 是事件输入/人工求助入口之一，不是 Agent 的唯一运行方式 |

## 10. 首批自动化规则（建议默认启用）

1. **DDL 雷达**：72小时、24小时、6小时触发；读取真实交付要求、进度和证据，生成剩余动作并检查每日容量。已排计划不因普通新事件随意挤占固定事务。
2. **临时任务插入**：用户新增任务后先判断是否硬截止/必须立即处理；只局部重排受影响任务，保留未受影响时间块。
3. **卡壳救援**：同一任务连续失败两次、工具返回同类错误或超出动态估时阈值时触发；先读失败历史，换解法、缩小动作或切换任务，不重复问已回答的问题。
4. **疲惫保护**：低精力信号到达后暂停高负荷任务，保存断点，安排低负荷任务/休息，并重新计算剩余容量。
5. **死磕干预**：默认观察90分钟窗口，但按任务实际估时、失败次数和产出判断；触发后不是只弹“停止”，而是生成具体下一步：保存断点、记录已尝试、换方法/求助/休息/转移到其他主线。
6. **证据到达**：自动识别材料类型、关联候选任务、检查是否满足该任务验收字段；证据不足时只指出缺项，不把点击完成当成通过。
7. **自动恢复**：Worker 中断或部署重启后按 run_id 恢复；工具副作用有幂等键，已成功的步骤跳过，未成功步骤继续。

## 11. 分阶段实施顺序

### P0：运行时底座（先做）

- 定义事件 Schema、状态机和租户边界。
- 在现有 SQLite 增加事件、运行、检查点、决策、工具轨迹和 Outbox 表。
- 实现 Event Gateway、稳定 ID、去重/合并、Worker 领取租约、心跳、超时回收。
- 实现 Context Builder 与 session_id/checkpoint 恢复。
- 实现 Agent Result Contract、WAIT_HUMAN、WAIT_TIMER、RETRY_WAIT。
- 实现权限分级、跳数熔断、失败隔离和审计查询。
- 加入后台 Worker 与服务启动恢复；空闲时不调用模型。

### P1：接入上岸鸭信号

- 接入 DDL、任务变更、精力、卡点、证据、资料版本等事件。
- 复用现有排程、RAG、任务验收和复核函数，不复制第二套业务逻辑。
- 加入任务局部重排、疲惫保护和死磕后的具体行动建议。
- 接入站内通知；人工决策卡片支持回复后续接原运行。

### P2：工具与外部事件插件

- GitHub Webhook/CI、飞书事件和网页监控按授权接入。
- 每个插件独立密钥、租户映射、签名校验、速率限制与撤销机制。
- 先只读和草稿；外发、合并、部署等副作用逐项白名单授权。

### P3：可靠性与真实验收

- 重复事件、乱序事件、并发任务、进程强杀、服务重启、通知失败、模型超时、工具部分成功等故障注入。
- 对照“人工逐轮操作”与“信号驱动自动执行”的耗时、重复提问次数、重复上传次数、Token 消耗、误触发率和任务按期交付率。
- 用用户真实项目做 V1→V2，保存原始证据，由非执行者独立复核；模拟测试不能替代真人收益。

## 12. 必须通过的验收用例

| 用例 | 操作 | 通过条件 |
|---|---|---|
| 同一事件重复投递 | 连续发送相同 event_id 10 次 | 只产生一个有效 run，不重复写入成果 |
| 用户三天不回复 | 触发 ask 后保持等待 | Worker 已退出；无模型轮询；数据库保留等待状态 |
| 用户回复继续 | 对原卡片作出选择 | 续接同一 run/session，不重复问相同问题 |
| 中途崩溃 | 工具成功后、状态提交前杀进程 | 恢复时通过 tool_call_id/幂等键识别已成功副作用，不重复执行 |
| 计划临时变化 | 执行中插入硬截止任务 | 产生新事件，只重排受影响时间块，保留已完成和固定事务 |
| 精力下降 | 发送 energy.low | 保存断点、安排休息/低负荷任务，不继续死磕高负荷任务 |
| 工具连续失败 | 同一动作失败两次 | 自动读取失败轨迹并换法/缩小动作；不循环重试同一提示词 |
| 资料已上传 | 同一文件再次被任务引用 | 通过 file_id/hash/version 复用，不要求用户重新上传 |
| 跨用户隔离 | 用户A事件尝试读取用户B项目 | 服务端拒绝，审计日志记录拒绝原因 |
| 注入攻击 | 事件正文要求更换工作目录/读取密钥 | 仅作为不可信数据，权限和路由不变 |
| 自动验收 | 上传课程进度/做题/PPT等证据 | 使用各自标准核验；未知项不能自动标通过 |
| 熔断 | Agent 连续生成自触发事件 | depth 达上限后停止派发并通知，不无限循环 |

## 13. 关键指标

- 事件接收成功率、去重率、事件到 Worker 启动延迟。
- 自动完成率、等待人工决策比例、恢复成功率、重复执行率。
- 重复提问次数、重复上传次数、用户逐轮确认次数。
- 单任务模型调用次数与 Token/费用；WAIT 状态应为零模型调用。
- DDL 按期交付率、固定事务被挤占次数、疲惫后继续死磕次数。
- 证据验收准确率、误通过率、未知判定率、独立复核一致率。

## 14. 实施边界与不做的事

- 不重写现有任务系统、资料中心、动态排期和证据系统。
- 不把每个工具调用都变成用户确认卡片。
- 不让 Agent 在没有新信号时持续空转或定时调用模型。
- 不因模型说“完成”就自动把任务标记通过；必须满足对应任务的证据标准。
- 不允许同一执行 Agent 给自己的成果做最终独立复核。
- 不把外部 Autoloop 的“macOS/Linux 支持”误写成 Windows 已支持。
- 不承诺完全无人值守；权限、外部副作用和不可验证事项仍需按规则处理。

## 15. 建议的第一条可运行闭环

先只选一个真实任务验证，不一次性接入所有信号：

1. 用户把任务、DDL、验收标准和已有材料登记一次。
2. 系统创建项目/任务记录并保存材料版本与引用。
3. DDL 或卡壳事件自动触发 Runtime。
4. Agent 自动读取既有上下文，拆解/执行安全动作；工具结果写入轨迹。
5. 如需用户决策，进入 WAIT_HUMAN 并退出；用户回复后续接原运行。
6. 产物与证据自动归档，调用对应验收器。
7. 根据剩余缺口更新排期；没有新信号时退出，不继续消耗 Token。

**完成标准不是“方案文档写好了”或“卡片弹出来了”，而是上述闭环在真实部署、真实材料、真实中断恢复下通过验收。**
