# 上岸鸭五项创新拆解、相似标杆与三人任务分工（2026-10-19）

> 项目定位不变：面向大学生竞赛、科研与创新实践的资料驱动执行智能体。本文区分“公开资料可核验的参考案例”“从案例提炼的方法”和“上岸鸭尚待验证的创新假设”。不得把参考案例写成国内赛事获奖作品，除非补齐官方获奖公告、作品名称与原始链接。

## 一、五项创新逐项拆解

### I1｜主创新：人做、模型验的真实成果闭环

**要解决的问题**：AI 给出建议、计划或“已完成”状态，不等于学生真正改出了合格作品；普通待办清单也不能证明新版本满足最初要求。

**产品流程**：
1. 冻结用户真实作品 V1 和原始验收标准；
2. A 诊断每个 gap，绑定当前版本、精确页/段/代码位置、现有证据与外部参考原文位置；
3. B 只把已核验 gap 转成有输入版本、目标位置、动作、理由、预期变化、输出、自检、失败下一步的 micro-step；
4. 队友只看行动卡，独立完成真实 V2，并记录实际耗时与卡点；
5. A 按原始标准逐项给 pass/fail/unknown；
6. B 只重排未通过项，保留已完成证据与历史记录。

**差异化假设**：不是“AI 能规划”，而是让“建议—真人产物—独立复核—局部返工”可追踪。该组合是否在市场上独特，仍需竞品核查，不能提前宣称首创。

**可演示证据**：同一个真实 PPT/报告/代码片段的 V1、3 条有定位的 gap、3 张不同的行动卡、真人 V2、按原标准的复核记录、剩余问题列表。

**验收指标**：盲执行者能否不靠口头解释开始做；原标准逐条通过率；错误放行数；复核后是否只改 remaining issues。

### I2｜主创新：停在哪、接回哪的任务现场恢复

**要解决的问题**：学生被临时任务、技术失败或疲惫打断后，常要重新翻资料、回忆做到哪里，导致任务重启成本高。

**产品流程**：
1. 保存项目 ID、作品版本、当前页/段/代码 locator、已完成项、尝试过的方法、当前卡点、下一动作、返回条件；
2. 用户回来时先匹配并确认项目与版本；
3. 恢复时展示“上次做到哪、证据是什么、下一步做什么”，不静默覆盖新版本；
4. 若材料版本已变化或恢复证据不足，转为 unknown/需确认，不假装准确恢复。

**差异化假设**：不是简单保存聊天历史，而是恢复“可执行任务现场”。需要用关页、重开、换会话、版本变更等场景测试。

**可演示证据**：中断前状态快照、重开后的恢复卡、恢复前后版本校验与日志。

**验收指标**：恢复到正确项目/版本/位置的比例；用户找到下一动作的时间；错误接续次数。

### I3｜支撑创新：论文难点的多讲法转换，最后回到原文做动作

**要解决的问题**：学生读不懂论文时，单纯生成长摘要仍可能没有理解，也没有推进原任务。

**产品流程**：
1. 锁定论文的原段落、公式、图表或术语；
2. 由用户选择或系统建议一种讲法：生活类比、分层解释、结构图、例子；短视频/动画仅作可选表达；
3. 解释结果标注对应原文位置，并明确哪些是类比、哪些是原文事实；
4. 讲解后给一个最小理解检查或实际动作；
5. 将回答与动作结果回写到该段落的学习记录，不能以“看完视频”直接判定学会。

**差异化假设**：创新不在“论文转视频”本身，而在“按卡点换讲法—核对理解—回到原文完成下一步”的闭环。

**可演示证据**：同一段论文的原文、两种解释、理解检查、用户答题/操作结果和原文定位。

**验收指标**：解释后正确回答率、能否定位原文证据、是否完成对应微动作。无真实用户试验前不写学习效果提升百分比。

### I4｜支撑创新：5 分钟冷启动，用真实小任务诊断卡点

**要解决的问题**：用户常说“我不会”“我不知道从哪开始”，但自我描述无法准确区分资料缺失、概念不懂、操作不会、任务过大或时间不足。

**产品流程**：
1. 从当前真实任务选一个可在约 5 分钟开始的小动作；
2. 给出可见产物，例如找到一个原文证据、跑通一个最小命令、改好一处 PPT；
3. 记录是否开始、实际耗时、失败位置和用户反馈；
4. 根据实际证据调整后续任务粒度与帮助方式，不把一次失败贴成能力标签。

**差异化假设**：以真实试做结果而非单靠问卷/自评来决定下一步。5 分钟是冷启动设计目标，不代表所有任务都能在 5 分钟内完成。

**可演示证据**：试做前的猜测、试做产物、实际卡点、调整后的下一动作。

**验收指标**：开始率、首个有效产物完成率、诊断与实际卡点一致性。

### I5｜支撑创新：低打扰状态分流——先询问，再决定换讲法、休息或继续

**要解决的问题**：同样的停顿可能来自听不懂、技术困难、临时有事或疲惫；系统不能未经确认就替用户判断状态。

**产品流程**：
1. 发现任务停滞或用户主动表示卡住时，先用低打扰问题确认原因；
2. 按用户选择分流：听不懂→换讲法；技术困难→排障；临时有事→保存现场并约定返回条件；疲惫→由用户决定休息或继续；
3. 只记录完成任务所需的最少状态信息，允许修改/不回答；
4. 摄像头、穿戴等被动状态识别不进入首版主流程，只能作为另行评估的可选研究方向。

**差异化假设**：以用户确认的原因驱动不同恢复路径，而不是用单一提醒或未经证实的情绪/疲劳识别。

**可演示证据**：同一个任务停滞场景，分别选择“听不懂/技术困难/临时有事/累了”后产生的不同动作卡。

**验收指标**：分流路径是否符合用户选择；不必要打扰次数；恢复后能否接回原任务。不得声称能准确识别情绪或疲劳，除非另有有效研究证据。

## 二、相似公开标杆：亮点、可借鉴方法与边界

### 案例 A｜SWE-agent（NeurIPS 2024）

- **可核验事实**：SWE-agent 是由普林斯顿大学与斯坦福大学研究者开发的开源 Agent 项目，论文发表于 NeurIPS 2024；它围绕真实 GitHub issue 操作代码仓库并尝试解决问题。
- **亮点**：把自然语言问题落到具体仓库和工具操作；强调 agent-computer interface 与实际任务结果，而不是只给建议；有公开论文、代码与 SWE-bench 评估可复查。
- **上岸鸭可借鉴**：真实输入定位、操作轨迹、可复现实验、结果验收；对应 I1 的“真实材料—具体动作—结果复核”。
- **不能照搬/不能声称**：SWE-agent 主要面向软件工程，不是高校科研学习产品；它的学术接收不证明上岸鸭独有，也不能证明我们的闭环已有效。

参考：
- 项目与论文说明：https://github.com/SWE-agent
- 论文：https://arxiv.org/abs/2405.15793
- SWE-bench 官方基准与排行榜：https://www.swebench.com/

### 案例 B｜OpenHands：暂停、恢复与持久化会话

- **可核验事实**：OpenHands SDK 官方文档提供会话暂停/恢复、跨会话状态持久化等开发能力。
- **亮点**：将会话状态和工作区状态作为工程对象管理；可在执行中暂停，再恢复继续，而不是完全依赖用户重述。
- **上岸鸭可借鉴**：I2 的项目现场快照、明确恢复点、会话持久化、工具/工作区上下文的关联。
- **边界**：这是工程能力参考，不将其写成竞赛获奖作品；仅有“支持暂停恢复”不等于已经解决上岸鸭的跨版本任务现场恢复。

参考：
- 官方暂停与恢复指南：https://docs.openhands.dev/sdk/guides/convo-pause-and-resume
- 官方持久化指南：https://docs.openhands.dev/sdk/guides/convo-persistence
- SDK 概览：https://docs.openhands.dev/sdk/arch/sdk

### 案例 C｜SWE-bench：用真实任务结果评估 Agent

- **可核验事实**：SWE-bench 以真实 GitHub issue 和对应代码库为任务，评估 Agent 是否解决问题；官方页面提供不同任务集与结果。
- **亮点**：评估不止看输出是否流畅，而看任务是否解决；设置可复查的任务与统一的评价口径。
- **上岸鸭可借鉴**：为 I1 建立原始判据、V1/V2 对照、pass/fail/unknown、失败案例和同任务对照；为 I3/I4 设计可观测结果。
- **边界**：软件修复基准不能直接证明教育效果；上岸鸭必须自建适合 PPT、论文、调研和科研任务的评价标准。

参考：
- 官方排行榜与基准说明：https://www.swebench.com/
- SWE-bench 项目组织与代码：https://github.com/swe-bench

### 如何使用“相似获奖作品”资料

团队此前已有的获奖作品拆解文档，应由 A 同学补齐每个国内参赛作品的：**官方获奖公告链接、准确作品名、主办方/奖项/年份、官方作品介绍或仓库、原文页/段定位、能借鉴的方法、与上岸鸭的区别**。目前本文件不把未核实的作品名冒充为获奖案例。公开标杆与国内比赛获奖作品分开列，避免答辩被追问时无法出示证据。

## 三、创新与五个运行机制要分开讲

“五项创新”是用户价值/产品假设；“循环机制、对话示意、工具调用、上下文原则、记忆器”是支撑 Agent 稳定运行的工程机制。不要把这两组内容混成同一层级。

- 循环机制：诊断 → 行动 → 执行 → 复核 → 局部重排。
- 对话示意：展示用户输入、澄清、动作确认、结果反馈与失败分流。
- 工具调用：说明什么条件下读文件、定位原文、执行操作、保存版本；失败如何处理。
- 上下文原则：优先使用当前项目、真实材料和版本化证据；资料不足就 unknown/blocked。
- 记忆器：存储项目状态、版本、位置、尝试、卡点和下一动作；区分持久状态与当前对话，不把猜测写成事实。

## 四、三人任务分工与依赖顺序

> 仓库现有分工使用 A（资料诊断）、B（行动与排程）、C（队长集成）。用户此前确认 A 的资料抓取已完成，因此不重复安排“重新爬取”，只补来源核验与定位。

### A 同学｜资料研究、证据化诊断与复核

**任务**
1. 对照已有获奖作品拆解文档，整理至少 3 个最相近的公开作品/标杆；国内赛事案例必须有官方获奖证明。
2. 每个来源记录：官方 URL、标题、作者/主办方、年份、原文页/段/章节 locator、可借鉴的方法、不可照搬的部分。
3. 针对冻结的真实 V1，产出至少 3 条证据化 gap：作品版本、精确位置、当前证据、参考原文位置、提取方法；资料不足标 unknown。
4. 对 I3 产出同一论文段落的两种讲解脚本与原文映射；收到真人 V2 后按原判据复核 pass/fail/unknown。

**交付物**：research/reference-evidence-matrix.md、真实材料诊断表、复核记录。

**验收**：随机抽 3 条 gap，其他队员能独立定位当前作品问题与参考原文；只给 URL、摘要或“建议优化”不算通过。

### B 同学｜微行动卡、排程与剩余问题重排

**任务**
1. 只接收 A 已核验的 gap；将每条转成 grounded micro_steps，不能用通用三步模板补位。
2. 每步必须包含：input_version、target_locator、action、reason、expected_change、output、self_check、failure_next、capability_basis、source_refs。
3. 任务类型分别处理 PPT、论文/文献、调研数据、代码/接口，不能一套步骤套所有任务。
4. 首步尽量设计为约 5 分钟能启动且有可见产物；如果材料/定位/动作缺失，标 blocked/unscheduled。
5. A 复核后只调整 remaining issues，不覆盖 completed、in_progress、pending_review 或 locked 任务。

**交付物**：行动卡样例、任务状态变更记录、剩余问题重排结果。

**验收**：未参与前文的队友只看行动卡即可开始操作；找不到材料或失败时知道下一步找谁、补什么证据。

### C／队长｜冻结版本、盲执行、集成与数据记录

**任务**
1. 选择一份真实作品，冻结 V1 与原始验收标准；不使用预置 Demo 数据冒充真人结果。
2. 把 A 的诊断、B 的行动卡和参考资料链接串成一条可追踪链路。
3. 安排另一名队员只看行动卡完成 V2，记录实际耗时、卡点和操作产物。
4. 收集 A 的逐条复核结果，再让 B 只调整未通过项；保存 review_id、版本与状态变化。
5. 组织 5–8 位有近期真实科研/竞赛卡点的学生做探索性测试；区分用户原话、观察事实和研究者解释，保留反例。
6. 汇总 PPT：主创新只讲 I1、I2；I3–I5 放在支撑创新页；没有实测数据的内容明确标“待验证”。

**交付物**：V1/V2 对照、真人盲执行记录、复核记录、试用数据表、PPT证据页。

**验收**：从目标能反查 gap → 参考原文 → micro-step → 执行人 → V2 → 复核 → remaining issue。缺一环就不能宣称闭环完成。

## 五、执行顺序与阻塞条件

1. C 冻结真实 V1 与验收标准。
2. A 做证据化诊断并交来源定位。
3. B 基于已核验 gap 写具体行动卡。
4. 另一队员只看行动卡，产出真实 V2。
5. A 按原标准复核。
6. C 确认记录完整；B 只重排剩余问题。
7. C 更新 PPT 和试用数据，注明样本量与限制。

阻塞规则：
- A 无真实材料/定位 → 停在诊断阶段。
- B 无 grounded micro_steps → blocked/unscheduled。
- 无真实 V2 → 不得宣称闭环完成。
- 无 A 复核 → 不得将成果标为通过。
- 无用户试验 → 创新效果只能写假设，不写虚构提升百分比。
