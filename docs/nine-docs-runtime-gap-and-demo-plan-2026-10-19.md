## 一、先把产品说清楚

**上岸鸭不是再做一个学习聊天机器人，而是帮助第一次做科研、竞赛和创新实践的大学生，把手上的真实作品从 V1 推到可复核的 V2；中途卡住或离开后，仍能回到准确的原步骤。**

两条主创新：
1. **人做、模型验：** 读取真实 V1 和原始判据 → A 按原文位置诊断差距 → B 给出绑定版本与位置的微动作 → 人实际修改并提交 V2 → A 按原判据逐条给 pass/fail/unknown → B 只调整剩余问题。
2. **停在哪、接回哪：** 中断前保存项目、版本、原文位置、卡点、已试办法、承诺、下一动作和返回条件；新会话/页面重开后先确认项目，再接回准确的微动作。

三个支撑方向，不单独包装成 headline innovation：
3. 论文卡点换讲法：只针对用户选中的当前段落生成有原文定位的通俗解释/图文/短片；看完必须回到原段落完成一个微动作。
4. 5 分钟冷启动：以当前真实目标、材料、能力与时间，生成一个能在 5 分钟内开始、留下可检查产物的第一步。
5. 用户自主状态分流：用户选择“听不进去 / 真的累了 / 遇到技术困难 / 临时有事”，系统走不同分支；不以摄像头或表情推断状态。摄像头、穿戴设备不属于首版必做。

注意区分：以上是**五个产品创新方向**；寄存器、循环、上下文、工具调用、跨对话记忆是支撑这些方向的**五个运行机制**，不是另外五个创新点。

## 三、当前究竟哪里“没跑明白”

### P0：必须先跑通，否则不能称为闭环

1. **真实材料诊断不稳定。** 文档记录过真实模型诊断 4 次仅 1 次成功、复核 3 次全失败。PR #22 的 70 项工程测试通过，不代表真实模型语义质量已通过。
2. **A→B 的证据交接仍是核心风险。** Issue #7 明确指出：如果 A 没提供有依据的 `micro_steps`，B 不能退回“打开材料→完成目标产物→逐条检查”这种通用三步。缺定位、缺引用、缺真实产物或验收条件时必须 `unknown/blocked`，不能伪装成已排程。
3. **真实 V2 没有验收记录。** 需要由另一位成员只看行动卡、不靠队长口头解释，实际改一份 PPT/报告/代码，记录耗时、卡点与新版本。
4. **A 复核后只调整剩余项的真人闭环未完整验收。** 必须按原始判据给 pass/fail/unknown；复核前不可宣称完成；已完成、进行中和锁定任务不得被重排覆盖。
5. **PR #21/#22/#25 的代码交付状态不等于已上线。** PR #25 描述中工程门槛与 Windows Chrome DOM/SQLite/HTTP 已用受控夹具验证，227 项通过；但 PR 仍为草稿，main 未合并。它明确承认真人 V2、真实模型语义质量和完整人工操作仍待验收。
6. **中断后准确接续没有真实试验。** 已有现场卡/尝试/承诺/条件返回等基础，但需真实关闭页面/重开或新会话，验证恢复到同一个项目、版本、原文位置和下一动作，而非只显示一段摘要。

### P1：主闭环稳定后补齐的支撑功能

7. **五分钟冷启动没有证明用户真的能开始。** 需要拿一个真实任务测从打开卡片到首次有效操作的时间、产物和完成标准；不能只看 AI 是否生成计划。
8. **论文换讲法尚未形成完整可验收交付。** 需要原文定位、通俗脚本、人工核对、实际可播放视频/图文、看完回原段落做动作。脚本或分镜完成不等于视频完成。
9. **状态分流/休息计时仍有功能缺口。** 首版先做用户主动选择、保存现场、短休/延长/结束、返回确认和误提醒记录；摄像头、华为穿戴不作为首版依赖。
10. **真实模型接入与错误恢复未证实。** 需要检查模型 API 是否稳定、结构化字段能否解析、失败是否留痕、重试一次后是否转入 blocked/unknown；API key 必须后端保存，不可暴露在前端。
11. **公网评委体验未形成最终验收。** main 当前根目录仍被 PRD 描述为部署压缩包；要提供可访问网址、匿名化测试账号和预置样例作品，并在无本地开发环境情况下点开验证。
12. **用户证据缺失。** 还没有真实 5–8 位目标用户的访谈与 3–5 位试用用户的完整记录。不能编造“提升 X%”或宣称创新点已由调研证明。

## 四、Demo 不要做成五个功能大拼盘

建议做**一个可交互的主场景 + 五个分支入口**。答辩主流程只演两个主创新；三个支撑方向作为遇到具体情况时的分支。样例数据必须明显标注“预置演示样例”，不可冒充真实用户或真实模型结果。

### Demo 主场景：一份参赛项目 PPT

预置材料：
- 目标：把参赛项目 PPT 改到符合指定的提交要求；
- V1：一份可打开、可定位到页码的 PPT/文本样例；
- 原始判据：例如“问题定义有来源”“方案步骤可执行”“结果指标有口径”；
- 一条真实、可定位的差距；
- 一张 B 行动卡；
- V2 示例（由团队实际修改产生，不由 Demo 假数据自动宣称成功）。

### 屏幕 1：创建项目与接入材料
用户选择项目、上传 V1、输入目标与原始判据。页面显示文件名、版本号、解析状态和可定位内容。解析失败必须显示失败，不得继续进入诊断。

### 屏幕 2：A 诊断差距
每条差距必须有：
- 差距 ID、当前作品版本、页码/段落定位；
- 原文证据与来源；
- 当前差距是什么、为什么影响目标；
- 不确定项与缺失证据；
- 一个可执行微动作。
没有证据定位时显示 `unknown/blocked`，不能生成看似完整的结论。

### 屏幕 3：B 生成行动卡
卡片至少包含：
`input_version / target_locator / action / reason / expected_change / output / self_check / failure_next / capability_basis / source_refs`。
第一步尽量在 5 分钟内能启动。缺真实产物或验收条件的任务不允许进入执行日程。

### 屏幕 4：人真实执行
用户勾选“开始”，输入/上传实际修改结果，记录开始与结束时间、遇到的卡点和尝试过的方法。Demo 不可仅点一下“完成”就伪造 V2；需要接受真实文本或真实文件。

### 屏幕 5：V2 提交与 A 复核
V2 提交后先进入 `pending_review`。复核页按**原始判据**逐条显示 pass/fail/unknown、证据位置、原因和剩余问题。版本不匹配、引用不存在或证据不足必须拒绝放行。

### 屏幕 6：B 只调整剩余问题
保留已通过和锁定任务，只针对 fail/unknown 生成下一轮行动卡；记录计划版本。到此才完成一次主闭环。

### 屏幕 7：中断接续
在行动卡执行中点击以下之一：
- “听不进去”：保存存档点，展示当前段落的通俗解释/图文，结束后回到原位置做一个小动作；
- “真的累了”：保存现场，选择短休、延长或结束；返回时由用户确认继续，不自动勾完成；
- “遇到技术困难”：记录错误与已尝试办法，提供可核对的下一步/求助卡；
- “临时有事”：保存当前步骤、承诺和返回条件。
刷新/关闭后重新打开，页面必须先显示“做到哪、已完成什么、下一步”，并让用户确认项目。

## 五、五个创新点在 Demo 中分别怎样出现

| 创新方向 | 可见交互 | 关键验收证据 | 不算通过的情况 |
|---|---|---|---|
| I1 人做、模型验 | V1→A 差距→B 卡片→真实 V2→逐条复核→剩余项 | V2 文件/文本、原判据、复核记录、人工确认 | 模型自己生成 V2；只显示“完成” |
| I2 停在哪、接回哪 | 中断保存→刷新/新会话→确认项目→回到原微动作 | 保存前后同项目、同版本、同位置、同下一步；恢复耗时 | 只恢复聊天摘要或重开后重新规划 |
| I3 论文卡点换讲法 | 选择“听不进去”→原文定位解释/图文→回原文做动作 | 每句解释能回溯原文；动作产物与耗时 | 只生成摘要/视频，没有回原文动作 |
| I4 五分钟冷启动 | 选择真实目标→生成首个微动作→执行产物 | 首次有效操作时间、实际产物、用户能独立照卡完成 | 只给长期计划，或依赖口头讲解 |
| I5 用户自主状态分流 | 用户主动选择卡点/疲惫/临时中断→不同处理→接回 | 用户选择、分支结果、误提醒/关闭记录 | 摄像头自动给用户贴状态标签或倒计时自动算完成 |

## 六、实现顺序与团队分工

### 第一阶段：先打通最小主闭环
1. 固定一个真实参赛 PPT/科研材料和原始判据。
2. 核验文件解析、版本与 locator。
3. 让 A 对一条真实差距给出证据和具体微动作。
4. 让 B 只接收通过证据门的微动作；没有就 blocked。
5. 由另一名成员只看行动卡改出 V2。
6. A 按原判据复核，B 只生成剩余项。
7. 留存每一步的输入、输出、耗时、错误和人工确认。

### 第二阶段：在主闭环中加入中断接续
1. 行动卡执行中保存存档点。
2. 触发“听不进去”或“真的累了”。
3. 刷新/关闭/重新打开后核对准确恢复。
4. 用户确认后继续原微动作；讲解/休息本身不算任务完成。

### 第三阶段：补三项支撑方向
- I4 先做可执行 5 分钟卡；
- I3 先做带原文定位的图文解释，再人工成片，不依赖未验证的视频 API；
- I5 先做用户主动按钮和记录，摄像头/手表另行验证。

### A/B/C 交付边界
- **A：** 真实材料、原始判据、来源与 locator；输出有证据的 gap；复核 V2。不能只交资料抓取或泛化建议。
- **B：** 只接收已核验的 gap，交付字段完整的微动作卡；缺字段就 blocked；依据实际 V2 只排剩余任务。
- **C/队长：** 维护状态、版本保护、项目确认、承诺/依赖调度、联调和验收；记录每步实际结果，不以接口返回代替用户完成。

## 七、最小验收清单（演示前逐条打勾）

- [ ] 真实 V1 能被读取，且版本/页码/段落可定位。
- [ ] A 至少输出一条有原文证据的真实差距。
- [ ] B 生成的行动卡可由另一人独立照做，包含产物和自检标准。
- [ ] 执行人真的修改并提交 V2，记录实际用时与卡点。
- [ ] V2 先进入 pending_review；A 按原判据输出 pass/fail/unknown。
- [ ] 有至少一条 fail/unknown 能生成下一张卡，已通过项不被重排覆盖。
- [ ] 在任务中断后刷新/重开，能恢复到同一项目、版本、locator 和微动作。
- [ ] “听不进去”和“真的累了”走不同路径，均能回到原动作。
- [ ] 失败不记成功；缺证据不放行；版本冲突会阻止旧结果覆盖新状态。
- [ ] 真实模型与预置样例明确区分；错误和耗时留痕。
- [ ] 公网地址和测试账号经无痕/独立浏览器验证；匿名化，不泄露个人信息。
- [ ] 真人试用记录与指标口径可复核；没有数据就写“尚未测量”。

## 八、试用数据怎么记

每位用户/每次任务至少记录：
- participant_code（匿名编号）、任务类型、开始时间；
- 原始目标与判据、V1 版本、差距条数；
- 行动卡 ID、是否无需口头解释即可开始、第一次有效操作时间；
- V2 版本、实际耗时、卡点、返工次数；
- 原判据 pass/fail/unknown 数量、误放行次数、人工复核结论；
- 中断时间、恢复时间、恢复后是否回到原微动作；
- 用户负担、误提醒、是否愿意继续用。
先做 5–8 人访谈、3–5 人试用；样本只代表这批用户，不能外推全体大学生。

## 九、最终答辩表述

可以说：“上岸鸭把科研与竞赛助手的终点从生成建议，推进到真实作品的版本化修改与按原判据复核；同时保存任务现场，在用户中断后恢复到准确微动作。我们正在用真实 V1/V2 和中断恢复试用验证这两项主张。”

在完成真实测试前，不可以说“已证明优于所有竞品”“提升效率 X%”“五个创新点均已跑通”。工程测试通过、预置样例演示、真实用户效果是三个不同证据等级。
