# 上岸鸭总调度｜真实作品驱动的私人定制测试与三人迭代（2026-10-23）

## 0. 队长决策摘要

本轮不是重新生成一条通用学习路线，也不是只对获奖作品做竞品分析。目标是把团队提交的真实作品、本人目标（省奖/国赛质量）和对应官方规则作为输入，测试上岸鸭能否完成：

**当前真实作品 V1 + 用户目标 → 证据化差距诊断 → 个人专属第一步 → 真人执行 → 真实 V2 → 按原标准独立复核 → 只重排未通过项 → Agent 缺陷修复 → 同输入回归。**

真实作品是主要验收样本。模拟作品只用于补测边界情况，必须显式标注 SYNTHETIC，不能算作真实成果、真实用户效果或获奖证据。

本文件是团队内部总调度，不是赛事官方评分，也不保证获奖。最终目标标准必须来自对应赛事、年份、赛道的官方通知、评分表与提交要求；参考作品只提取方法，不复制内容和版式。

## 2. 创新主张：什么才算真正差异化

1. **以真实作品为对象，不以自述水平代替实际诊断**：差距必须指向具体文件版本、页/段/表格/代码位置和原文证据，并绑定官方目标标准。
2. **按个人条件定制第一步**：结合已展示能力、截止日期、可用时间、依赖、材料条件和用户选择的困难状态，生成 1–5 分钟内可开始的微动作及可检查的小产物。
3. **失败后能换路径**：记录尝试、失败原因和实际耗时；资料缺失、方法不懂、操作报错、中断遗忘应走不同分支，重复无效两轮后转补证/求助，不继续重复空泛建议。
4. **准确接回现场**：保存项目、版本、材料锚点、已完成产物、已尝试方法、下一动作和恢复条件；版本变化先核对，不串项目、不重复完成项。
5. **人做、Agent 按原标准验**：真人提交 V2 后按冻结标准逐项判 PASS/FAIL/UNKNOWN；没有新版本证据不能通过。
6. **只重排剩余问题**：保留 completed、in_progress、pending_review、locked 任务与依赖；只针对 FAIL/UNKNOWN 预览调整，确认后才应用。
7. **低打扰状态分流**：状态由用户主动选择；干预后必须回到原作品和原动作，不使用未经同意的摄像头推断。

上述是待验证的产品假设。工程存在、页面可点、单测通过，不等于真实创新效果成立。

## 3. A 同学批注｜真实样本登记、目标标准和证据诊断

**主责：先把真实作品“现在是什么、目标要求什么、差在哪里”说准。**

### 本轮任务
1. 对用户已提交的作品逐一建立登记：作品 ID、原件路径/链接、文件版本或 hash、可读覆盖率、赛事名称/年份/赛道、官方规则链接、提交物和评分维度。
2. 首轮至少覆盖：
   - 嘉农芯生：核查专利状态、效率/成活率等指标的原始批次、样本量、对照与计算口径。
   - 滴水润疆：核查 PDF 与图片型 PPT 的解析覆盖，推广/效率主张是否有原始数据。
   - 菌润乡土：确认旧 DOC 是否完整解析；实验、样本、技术和推广数据缺证时标 UNKNOWN。
   - 湘秀未来/湘匠织秀：核对当前作品版本、目标标准、工艺/产品/用户需求与市场证据。
   - 《影幻魔方》及其他提交样本：沿用 Issue #8 的方法，不能把已有的问卷、商业模式、服务链误写成“缺失”；只标真实存在的 gap。
3. 对每个 gap 必须写：目标标准、当前原件位置、原文证据、参考作品原始位置、只提取的机制、适用条件、证据等级、影响、补证动作。
4. 外部参考作品中的数字只能当参考，不能移植为我方成果。区分“已实现/原型/计划”“实测/引用/假设/未知”。
5. 图片/表格/扫描 PDF/旧 DOC 未完整读取时，先标覆盖缺口并 OCR/视觉复核，不得根据不完整文本判断全文。

### A 的交付与验收
- 真实样本登记表 + 官方标准映射表。
- 每个首轮样本至少 3 条有原件定位的差距；材料不足时明确 UNKNOWN/BLOCKED。
- 另一成员随机抽查至少 10 条诊断，能在 2 分钟内定位正确文件版本和原文；错版、错引、无证据断言即 FAIL。
- 把已验证的 gap 交给 B；没有证据的 gap 不得转成生产行动卡。
- 在 Issue #7 回报：样本/版本、原件定位、官方规则来源、失败条目、修复文件/函数、复测结果。

## 4. B 同学批注｜私人定制行动卡、真实执行和 V2

**主责：证明 Agent 给的是这个人、这个作品的下一步，而不是通用学习路线。**

### 本轮任务
1. 只消费 A 的 grounded gap。每张卡至少包含：
   `input_version / target_locator / action / reason / expected_change / output / self_check / failure_next / capability_basis / source_refs`。
2. 第一步必须能在 1–5 分钟内启动，并有看得见的小产物；依赖、工具、资料、预计时间、实际时间、完成定义和求助条件必须写清。
3. 按不同作品类型采用不同动作：
   - 技术/科研类：补原始数据、复现实验、验证方法或对照指标。
   - 商业/产品类：补真实用户访谈、需求验证、交付流程或成本收益依据。
   - 市场/传播类：核查样本、问卷方法、渠道证据、传播/转化数据。
   - 财务类：核对假设、公式、统计期、成本/收入/利润与敏感性分析。
   不允许同一套三步模板套全部项目。
4. 选至少两个不同类型的真实作品，由**没有参与诊断/编卡的人**只看行动卡独立执行；不得口头补充。记录是否在 5 分钟内开始、求助次数、实际耗时、卡点、产物路径和 V1→V2 差异。
5. 如果 `micro_steps` 缺失或没有具体位置，生产任务必须保持 BLOCKED/UNSCHEDULED；不能退回“打开材料→完成产物→检查”的万能三步。
6. 真实 V2 提交后进入 PENDING_REVIEW；不得自己给自己判 PASS。失败后只修改未通过项，并保留原版本、尝试和时间记录。

### B 的交付与验收
- 至少两份不同类型真实作品的专属行动卡、独立执行记录、V2 文件和失败记录。
- 非作者不看前情也能开始；若必须口头解释、找不到位置、产物无法检查，即 FAIL。
- 对比修复前后的行动卡，证明同一 Agent 对不同项目给出不同且有证据的动作。
- 在 Issue #7 回报：卡片 JSON/导出、执行者、开始耗时、实际耗时、V2 路径、需要的修复和回归结果。

## 5. C／队长批注｜集成、版本保护、真实模型与总验收

**主责：让 A→B→真人→A 复核→B 局部重排真正连起来，维护唯一可信进度。**

### 本轮任务
1. 核对 PR #21、#22、#25、#35 的分支、CI、合并状态与部署状态；目前它们均为 Draft/未合并，不把分支测试通过说成主分支已经具备。
2. 先处理 P0：确认真实 V2 没有 A 当前版本复核和必要人工确认时，不能进入 completed；旧版本回调不能通过新版本验收；缺 micro_steps 的任务不能被总调度改回可执行。
3. 用同一个真实项目跑端到端：
   `真实 V1 → A 证据诊断 → B 专属微动作 → 非作者执行 → 真实 V2 → A 按原判据复核 → B 只重排 FAIL/UNKNOWN → C 保存 trace`。
4. 单独验证真实模型调用、材料检索与语义诊断。未配置/失败就写 BLOCKED/FAIL，不能以 Mock、fixture、headless 测试代替。
5. 做中断恢复、版本变化、跨项目串线、重复任务、失败两轮、无产物强行完成、部分通过后重排等回归。
6. 招募 5–8 位同学，对相近任务进行上岸鸭与通用助手对照；尽量固定作品、目标标准、时间预算与盲评规则，记录首步耗时、恢复耗时、V2 质量、独立执行率、求助次数、用户负担和调用成本。小样本只作探索性结果。
7. 汇总国赛质量证据：真实应用链接、演示账号（不公开密码）、现场可操作链路、V1/V2 对比、失败案例和修复记录、真实用户反馈、风险与局限。

### C 的交付与验收
- 一张分支/PR/CI/部署状态表；每个状态有链接和时间。
- 一条完整真人闭环的 trace 和复核证据。
- 真实模型、工程、模拟、真人四类结果分开统计。
- 只有证据达到 E4（独立复核/对照）才可把核心创新主张写成“已验证”；否则标“部分验证/待验证”。
- 最终决定 GO / REVISE / STOP，并说明理由、阻塞和下一责任人。

## 6. 统一证据等级和状态定义

- **E0 / NOT_RUN**：仅有设计，未测试。
- **E1 / ENGINEERING_PASS**：单测、接口或受控工程测试通过；不代表真实模型或真人效果。
- **E2 / LIVE_MODEL_PASS**：真实模型与真实工具运行，输入、输出、trace 可复现。
- **E3 / REAL_HUMAN_TASK_PASS**：非作者真实执行并提交真实产物，记录实际耗时和卡点。
- **E4 / INDEPENDENT_REVIEW_PASS**：另一人按冻结的原标准独立复核，保留 V1/V2 和逐项证据；若声称优于通用助手，还须有公平对照。
- **BLOCKED**：缺模型配置、原件、官方标准或必要权限；必须写阻塞原因与解除动作。
- **FAIL**：实际行为未达到冻结判据。
- **UNKNOWN**：证据不足，不能判定。
- **PASS**：仅对具体测试用例生效，不自动代表整个项目通过。

## 9. 最终总控规则

- 不按“批注写了、代码存在、按钮能点、单测通过”宣布创新通过。
- 不把参考获奖作品的指标复制到自家项目；不把模拟案例说成真实成果；不把计划/意向说成客户或收入。
- 不为追求分数修改冻结标准；记录失败、未知与反例。
- 先跑通一条真实闭环，再扩展更多作品。对每个真实作品都做个性化诊断，但第一轮先选两个类型差异明显的项目验证通用机制。
- 每位成员只对自己负责的交付和证据签字；队长依据独立证据做总验收。
