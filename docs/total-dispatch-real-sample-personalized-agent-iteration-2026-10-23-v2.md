# 总调度 V2｜真实作品驱动的私人定制 Agent 测试与国赛质量迭代
更新：2026-10-23  
仓库：phucmanh146-dot/shangan-ya  
总负责人：队长 C  
目标：用团队真实参赛作品验证上岸鸭的私人定制提升功能，发现 Agent 缺陷后修改并回归；逐步形成可复现、可交付、可现场演示的高质量国赛作品。**不承诺获奖，不把计划、mock 或工程测试包装成真实效果。**

## 0. 你真正要验证的是什么？

不是拿获奖作品做一次普通竞品总结，也不是让 Agent 生成一份通用学习路线。真实测试应当回答：

> 给 Agent 一份我们自己真实的参赛作品、当前进度和明确目标，它能不能准确找出这份作品离目标差在哪里，参考优秀作品中可迁移的方法，定制出适合这个项目的第一步；由队友实际执行、产出新版本，再按原判据复核。失败后，团队能不能据此修改 Agent，并用同一输入证明是否改善？

目标链路：

**真实 V1 + 目标标准 → 证据化差距 → 项目专属微动作 → 非作者真人执行 → 真实 V2 → 独立复核 → 只重排剩余问题 → 中断恢复 → 失败进入回归集。**

“优秀作品”是质量参照和方法来源，不是让 Agent 复制其内容，也不自动等同于本届官方评分标准。模拟样本只用于补充异常/边界测试，不得计入真实项目效果。

## 1. 创新性判断：设计方向有潜力，但尚未被真实验证

### 当前最值得保留的两个主创新假设
1. **作品级私人定制与真人交付闭环**：不是按用户自述能力生成通用计划，而是基于用户自己的作品版本、原文位置和目标标准生成差距与微动作，最终要求真人产出 V2 并按原判据复核。
2. **中断后精确接续与剩余项重排**：记住准确项目、版本、文件位置、已完成证据、失败尝试和下一步；回来时接回原步骤，复核后只重排 fail/unknown。

以下可作为支撑机制，而不是独立宣称的核心创新：按当前步骤装配上下文、缺证拒答/求助、有限循环和停止条件、失败回归测试。

### 为什么现在不能说“创新已经满足”
上传的《上岸鸭竞品拆解与过程干预方案（含大模型技术分析）》中明确记录：历史真实模型诊断 4 次成功 1 次、复核 3 次成功 0 次；完整真人 V1→行动卡→V2→独立复核链仍未提供。它说明设计差异点已提出，不等于差异已经被真实用户数据证明。  
PR #35 的当前工程记录进一步显示：239 项 Python 测试、JS 语法和受控无头浏览器流程通过；但 PR 自己注明真实模型未配置、未取得真人 V2/试用效果、未部署生产。流程证据覆盖 A 5/20、B 0/20、C 5/20，是记录覆盖度，不是成员能力或竞赛评分。

## 3. 三人任务分配与验收

### A｜真实材料接入、证据定位、差距诊断
主责样本：嘉农芯生、滴水润疆、菌润乡土。

1. 为每份原件建立 manifest：文件名、可访问来源、版本/hash、赛事年份/赛道、官方目标标准、隐私/脱敏状态。只在 D 盘且 Agent 当前读不到的，标 `BLOCKED`。
2. 每个样本至少人工核验 3 条 gap；每条包括当前作品 locator、当前证据、目标/参考来源 locator、适用理由和事实/推断/unknown 分类。
3. 嘉农芯生：核对专利状态与“1200 株/小时”“96% 成活率”对应的原始试验批次、样本、日期和计算口径。
4. 滴水润疆：核对同一批次投放、回收、称重、质检和成本的追溯链。
5. 菌润乡土：验证旧 DOC 的可执行转换/解析路径；订单、批次、损耗、复购与结算不混用。
6. 测试图片 PPT/PDF、表格跨页、旧 DOC、ZIP、大文件和缺失/冲突数字。逐项记解析覆盖与未解析位置。
7. 每个失败都要有复现步骤、预期/实际、根因、修改文件/函数、commit、修复前后同输入结果。
8. **验收门**：无真实 locator/source_refs 的 gap 不得交给 B 生成 production action card；证据不足必须 unknown/blocked。

### B｜私人定制行动卡、盲执行、真实 V2
主责样本：文玩玉米、本草云联、湘匠织秀/湘秀未来。

1. 只用真实 V1 与 A 已核验 gap 生成行动卡；每一步包含 project/version/target_locator/action/reason/expected_change/output/self_check/failure_next/capability_basis/source_refs。
2. 对比不同项目的第一步。若都只是“加强调研、优化方案、完善 PPT”，判私人定制失败。
3. 缺少 grounded `micro_steps` 时必须 `blocked/unscheduled`，不能回退通用三步。
4. 将行动卡交给未参与诊断的人盲执行，不口头补充；记录 5 分钟内能否开始、耗时、求助次数、卡点原话和产物。
5. 文玩玉米：区分产量、售价、销售收入、成本、损耗和净收益的口径。
6. 本草云联：区分已实现、原型和规划；模拟/非临床数据必须显著标注。
7. 湘匠织秀：只选一款真实产品，核需求方、纹样来源/授权、报价、制作、质检、交付、结算；无真实需求方时首步是访谈，不是假造订单或堆功能。
8. 保存真实 V2 文件、版本/hash，由 A 或第三人按冻结原标准逐条复核。B 不得自评通过。
9. **验收门**：行动卡 + 盲执行日志 + 真实 V2 + 独立复核 + 修复回归缺一不可。

### C / 队长｜集成、状态恢复、独立总验收与创新证据
主责样本：数智助老/泉城护航、无界智泊；同时统筹全队。

1. 核验 PR #21/#22/#25/#35 当前状态、head/base、实际 runtime、main、部署版本和模型配置。分别记录 open/merged/deployed，不混为一谈。
2. 解决 `team_recovery.py` 同名文件职责冲突；按调用方和状态机比较，不整文件覆盖。
3. 数智助老：核验“15 分钟响应”“效率提升 65%”的基线、样本、履约记录和计算口径；缺证标 unknown/目标值。
4. 无界智泊：分开记录本项目授权/试点证据、第三方案例和模拟流程；复测预约、冲突、结算、退款。
5. 串起完整交接：A evidence-based gap → B 专属行动卡 → 非作者执行 → 真实 V2 → A/第三人独立复核 → B 只重排 fail/unknown → C 保存 trace 与状态证据。
6. 测中断恢复、跨会话项目确认、版本冲突、工具失败、重复无效策略、已完成项保护；两轮无产物后换法/求助/停止。
7. 首条真人闭环完成后，再招募 5–8 位同学做探索性对照：同一真实任务、相近时间预算、统一 rubric；记录首个产物耗时、回到原步骤比例、V2 得分、人工介入、负担和成本。小样本不外推。
8. **验收门**：至少一条真实 V1→V2→独立复核通过的完整链路；C 不得仅凭 A/B 自评宣布成功。

## 4. 下一步执行顺序（按依赖，禁止跳步）

### P0｜先让真实输入能跑
1. A 先确认本机原件能否被当前 runtime 读取；建立 manifest 和 3 条人工基准 gap。
2. C 同时确认当前运行分支、main、模型配置、PR 状态与部署版本；保存实际 commit/trace。
3. 对图片 PPT/PDF、旧 DOC、ZIP、大文件逐类复现读取问题；给出修复或可验证的转换/分块方案。
4. B 验证无 grounded micro_steps 时生产任务是否确实 blocked；若还能生成通用三步，先修并回归。
5. 解决 PR #21/#22 集成与同名恢复文件冲突；合并前后重跑相应工程回归。未合并不等于已上线。

### P1｜优先跑两个不同项目的真实私人定制闭环
首选数智助老与湘匠织秀（前提是原件和目标标准可访问）。这两个项目应当生成明显不同的首步：
- 数智助老：先做 claim-evidence 表，逐项核验“15 分钟响应/65%”的来源、基线、样本、时间窗、计算口径；缺证标 unknown。
- 湘匠织秀：先选一款产品，建立需求方、用途、预算、纹样来源/授权、报价、制作、质检、交付、结算的台账；缺真实需求方就先做访谈。
若 Agent 给两者相同通用计划，则记录为私人定制失败，修 planner/context/diagnosis 后用同输入复测。

### P2｜真人执行、复核、局部重排
- 另一位成员只看行动卡执行，产出真实 V2。
- 复核人使用冻结的原判据判 pass/fail/unknown，不因看见新版本就降低标准。
- 只有 fail/unknown 进入剩余项重排；completed/locked/in_progress/pending_review 不得被覆盖。
- 记录中断前后 project/version/locator/next action 是否一致。

### P3｜把失败变成回归资产
每次失败：冻结输入与标准 → 保存 trace → 分类根因（解析/检索/证据定位/计划/工具/状态/复核/部署）→ 修改实际代码/流程 → 同输入复测 → 相关回归 → 记录是否改善。模型或知识库改动后重新跑核心集。

### P4｜用户效果与创新判断
完成首条真人闭环后再做 5–8 人探索性对照。对两项主创新分别写支持证据、反例和未测项；结论只能是 GO / REVISE / STOP。没有对照数据，不得说“已证明优于通用助手”。

## 5. 状态标签与硬性证据等级

- `ENGINEERING_PASS`：工程/单元/集成规则通过。
- `SIMULATED_MODEL_PASS`：模拟数据或固定回复通过。
- `LIVE_MODEL_PASS`：当前真实模型配置运行成功，有输入/输出/工具 trace。
- `REAL_ARTIFACT_PASS`：真实作品诊断和行动卡按冻结判据合格。
- `HUMAN_LOOP_PASS`：非作者真实执行产出 V2，另一人独立复核通过。
- `BLOCKED`：缺原件、权限、模型配置、标准或依赖。
- `NOT_RUN`：没有实际运行记录。
- `FAIL`：运行后不满足预期。

这些等级不能互相替代；239 项工程测试通过不等于真实模型通过，更不等于真人闭环通过。

## 6. 每个真实项目必须留存的证据包

1. 原件 manifest（来源、版本/hash、标准、脱敏状态）。
2. 解析覆盖率与失败位置。
3. Agent 输入/输出、模型/代码版本、工具 trace、引用来源。
4. 3–5 条证据化 gap 与人工基准。
5. 项目专属 action card 与失败路径。
6. 非作者执行日志、耗时、求助次数、卡点原话。
7. 真实 V2 文件/版本/hash。
8. 独立复核表（按原标准逐项 pass/fail/unknown）。
9. 只重排剩余问题的记录。
10. 根因、代码/流程修改、commit、修复前后同输入结果与回归结果。
11. 创新假设判断（GO/REVISE/STOP）和证据限制。

## 7. 本轮成功定义

至少有一个真实项目完成：真实原件可访问 → Agent 定位真实差距 → 生成与项目匹配的第一步 → 非作者照卡执行 → 形成真实 V2 → 独立复核 → 只重排未通过项 → 修复 Agent 缺陷并同输入回归。中断接续另需实际验证。

在达到上述门槛前，准确结论是：**上岸鸭已有工程机制与差异化设计方向，但私人定制效果、真人闭环和国赛质量证据仍不完整。** 这不是否定创新，而是把创新从“我们认为有”变成“评委能现场复现、能检查证据”。
