仓库：`phucmanh146-dot/shangan-ya`  
基线：`captain/real-artifact-gap-review-20261024`  
本次工作分支：`captain/engineering-invocation-acceptance-20261025`  
关联：总调度文档、PR #42、Issue #7、PR #21/#22/#25/#35/#39。

> **本文件把“工程设计写在文档里”与“运行时真的调用工程”分开验收。** 代码、接口、工具、持久化或模型只在被真实执行、结果被下游消费且证据可复现时才算通过。PR 描述、架构图、静态页面、测试数量和 mock 成功都不能单独证明端到端能力。

## 1. 本轮目标：不是增加功能，而是证明调用链真实成立

上岸鸭面向第一次做竞赛、科研和创新实践项目的大学生。它要读取用户真实材料和目标，找到有证据的差距，把差距转成第一步不超过 5 分钟的微行动；执行中断后恢复到准确位置；用户产出 V2 后，按冻结的原标准独立复核，只重排未通过项。

工程链必须能在一次运行中证明：

`真实材料 → 解析/检索 → A证据诊断 → B行动规划 → 用户执行 → V2版本保存 → 独立复核 → 只重排剩余项`

同时，运行时需要有真实模型/工具调用、调用结果检查、状态持久化、失败路径、版本保护和可追溯日志。**某个环节没有真正接线时，状态必须是 `NOT_WIRED`、`NOT_RUN` 或 `BLOCKED`，不得用手工文案补成 PASS。**

## 3. 统一工程验收规则：每个“能力”必须证明被调用

每项功能提交时都必须提供以下六类证据：

1. **入口证据**：调用它的实际路由、命令、事件处理器或 orchestrator 函数名，以及代码路径/行号。
2. **调用证据**：测试或脱敏运行 trace 证明目标函数、工具或模型客户端确实被执行；只检查配置字段不算。
3. **结果消费证据**：目标返回结果被下游逻辑读取并影响输出/状态，而不是调用后丢弃、仍返回硬编码模板。
4. **负向证据**：依赖不可用、参数无效、超时、空结果、来源不足时，断言失败状态和用户可见的下一步。
5. **状态证据**：持久化前后状态快照；刷新/进程重启后恢复；版本冲突时旧成果不被覆盖。
6. **可复现证据**：commit SHA、输入文件版本/hash、命令、退出码、日志路径、预期/实际结果和复核人。

测试分三类标记，不可混记：
- `UNIT/MOCK`：验证分支逻辑或协议，不证明真实服务可用。
- `INTEGRATION`：真实模块间调用，外部依赖可使用受控测试服务，但必须标明。
- `LIVE/HUMAN`：真实模型、真实材料或真实用户运行，必须保存去敏证据。

如果代码中找不到调用点，先标 `NOT_WIRED`，由负责人补实现或确认不在本轮范围；不允许只把 PRD 写得更完整后标完成。

## 4. 必须验证的调用链

| 编号 | 调用链与具体检查 | 通过门槛 | 失败时状态/动作 |
|---|---|---|---|
| ENG-01 | 材料接入 → 文件解析器 → 解析结果/locator 被诊断模块消费 | 真实文件能读取；抽样段落、页码/表格位置能回原件核对；解析失败有明确错误 | `BLOCKED_SOURCE`；不允许生成伪造引用 |
| ENG-02 | 检索/参考库 → 检索工具 → 来源筛选 → 诊断引用 | 每个关键 gap 带原件位置和来源定位；资料不足时拒答或标 unknown | 缺引用的 gap 不可交给 B |
| ENG-03 | 总控 → A 诊断实际调用 → gap schema 校验 → 持久化 | gap 具备 artifact/version/hash、locator、证据、判据、事实/推断/unknown；空诊断不能通过 | `BLOCKED_DIAGNOSIS` |
| ENG-04 | 总控 → B planner 实际调用 → micro-step 校验 → 行动卡持久化 | 每一步有修改位置、动作、理由、产物、自检、耗时、依赖、失败下一步；与 gap_id 绑定 | `NOT_SCHEDULED`，不能用通用模板冒充 |
| ENG-05 | 调度器 → 读取真实容量/截止期/依赖 → 生成计划 → 用户确认采用 | 计划可解释；超容量和冲突显式显示；未确认的预览不覆盖已采用计划 | `BLOCKED_CAPACITY` 或 `PENDING_CONFIRMATION` |
| ENG-06 | 状态寄存器/SQLite → 保存当前步骤、尝试、版本、承诺和返回条件 → 重启后恢复 | 新进程/刷新后回到同项目同版本的原步骤，展示已完成、卡点和下一步 5 分钟动作 | `RECOVERY_FAIL`；保留数据库和日志排查 |
| ENG-07 | 模型客户端/工具调用 → 真实结果校验 → trace → 下游消费 | 真请求有模型 ID、耗时、结果摘要、状态码/错误码；无效配置不能伪成功或静默切 mock | `LIVE_MODEL_BLOCKED`；可明确切换离线模式，但必须标记模拟 |
| ENG-08 | 用户提交 V2 → 版本锁定 → A 独立复核 → review record | V2 不覆盖 V1；复核按冻结判据逐项 pass/fail/unknown，含证据位置和复核人 | `PENDING_REVIEW` 或 `REVIEW_BLOCKED` |
| ENG-09 | 复核结果 → B 只重排 fail/unknown → 版本差异与依赖重算 | pass/completed/locked 项保持不变；剩余项重排有原因和前后差异 | `DISPATCH_FAIL`，不得全量重置 |
| ENG-10 | 全流程 trace → 评测记录/试用 CSV → 指标计算 | 原始分母可追溯；缺失值不填 0 冒充；模拟和真人数据分表 | `EVAL_NOT_RUN` |

## 5. 三人执行调度：按依赖交接，不按文档章节各自写完

### 阶段 0 — 队长 C：先冻结工程基线（P0，先于 A/B）
交付：
- 当前工作分支、commit、工作区状态、PR base/head 和未提交改动记录。
- 当前目标分支下的文件/函数清单：A 诊断入口、B planner 入口、总控调用点、模型/工具客户端、SQLite 状态读写、复核与重排入口。
- 将每个入口映射到 ENG-01 至 ENG-10；缺少调用点的明确标 `NOT_WIRED`。
- 重新运行可复现的测试，并分开列出 UNIT/MOCK、INTEGRATION、LIVE/HUMAN 结果。

验收：队长提供代码路径/行号、命令和日志；不能只写“已有某功能”。基线不清或存在未保存修改时，停止改动并先保护工作区。

### 阶段 1 — A 同学：真实材料与证据诊断（P1）
交付：
- 两份获授权真实作品的冻结版本、版本号/hash、目标判据和可回查原件。
- 每份至少 3 条 grounded gap；字段含 `gap_id`、`artifact_id/version/hash`、`current_locator`、原文证据、`target_criterion/source_locator`、参考定位、事实/推断/unknown、影响和补证动作。
- 在系统中真实触发诊断调用，并证明结果来自当前材料和当前 commit；保留脱敏 trace 与诊断 JSON。
- 一份“无法判断/资料缺失”用例，确认系统会拒绝编造并阻断行动规划。

验收门：队长随机抽查至少 3 条 gap，必须从定位字段回到原件；来源不支持结论、locator 不存在、或模型总结代替原文时退回。A 未过门，B 不开始正式编卡。

### 阶段 2 — B 同学：由 gap 驱动行动卡和排程（P2）
交付：
- 仅消费 A 已验收的 `gap_id`；每个 micro-step 绑定输入版本、目标位置、动作、理由、预期变化、产物、自检、失败下一步、能力依据、来源、负责人、依赖、预计/实际耗时。
- 在系统中真实调用 planner，并证明输出进入计划/状态存储，而非仅打印模板。
- 至少两类项目的行动卡在首步、交付物和验收方式上有材料驱动的实质差异。
- 容量不足、截止期冲突、缺 gap、模型失败四类负向测试。

验收门：找一位没参与编卡的同学，只给他材料与行动卡；其无需口头解释就能开始，并在第一步 5 分钟内留下可检查的小产物。若只得到“继续完善/优化一下”等泛化建议，退回。

### 阶段 3 — 队长 C 集成：工具/模型调用与恢复（P3）
交付：
- 实际调用图：入口 → orchestrator → A/B 模块 → 工具/模型 → 结果校验 → 持久化 → 下游消费。
- 至少一次真实模型对话、一次真实材料定位；配置未就绪则保持 `LIVE_MODEL_PASS=NOT_RUN/BLOCKED`，不能用 mock 代替。
- 进程重启/浏览器刷新后恢复同项目同版本、准确步骤和下一动作。
- 超时、无效模型 ID、检索为空、工具异常、重复提交、版本冲突测试；错误状态明确，已有产物不丢。
- 当前 commit 的 provenance/测试报告，不沿用旧版本哈希。

验收门：ENG-01 至 ENG-10 的代码调用点与证据逐项对上；没有实际调用的模块不能标 PASS。受控夹具仅计入工程门。

### 阶段 4 — 非作者执行与 A 独立复核（P4）
交付：
- 冻结 V1、原始判据、行动卡版本、执行者身份角色（不必公开个人隐私）、实际耗时、卡点、求助次数、真实 V2、diff/hash。
- A 不看作者自评，按原判据逐项复核 `PASS/FAIL/UNKNOWN`，附 V2 位置和理由。
- B 只对 `FAIL/UNKNOWN` 重排；保存重排前后计划快照，并证明 `PASS/completed/locked` 项不变。
- 队长检查完整 trace、版本关系和证据链。

验收门：至少一个真实项目完整走通 V1→gap→行动卡→非作者执行→V2→独立复核→只重排剩余项。缺任何关键产物均为 `HUMAN_LOOP_PASS=NOT_RUN`。

### 阶段 5 — 用户试用与对照（P5）
队长组织 5–8 位同学试用；资源不足时先完成 1 条完整闭环，但不得把单例写成普遍结论。尽可能同类任务、同一判据，对照上岸鸭与普通助手，记录：
1. 中断后回到原步骤的比例；
2. 恢复后到实际动手的时间；
3. 最终产物按同一标准的得分；
4. 用户自评负担。
保存原始记录、分母、缺失数据、同意/隐私处理和指标计算方式。未执行时标 `NOT_RUN`，不编造效果数字。

## 6. 总调度阻断规则

以下任一项成立，都不允许宣布“工程闭环通过”：
- 只有文档/架构图，没有真实代码调用点；
- 测试只 mock 目标函数，却把结果写成真实模型/工具通过；
- 工具返回值未被下游使用，输出仍由硬编码模板生成；
- 证据没有原件 locator，或检索失败仍生成肯定结论；
- 重启后找不到原项目/版本/步骤，或已完成项被重排覆盖；
- V2 由编卡者自行宣布通过，没有独立复核；
- 测试结果没有绑定 commit、输入版本和实际日志；
- 把受控测试数、模型连通、真人收益、获奖准备混为一个“通过率”。

## 8. 当前执行顺序（不得跳步）

1. **C：** 锁定当前 commit 与工作区，盘点真实调用点，补齐 ENG-01—ENG-10 映射。
2. **A：** 冻结两份真实作品并交付有 locator 的 gap；C 抽查通过后才交 B。
3. **B：** 对已通过 gap 生成行动卡，验证 planner 真实调用、持久化与个性化差异。
4. **C：** 集成测试模型/工具、异常、状态恢复、版本保护；模型未配置时明确阻断。
5. **非作者执行 + A：** 产生真实 V2 并独立复核。
6. **B：** 只重排 fail/unknown 项；C 检查状态不变量。
7. **C + 全队：** 组织真人试用、同条件对照，保存原始指标。
8. **队长最终审批：** 按每道门分别签收；缺证即不放行。
