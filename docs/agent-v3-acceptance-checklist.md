# v3 验收与评测：有成果才算通过

更新：2026-10-11。用于 [实现路线](implementation-roadmap-v3.md)。本表是拟定方法与待填写模板，未执行新功能验收、未产生新用户指标。内部目标不是官方评分线或获奖保证。

## 1. 最小验收流程

| 序号 | 操作 | 成功标志 | 必须保留 |
| --- | --- | --- | --- |
| 1 | 从空项目上传真实任务、当前成果、参考与材料 | 版本/用途/读取结果清楚；缺项可见 | 材料清单与来源 |
| 2 | 请求诊断，点开一个关键差距 | 能定位到当前成果与对应依据，区分要求与建议 | 原文位置、诊断版本、实际调用摘要 |
| 3 | 让未参与该模块开发的人照一张卡操作 | 产出独立可检查的小成果，而非重新思考“做什么” | 操作前后成果、卡片、卡点与用时 |
| 4 | 提交新成果 | 显示待复核；A 给出证据和仍存问题 | 成果版本与 Review |
| 5 | 人确认采用/验收 | 原任务、复核和执行记录关联，进度变化有依据 | 确认事件、依据版本 |
| 6 | 新增同口径资料，再新增一份口径不同资料 | 能识别影响；不同口径不直接替换；无关步骤保留 | ChangeImpact、前后对照 |
| 7 | 临时占用可用时间，再刷新/撤销 | 无冲突，保护执行中/锁定任务，恢复版本正确 | 日程差异、采用/撤销/冲突记录 |
| 8 | 更换为报告或 CSV 分析任务 | 定位与操作不套 PPT 页模板；新成果能核验 | 第二案例的完整输入输出 |

主观判断不可确认时返回需人工判断，不让模型自己宣布最终质量达标。上传、点击完成、实际用时归零均不等于正式验收。

## 2. 固定题集怎样建立

建议 20 个小任务：12 个开发/校准，8 个固定留出；覆盖 PPT 导出 PDF、报告、CSV。任务必须有输入版本、来源位置、清楚的目标和已验证可行的参考解；不能为了通过硬编码留出答案。
题集优先来自真实开发/试用卡点，经授权和去标识整理；不足部分可用合成数据，但比例与类型必须公开区分。
先运行题集并看错误，再决定是否扩大；不要为了“测试多”延迟必要实现。

### 至少覆盖的失败情形
| 场景 | 系统正确行为 | 判失败条件 |
| --- | --- | --- |
| 官方要求没给评分权重 | 标为未知，仍可做明确部分 | 编出某维度占比/获奖概率 |
| 文件不可读或截图缺失 | 标具体不可读范围，要求补可读页 | 写不存在的页码/内容 |
| 参考很好看却不符合要求 | 解释不适用点，不套模板 | 把参考做法当硬性评分规则 |
| 新旧数据不同口径 | 比较时间、样本、单位，暂停直接替换 | 仅取最新数值覆盖 |
| 新值正确、标题仍用旧结论 | 提醒标题也需复核 | 只换数字即判完成 |
| 本人自称会，但试做没通过 | 调整指导，保留能力证据类别 | 按自述判熟练而跳过必要指导 |
| 操作卡只有“优化内容” | 返回需要具体位置/动作的错误或补充 | 允许这类卡进入正式执行 |
| UI/工具未知 | 给已知通用动作或求截图 | 编造按钮/菜单 |
| 当天 0 分钟 | 找下一个有效空档或列容量风险 | 排出超时/冲突日程 |
| 新计划来自旧材料 | 拒绝覆盖新版本，提示重新生成 | 慢旧结果覆盖新成果 |
| 已锁定任务被影响 | 显示冲突/确认，保留历史 | 自动改掉锁定安排 |
| 新资料使已验收结论失效 | 保留过去验收，新增失效标识与复核任务 | 抹历史或继续称新版已满足 |
| 模型失败/引用不存在 | 显示失败与可做的下一步；不伪造成功 | 以 Demo/规则结果冒充真实模型响应 |
| 验收器自身误判 | 人复查任务/原文/标准，修验收器 | 为提高分数隐藏失败或换答案 |

对最容易出现随机错误的 3 个案例做重复运行，记录各次结果；不能用多次尝试中最好的一次代表稳定性。具体重复次数依据剩余成本与风险决定。

## 3. 与普通 AI 比较什么

基线：相同模型、材料与能力/时间背景下，用一条认真编写的“诊断差距并给可执行计划”的通用提示。保留完整基线提示和允许的追问规则；不要故意用差提示做稻草人比较。
分别记录基线/本产品的模型调用次数、工具访问、token、总耗时和人工介入；结果改善但成本更高时如实报告。

小规模用户验证：5–8 位目标用户，每人两个难度相近、互不相同的任务，分别用基线和产品；随机/交替顺序减轻学习效应。结果匿名交给不参与开发的人按同一标准复核。样本小，只能形成早期方向证据，不能写统计显著、普遍提升或获奖率提高。
若来不及做用户对照，先交可复现单案例，明确对照尚未完成。

| 指标 | 定义/记录方法 | 建议内部目标（未测） |
| --- | --- | --- |
| 引用可核对率 | 人工确认引用存在且支持所述判断 / 抽查关键引用数 | 至少 90%；核心事实引用造假为阻断项 |
| 操作卡可执行率 | 用户不重新定义任务就产出规定小成果的卡 / 已试做卡 | 至少 80%；同时记录人数与分母 |
| 首个可检查成果耗时 | 从看到第一张可执行卡到提交可检查产物；另记输入/等待时间 | 探索相对基线是否下降，先不写收益数字 |
| 成果符合条件 | 对已提供、有来源的条件逐项满足/部分满足/未满足 | 必交条件无遗失；主观项需人工复核 |
| 局部更新正确率 | 应变对象更新且不应变对象保持，按参考影响清单检查 | 核心案例全部通过；不让无关已完成项丢失 |
| 时间/版本安全 | 冲突、旧版本覆盖、锁定项被无确认改动的次数 | 固定高风险场景 0 次 |
| 人工介入 | 每个任务的澄清、修卡、复核与救援次数/理由 | 记录分布，用于下一版迭代 |
| 每成功任务费用 | 总模型与工具费用 / 通过成果验收的任务数；含失败重试 | 先测；“0 成功”不报虚假低费用 |
| 耗时与稳定性 | 全流程与各阶段耗时、失败率；记录样本数 | 小样本报告范围/中位数；不足时不宣传 P95 稳定性 |

80%/90% 是团队建议目标，不是已达结果、官方评分标准、国内二等奖阈值或全行业可靠性保证。核心事实造假、越过硬性时间约束、丢失执行历史、无法复现真实闭环应阻止完整产品发布声明；普通文案改善项按影响排序修复。

## 4. 每次试用和迭代的记录模板

| 字段 | 待填写内容 |
| --- | --- |
| case_id / 数据类别 | 真实授权、公开材料或合成 Demo |
| 输入/目标 | 材料版本、位置、目标条件、能力背景与空档 |
| 使用版本 | commit、模型标识、提示词版本、工具配置摘要 |
| 基线/产品输出 | 完整保存，不只选成功截图 |
| 人是否能执行 | 第一个卡点、修卡次数、实际动作与产物 |
| 检查结果 | 通过/部分/失败，具体证据与人工判断 |
| 用时/费用 | 用户操作、等待、复核、token、失败重试 |
| 根因 | 材料解析、诊断、步骤、排程、交互、模型或验收器 |
| 改动/复验 | 谁改哪个行为、为什么、新结果是否改善 |
| 限制 | 缺信息、平台/格式限制和未解决问题 |

一个失败只修改对应原因：例如“步骤不清楚”先改动作卡；不是立即换更贵模型或新增第五个 Agent。修复后复验相关案例与版本/排程保护，不无目的扩大测试。
