# 实现路线 v3：把模糊竞赛任务变成可检查的成果

更新：2026-10-11（Asia/Shanghai）。仓库 phucmanh146-dot/shangan-ya。
这是基于现有代码和公开案例形成的开发提案。本文新增的诊断、精细指导、成果复核和评测要求尚未因文档提交而实现。日期为有条件的内部建议，不代表三人已承诺；获奖和薪资都不是产品可保证的结果。

相关文档：[v2 完整需求](team-tasks-v2.md)、[获奖案例与岗位研究](agent-award-readiness-research.md)、[验收与评测表](agent-v3-acceptance-checklist.md)。

## 1. 一句话产品定义和首批用户

上岸鸭比赛任务落地 Agent：把学生领到的模糊竞赛任务，结合规则、当前成果、目标参考、本人理解和实际空档，转成“在什么位置、为什么改、下一步做什么、改到什么程度”，收回新成果核验后继续推进。

首批用户：已经领到具体分工、手里有一版成果，但不知道离目标差在哪里的学生竞赛成员；先招募 5–8 位参与试用。这是验证计划，当前并无这批用户的试用结论。
首个任务用真实比赛的一个交付物与一个关键差距。PPT 可作为主案例；第二个案例用调研报告或 CSV 数据分析成果，检验是否套用了固定 PPT 模板。

目标必须分四层：
| 层 | 来源 | 如何使用 |
| --- | --- | --- |
| 比赛硬性要求 | 所选赛道最新官方通知/附件与提交页 | 不得为赶时间自行删掉；保留原文位置和版本 |
| 用户目标 | 本人确认的目标、理想效果 | 转成能检查的交付条件；“获奖”继续是外部愿望 |
| 参考做法 | 合法提供/公开可引用的作品 | 分析具体做法与适用条件，不能把它当本赛评分标准 |
| 系统建议 | 诊断与操作建议 | 标明推断、依据和不确定项，允许用户修改 |

“争取国家级二等奖”落到开发侧的目标是：符合参赛要求，有能独立复现的核心闭环，有真实用户与成果改进证据，能解释相对现有工具的价值。不能输出“完成 85% 就能拿二等奖”或自动预测获奖概率。

## 3. 第一版范围和顺序

### P0：提交前最小闭环
1. 接收规则、原任务、当前成果、参考成果、新资料、本人理解、时间与 DDL；缺一项要显示缺失如何影响判断。
2. 文件版本与真实位置可追溯。先支持可提取文本的 PDF、Markdown/TXT 和 CSV；PPT 用导出的 PDF 做阅读入口。PDF 中复杂图形或扫描文本没有可靠解析时显示局部未知，允许提交对应页截图补充。
3. 产生一个关键差距，区分要求与参考，说明理由、适用条件和证据。
4. 生成一张能执行的操作卡，完成该卡会留下一项可核验的小成果。
5. 上传新成果，对照原差距复核；显示满足、部分满足、未满足和人工判断需要。
6. 基于本人可用时间排程；临时占用和新资料只更新受影响部分；确认和撤销有记录。
7. 从空项目跑通一次真实输入、真实模型、真实成果回传；第二种交付物复验。

可阅读但不可编辑的格式要在入口直接说明。首版精细文件修改由用户按卡执行，系统生成修改建议、可复制的内容和对照结果；“导出建议”不能宣传成“已修改原 PPTX”。具体文件自动编辑作为 P1 适配器扩展。

### P1：核心通过后再做
- PPTX/图像的对象级解析与编辑、图表计算核验、更多格式的精确定位。
- 针对用户试做的指导深度调整，并用对照试验验证是否减少卡点。
- 增强新旧证据的影响分析与局部复核，积累更多真实任务与长期用户。
- 自动生成可下载的新文档/数据文件时，先预览差异，输出新版本并验证，不覆盖原件。
- 按所选赛道平台接入部署、身份与数据隔离；公开服务需要鉴权、上传限制、删除机制和服务端密钥。

### P2：后续验证价值再投入
全网自动收集所有比赛、全面远程控制所有软件、自训练大模型、所有领域通用能力评分、职业/生活/竞赛全能工作台。它们的价值与成本尚未验证，不纳入本次关键路径。

## 4. 输入、输出和运行链路

队长先创建项目，A 和 B 接到相同 project_id，不能把互不关联的几个聊天页称为已联调。

| 步骤 | 必需输入 | 系统输出 | 缺信息时的下一步 |
| --- | --- | --- | --- |
| 收材料 | 任务、材料用途、文件版本、目标、DDL/空档 | 材料清单与读取状态 | 指出具体缺项，先做可确定部分 |
| 定目标 | 官方要求与用户目标 | 交付物清单、检查条件与依据 | 不编造评分权重；保留待核验 |
| 看现状与参考 | 当前成果、参考位置与有关证据 | 现状—目标—差距表；参考适用性说明 | 参考不适用则解释并不迁移做法 |
| 看本人理解 | 已有成果、自己的解释、一个小样试做 | 已验证/自述/未验证与指导需要 | 不凭一句“我会”打能力分 |
| 给下一步 | 有效差距、定位与能力证据 | 单一动作、输出、检查、失败下一步 | 给补证据/试做卡，不猜按钮与内容 |
| 安排时间 | 依赖、估时范围、真实空档与占用 | 今天可做、未排入、缓冲与原因 | 排不下就列取舍，不延长官方 DDL |
| 收成果复核 | 新成果版本、原差距、检查条件 | 满足状态、具体证据、剩余问题 | 不可读即待复核，不勾完成 |
| 局部更新 | 新材料或复核结果、当前执行版本 | 受影响卡片与日程差异 | 保护任务冲突交用户确认 |

系统不能只串固定提示词然后宣称完全自主。首版采用可观察的工作流；在需要判断时由模型选择“读取相关证据、对比材料、请求补充、生成下一步、复核成果”等受限动作。真正调用了哪些工具、为什么停止、得到什么结果要留记录。排程冲突、版本一致性、引用是否存在由代码检查；内容质量由模型建议与人工复核共同确认。

建议限制：单次诊断/复核最多两轮补证据；超出后返回明确缺项，避免无限生成。重试次数、费用与耗时阈值放配置，先记录真实运行数据再定正式值。

## 5. 数据和接口怎样实现

### 保持现有字段兼容
保留 p1-contract.md 的 schema_version 0.1、gap_id、task_id、诊断与计划版本、原任务状态。新增内容置于可选细化字段；只有适配器与校验器都通过后才启用新流程。不要直接修改版本号并假设所有旧消费者已经支持。

下列是新增设计字段，当前接口尚不保证校验：
| 对象 | 新内容 | 责任 |
| --- | --- | --- |
| 材料记录 | 用途、版本、内容摘要值、读取状态、真实定位、来源日期 | 队长收版本，A 提解析定位 |
| 目标条件 | criterion_id、类型、来源位置、检查方法、是否硬性 | A 提取，用户确认个人目标 |
| 差距 | current_locator、criterion_refs、reason、applicability、能力证据、未知项 | A |
| 参考拆解 | 位置、具体做法、解决的问题、依据、适用边界 | A；原因推断明确标注 |
| 操作卡 | micro_steps、输入版本、位置、单一动作、输出、自检、失败下一步 | B |
| 复核记录 | 原 gap、成果版本、满足状态、证据、剩余问题、人工判断项 | A |
| 影响记录 | 改变的证据与结论、影响 gap/step、理由、需重新复核的已验收对象 | A→B→队长 |
| 执行事件 | 请求、模型/工具结果摘要、基于哪个版本、采用/撤销/复核 | 队长 |

定位应允许 PDF 页/文本段、报告段落、CSV 行列、以后扩展 PPT 对象或代码函数。没有可靠位置，填 unknown 和原因；不能给模型自由编造页码。

现有服务面向本机、带 Host/Origin 限制；不可只改监听地址就当公开多用户服务。若赛道要求指定平台，把模块输入输出接入平台节点并保留可复现版本，不以本地网页替代平台要求。

### 模型和规则的分工
- 模型：理解模糊任务、分析参考适用性、提出差距和具体改法、解释反馈。
- 程序：确保材料与版本真实存在、定位合法、数值/单位可比、引用关联有效、依赖无环、时间不重叠、旧结果不能覆盖新结果。
- 人：确认目标与取舍、提供真实成果、处理不确定的质量判断、确认正式验收。
- 对小材料先按位置检索/过滤；只有材料规模产生实际检索需求时再引入向量库。RAG 或三 Agent 的数量本身不作为创新证据。
- 不把“两模型同意”当真实性证明；事实必须回到来源或计算结果。

## 6. 把用户举的 PPT 例子拆到可执行程度

以下全部是构造样例，文件、页码、数字与时间不代表用户已上传的真实材料或比赛要求。

假设输入：draft-v1.pdf 第 4 页称“试用者 70% 愿意推荐”；old.csv 对应 7/10；new.csv 是 18/30=60%，来自相同问题和统计口径；参考 PDF 第 6 页展示样本量、调查时间、数据来源。用户目标是“答辩时能解释数字，并使页面结论与最新有效数据一致”。

1. A 定位旧结论与数据；核对两个调查的时间、样本范围、问题措辞和单位。若口径不同，先保留两组数据并说明差异，不能执行替换。
2. A 拆参考：在图表旁显示样本量和日期可以让读者理解结论的范围；这是分析理由，并非已证明的获奖原因。参考行业不同的内容不迁移。
3. A 让成员说明如何计算 18/30、这组样本能支持什么结论；不会计算时，由 B 先给一个最小练习。
4. B 给以下动作链，每一步有独立成果，而非只写“优化第 4 页”。

| 小步 | 单一动作 | 为什么做 | 留下什么 | 如何检查/失败处理 |
| --- | --- | --- | --- | --- |
| 核对 | 在核对记录里填入两份数据的来源、日期、样本和问句 | 防止把不同口径当更新 | 一行可追溯核对记录 | 不一致则回 A 澄清，不改数字 |
| 计算 | 计算 18÷30，记录分子、分母与 60% | 让结论可复算 | 计算记录 | 算错就示范一次，再让本人试做 |
| 更新图表 | 在已确认的源演示文件第 4 页，把该图表对应值换成 60%，另存 v2 | 使图表与有效数据一致 | 源文件新版本/对应页截图 | 软件/对象未知先请求截图，不猜菜单 |
| 更新标题 | 将标题改为只描述本次样本支持的结论 | 旧标题可能因新值失效 | 新标题与理由 | 不得扩大到所有用户 |
| 补证据 | 在对应页附 n=30、调查日期和来源编号 | 能解释数字的范围 | 带来源说明的页面 | 日期未知写待补充，不能编造 |
| 复核 | 导出对应页并提交新成果 | 核验修改而非相信勾选 | draft-v2.pdf 与版本记录 | A 查数字、标题、来源；未过则返回具体位置 |

第一版对导出的 PDF 提建议，源演示文件由用户修改；文件名与位置在真实案例里从上传结果取得。最终目标不能只变成“标题改完”，而是该目标条件有新成果支持。

非 PPT 复验：调研报告的某段结论引用同一数据。系统应定位到报告段落、给出数字与措辞修改卡，复核该段与数据的对应关系，不要求不存在的“第 4 页图表”。

B 现在可以先做 B1、用标 Demo 的 Diagnosis 做 B2 原型、准备动作可用性测试；A 的真实诊断到来后替换输入并重新验。这样可减少等待，但不能据 mock 结果宣布与 A 已打通。

建议工程量仅用于容量检查：A 12–20 小时，B 12–18 小时，队长 14–22 小时，三人联合试用与整理 6–10 人时，合计约 44–70 人时。这是复用现有代码、熟悉项目、有可读材料和可用模型条件下的初始估计；复杂解析、平台迁移或环境修复另计。先用第一张真实卡校准，再锁定内部承诺。

降级顺序：

## 9. 怎么证明值得参赛和成为产品作品集

具体指标、失败场景和记录模板见 [验收表](agent-v3-acceptance-checklist.md)。
对外展示应回答：
- 谁遇到什么具体问题，原来怎样完成、在哪一步卡住？
- 相同材料和时间下，本产品在哪个可观察结果上优于普通一次性提示？
- 具体新材料改变了什么，为什么只改这些地方？
- 用户按一张卡真的交出什么，复核发现什么、下一轮如何调整？
- 哪些是规则保障、哪些依赖模型、哪些需要人判断，成本与失败怎样处理？
- 本人负责哪些决策和交付，有哪些证据能说明掌握了对应能力？

B 的个人作品集交付：操作卡从 v1 到 v2 的改进原因；一次用户卡点与修复；对照方法与真实指标；一项范围取舍及理由；可复现演示与模块代码。成员本人另做一次无辅助讲解或小修改，证明理解，不能把 AI 写出的所有内容算成本人独立能力。
