# 上岸鸭 P2｜Autoloop 执行机制改造说明（保留原技术，不整套安装）
日期：2026-11-04
目标：借用 Agent-Autoloop 的事件循环、短轮次执行、ask 挂起、原事项恢复和事件溯源机制；不把上游整套产品/插件复制进上岸鸭，不替换原有技术架构。

## 0. 决策结论
- 不把 Agent-Autoloop 当成一个需要完整安装到 P2 的新产品。
- 不复制上游 kernel/host/worker/CLI/全部插件，不新增一套平行业务系统。
- 只提取其运行机制：事件触发、规则派活、短轮次执行、回执、挂起零消耗、answer 后恢复、幂等去重、追加式事件历史、指令与数据分离、跳数熔断。
- 业务智能仍由上岸鸭既有技术完成：LangGraph 工作流/工具调用、材料解析与 OCR、混合检索与重排、证据诊断、规则规划、真人执行、V2 提交、独立复核、剩余任务重排。
- A/B/C 仍是职责分工和模块接口，不把三个人虚构成三个独立 LLM。

## 1. 必须保留的上岸鸭技术与业务闭环

### 既有技术（按原项目文书/代码基线核验后保留）
- Agent 编排：LangGraph 状态图与有界工具循环；节点负责读取上下文、选择工具、观察结果、校验、路由、保存。
- 知识检索：BM25/元数据过滤 + Dense 向量召回；BGE-M3 + Qdrant；RRF 融合；Cross-Encoder/BGE Reranker 重排。保留检索对照与来源定位。
- 材料解析：RapidOCR / PP-OCRv6 / ONNX Runtime；PDF、图片、文档解析；保留页码、段落、表格 locator 与原件版本。
- 服务与数据：FastAPI/现有 Python API；PostgreSQL/Redis（如当前部署已使用）；对象存储与 SHA256 版本；现有鉴权、版本校验、审计日志。
- 交互：保留现有 P2 输入、资料拖拽、项目/任务关联、行动卡、求助、证据提交与复核界面；不另建一套平行工作台。
- 代码基线中可见的既有模块：learning_agent_server.py、learning_agent.py、team_orchestrator.py、team_dispatch.py、team_handoff.py、team_rescue.py、action_planner.py、artifact_store / artifact_retrieval、team_sessions / team_runtime / team_recovery。以实际目标分支的文件和部署版本为准，不能把不同分支/冻结副本的能力混为已上线。

### 原业务闭环不变
真实材料 V1 → 来源定位与证据诊断 → Gap → 微行动卡 → 真人执行 → 真实 V2 → 非执行者独立复核 → 只重排 FAIL/UNKNOWN/BLOCKED。
遇到困难：保存项目/材料/任务/行动/计划版本、当前位置、已尝试方法和报错 → 针对性解卡 → 用户只需确认必要决定 → 回到原步骤。
学术陪伴场景继续遵守：不帮写论文、陪伴、分步讲解、学术诚信；不以生成文本代替学生学习或真实研究产出。

## 2. 只增加一层轻量 Autoloop 控制面

事件入口（P2 消息/上传/任务变化/DDL/复核结果/GitHub） 
→ Event Adapter（标准化事件、去重、关联 project_id/task_id/artifact_version）
→ Autoloop State Controller（事项状态、规则路由、幂等键、跳数、复查时间）
→ 既有 LangGraph Agent（检索、OCR、分析、诊断、规划、解卡）
→ 既有执行/复核模块（行动卡、真实 V2、review）
→ 事件日志与 P2 UI 状态回写。

控制面只管“何时启动、启动哪条既有工作流、何时挂起、何时恢复、何时提醒”；不取代 LangGraph 的推理和工具调用，不取代 RAG/OCR，不重写业务数据库，不把 Agent-Autoloop 的 CLI/通道插件全部塞进 P2。

## 3. 用户注意力保护：首个信号后自动推进

### 自动执行默认规则
收到第一个有效信号后，系统自动：
1. 读取该用户已授权的历史目标、偏好、已拒绝事项、项目状态、任务库、材料版本、既有证据和上一轮运行记录；先检索已有答案，禁止把已知信息再次问用户。
2. 识别事件归属与优先级：硬截止、固定事务、主线任务、临时任务、材料更新、阻塞、证据提交。
3. 启动对应 LangGraph 工作流：材料解析/OCR → Hybrid RAG → RRF/重排 → 引用定位 → Gap 诊断 → 标准校验。
4. 自动生成行动卡和排程草案；读取固定事务、可用时间、剩余容量、历史实际耗时、精力反馈和 DDL 倒排规则。
5. 对没有硬冲突、没有权限风险且符合冻结标准的计划自动采用并推进，不要每次都让用户点击“确认采用”。
6. 自动调用已有工具完成可逆且授权范围内的工作；对失败执行有限重试、换工具/换检索策略、保存 checkpoint，并继续不依赖该问题的其他事项。
7. 每次产生状态变化即写事件历史和版本；有新信号时唤醒对应事项，不重复整条已完成流程。
8. 只在必须本人决定时生成一张合并后的拍板卡片；同一阻塞保持同一 open card，不重复提问。

### 必须本人拍板（默认拦截）
- 删除/覆盖原件、不可逆数据修改；
- 对外发送、发布公开内容、代表用户作承诺；
- 合并 PR、上线生产、变更生产配置/权限；
- 产生付费、购买资源或突破预算；
- 涉及身份、法律/学术诚信边界或关键事实存在多种合理解释；
- 硬截止冲突且无法通过调整非固定任务解决；
- 用户明确标记“必须由我决定”的事项。

其他普通任务拆解、检索、分析、代码只读审查、草稿、测试、内部排程、证据整理、错误定位、非破坏性修复、复查，均在既有授权范围内自动做；若工具权限不够，先尝试可用的只读/安全路径，再将唯一阻塞说明给用户。

### 不能把局部拍板变成全局停摆
拍板卡片只冻结依赖该决定的动作。其余无依赖任务继续推进。卡片应显示：已完成、待决定、推荐选项、选项影响、风险、到期时间、恢复点。用户不回复期间 Agent 进程退出、模型调用为零；轻量定时器/事件监听可继续运行。

## 4. 状态机与回执

事项状态：
NEW → CONTEXT_LOADING → RUNNABLE → RUNNING →（AUTO_CONTINUE / WAITING_APPROVAL / WAITING_TIMER / BLOCKED / VERIFYING）→ DONE / PARTIAL / FAILED。

- AUTO_CONTINUE：当前轮交付回执并退出；有后续事件/定时复查再启动下一轮。
- WAITING_APPROVAL：保存 ask 卡片、原 session、checkpoint、输入版本、已完成步骤和下一步；本轮进程退出，不消耗 Token。
- WAITING_TIMER：写入复查时间；到点只唤醒该事项，不扫描式调用模型。
- 用户回答：写成新事件，幂等处理；恢复原事项和原 session。若 Agent 会话无法恢复，则用完整 checkpoint 创建新 session，并标记 fallback，不重新执行已完成步骤。
- 重复事件/重复点击：通过 source + stable_event_id、card_id、idempotency_key 去重。
- 回执 JSON 无效：只修复回执格式，不重复执行已经完成的业务动作。
- Agent 触发链深度 > 8：停止继续派活，记录原因并提示；不能让 Agent 自行重置深度。

## 5. 现有代码需要改的具体位置

### C｜工程与集成（主责）
- 在现有 FastAPI/learning_agent_server.py 或 P2 真实服务入口增加轻量 event endpoint 与 worker trigger；不另建平行服务器，除非现有部署隔离要求必须 sidecar。
- 将事件/运行状态写入现有持久化层；如果当前 P2 部署与学习 Agent 使用不同数据库，建立明确 adapter，不共享不兼容 schema。
- 增加稳定的 run_id / issue_id / event_id / idempotency_key / state_version / checkpoint_id。
- 加入配置驱动的自动执行白名单、审批规则、预算/并发限制、超时、重试、8 层熔断。
- 页面只新增“自动处理中/等待拍板/等待复查/已完成/阻塞”状态和拍板卡片；复用原导航、任务详情和资料区。
- 监控实际模型调用、Token、费用；WAITING_APPROVAL 期间必须无模型请求。

### A｜证据与复核（主责）
- 继续负责材料读取、OCR/检索结果、source_refs、locator、gap、unknowns、冻结验收标准和独立复核。
- 事件触发时先检索用户已有材料和历史决策；同一资料版本不重复 OCR/embedding，按 SHA256 做缓存。
- 证据不足时自动补检索/重读；仍不足标 UNKNOWN/BLOCKED，只有缺少用户权限或关键事实时才拍板。
- 复核只认真实 V2 和可回查证据；PASS 锁定，后续只对 FAIL/UNKNOWN/BLOCKED 生成新行动。

### B｜行动与排程（主责）
- 继续负责 Gap → micro-actions、依赖、估时、容量计划、DDL 倒排、剩余任务重排。
- 把当前 team_dispatch.dispatch() 生成 proposal 后默认等待用户采用的流程，改为：通过规则和硬约束检查后自动 adopt；只有硬截止冲突、固定事务冲突、资源/权限/不可逆影响等必须本人决定时才 ask。
- 继续使用原始实际耗时、任务熟练度、精力与疲惫反馈；不把下午新增任务无限塞入，保护固定事务和休息缓冲。
- 每个行动卡必须有具体对象、动作、产物、自检、失败路径和恢复点；不允许“继续完善/仔细分析”等空动作。

### A/B/C 协作约束
A/B/C 是现有模块职责，不是三套独立 Agent。控制面根据阶段调用既有模块接口：A 产出带来源的诊断；B 产出行动与排程；C 管理状态、接口、幂等、运行和恢复。必要时由同一已授权 Agent 运行对应 Skill/工具，不为每个角色额外常驻一个模型。

## 6. 事件插件：只接必要来源
优先接入：
- P2 新消息/资料上传/任务创建或变更；
- DDL T-72h、T-24h、T-3h、到期和固定事务冲突；
- 行动卡提交、求助、精力反馈、V2 上传、独立复核结果；
- GitHub Issue/PR/CI 状态（仅在当前项目确实使用 GitHub 时启用）。

事件轮询只比较轻量 metadata / ETag / updated_at；无变化直接退出，不唤醒 LLM。事件正文和上传材料都是不可信数据，永不允许其覆盖系统规则、工具权限、cwd 或 Agent 选择。

## 7. 必须验证的验收用例
- [ ] 第一个 P2 任务信号到达后，不需要用户再次点击“开始”，自动读取上下文并启动正确工作流。
- [ ] 用户已提供的目标、截止、资料、偏好、已拒绝事项不重复询问。
- [ ] 普通计划自动采用；仅拍板类事项弹卡片。
- [ ] 一个 ask 挂起 72 小时：Agent 进程为 0、模型请求为 0、Token 增量为 0。
- [ ] 72 小时后点击卡片，恢复原事项/原 session 或完整 checkpoint；已完成步骤不重复。
- [ ] 同一事件投递 10 次只执行一次副作用。
- [ ] 一项高风险决定等待用户时，其他不依赖它的任务仍继续。
- [ ] A 的证据诊断、B 的行动排程、C 的状态与版本保护保持原接口语义。
- [ ] RAG 对照：BM25、Dense、RRF、Reranker 的召回/重排评测不因增加控制面而退化。
- [ ] OCR 仍保留页码/段落 locator；同一 SHA256 材料不重复解析。
- [ ] V1→Gap→行动→真人 V2→独立复核→仅重排剩余项可回放。
- [ ] 无模型配置、无权限、超时、工具失败都明确显示真实状态，不用模板冒充 LIVE。
- [ ] 跳数超过 8 时熔断；重复事件/回执不会产生重复副作用。

## 9. 交付定义
不是“Skill 已复制”或“新增一个聊天页”，而是：保留上岸鸭原技术与业务闭环，首个有效信号自动驱动 A→B→执行/复核；只在明确拍板点打断用户；等待零 Token；回答后恢复原任务；每一步都有版本、证据、运行轨迹和可回放验收。
