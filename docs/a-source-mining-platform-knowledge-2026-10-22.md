# A 同学｜跨平台 Agent 知识点提取与仓库落地批注（2026-10-22）

> 目的：不是再做一份竞品摘要，也不是把网页内容堆进“获奖作品墙”。请从百度、小红书、抖音、B站、人人都是产品经理、程序员鱼皮的公开资料中提取可复用的工程/产品方法，逐条映射到 shangan-ya 当前真实代码和真实作品差距。  
> 适用主线：真实材料 → A 有证据的 gap → B 具体 micro_steps → 人工执行 V2 → A 按原判据复核 → B 只重排 remaining issues。  
> 本文里的“方法提取”是团队分析，不等于这些平台的官方规则，也不证明上岸鸭已有对应能力。

## 1. 来源提取表：看具体知识点，不只记网站名

### K1｜百度千帆 / 文心智能体：工作流节点、显式分支和异常兜底

- 来源类型：官方产品文档。
- 来源定位：
  - 文心智能体《工作流介绍》：“工作流是什么”“有什么作用”“意图识别节点”“参数提取”“工作流支持版本切换”。
  - 文心智能体《常见问题—效果优化》：Q2“如何有效触发工作流”、Q4“大模型节点失败时如何保证其他节点稳定运行”。
  - 百度千帆《工作流Agent》：“全局跳转节点”“信息收集节点”。
- 可提取的方法：
  1. 复杂任务要把节点输入、输出和前置依赖写清楚，不要只靠一个总 Prompt 希望模型自动理解所有流程。
  2. 每种意图/失败类型明确进入哪个分支；工作流工具调用的触发条件和先后顺序要显式描述。
  3. 模型节点失败要有可验证的兜底输出或人工接管路径；不能把异常后的默认文字当成功结果。
  4. 工作流应版本化；测试时标记运行的是哪个版本。
- 对仓库的映射：
  - `learning-agent/team_orchestrator.py::validate_diagnosis`：A 的 gap 应区分 official requirement、user artifact、reference 和 suggestion，不能混为同一种证据。
  - 诊断/计划状态：材料不足停在诊断阶段；来源解析失败应转 `unknown/blocked`，不可自动补成“优化一下”。
  - 工具/节点结果：失败结果、错误原因和版本写入 trace，不能只保留最后一段回答。
- 不复制：百度工作流的节点 UI、示例流程或平台专属配置；只借鉴显式输入输出、分支、异常出口和版本意识。
- A 的具体交付：任选当前真实任务的 3 个 gap，为每个标出当前作品 locator、外部来源 locator、提取方法、失败出口；没有来源原文时标 unknown。

### K2｜小红书 Agent 岗位描述：生产级 Agent 关注状态、恢复、工具治理和端到端评测

- 来源类型：企业公开招聘信息（代表岗位能力要求，不等于内部实现说明）。
- 来源定位：
  - “2027校招 AI agent算法工程师（企业智能）”职责第 2 点：任务拆解、工具调用、上下文管理、记忆、结果校验、多轮交互和工作流编排。
  - “2027校招 点点 Agent研发工程师”职责第 1–5 点：状态管理、异常恢复、工具检索与多工具协同、生成式 UI、端到端任务评测、真实工具实验环境、效果/稳定性/时延/成本。
  - “Harness Kernel 与执行架构研发”岗位描述：长任务状态持久化、断点恢复、幂等执行、工具安全、trace/遥测与成本。
- 可提取的方法：
  1. 不只评测回答内容，还要评测整条任务是否完成及执行轨迹中断在哪。
  2. 将状态持久化、工具调用、审批、记忆和评测当作可观察的独立层，避免页面显示“完成”但后端没有对应证据。
  3. 评测指标至少覆盖正确性、失败恢复、稳定性、时延和成本，不要只报测试用例通过数。
- 对仓库的映射：
  - 复用 `team_orchestrator` 的版本保护与 `pending_review`，不要另造一套 UI 状态作为真相。
  - 在 A 的 source record 中增加 `source_locator` / `evidence_quote_or_excerpt` / `source_type` / `retrieved_at` / `access_status`。
  - 记录从 A gap 到 V2 review 的完整 trace；工程测试、受控模型夹具、真人试做分开记账。
- 不复制：不能把招聘岗位描述当成小红书内部代码细节，也不能据此宣称行业统一标准。
- A 的具体交付：从岗位描述中只提炼可核验的能力要求，映射到当前仓库已有/缺失项，标记“行业基线 / 我们的假设 / 尚待验证”。

### K3｜抖音公开 Agent 内容：按风险分级权限；工具发现、选择、参数生成分别排查

- 来源类型：创作者公开视频（经验观点，不是平台官方规范）。
- 来源定位：
  - 《做AI Agent，权限千万别乱给！》：按可撤回性与影响划分低、中、高风险；低风险自动执行，中风险人工确认，高风险由用户亲自操作。
  - 《Agent工具总选错？三步排查动态加载》：工具发现 → 工具选择 → 参数生成。
- 可提取的方法：
  1. 工具调用错误要定位发生在“没发现合适工具”“选错工具”还是“参数错”，不要笼统地重试整个 Agent。
  2. 依据可逆性和影响设置权限：只读检索可自动进行；写文件、改版本、发送/提交等动作需预览或确认；高影响操作由用户执行。
  3. 每次工具调用保留选择理由、参数、结果和错误，方便定位失败阶段。
- 对仓库的映射：
  - 工具失败应有独立 error type 和 `failure_next`，按错误阶段返回 A 补证据、B 改动作或 C 等待/人工确认。
  - `team_orchestrator` 的成果复核门继续保护；不要让“工具返回 200”直接等于成果通过。
  - A 参考来源标为 `reference` 或 `suggestion`，不能伪装成 `official`。
- 不复制：不把短视频观点作为权威规则；必须以真实工具测试验证风险等级是否适用于本项目。
- A 的具体交付：挑一个当前工具失败或资料不足场景，指出失败属于发现/选择/参数/执行/验收哪一层，并附证据定位。

- 来源定位：

- 可提取的方法：
  1. 把工具的用途、输入参数、输出、权限、错误处理和人工确认点写成契约。
  2. 任务状态变化要通过明确事件/结果驱动，不能从聊天文字推断“已经执行成功”。

- A 的具体交付：给每条提取方法标出它属于 A 证据判断、B 动作生成还是 C 状态/权限治理，避免职责混写。

### K5｜人人都是产品经理：Agent 要把模糊目标转成任务卡，执行后校验并沉淀状态

- 来源类型：产品从业者文章/经验总结，适合提炼设计假设，不是独立实验结果。
- 来源定位：
  - 《做 Agent 半年才醒悟：对话框只是入口，真正的核心是任务闭环》：第 1 部分“纯对话式 Agent 的问题”；第 2 部分“任务闭环”；文中任务结构化、规则校验/模型校验、状态沉淀段落。
- 可提取的方法：
  1. 模糊需求先结构化为目标、资源、约束、截止与成功标准。
  2. 结果校验至少拆成规则层（字段、权限、版本）和语义层（是否满足原目标、是否遗漏）。
  3. 状态沉淀要让用户重开后继续未完成任务，而不是只保存聊天文本。
  4. 任务闭环主张必须用真实任务证据验证；文章观点不能直接当作效果数据。
- 对仓库的映射：
  - A 的 gap 应有当前证据、目标判据、为什么影响目标、适用性与验证方法。
  - C 继续检查版本与状态；A 复核结果使用 pass/fail/unknown；unknown 不等于 pass。
  - 用 V1/V2 和原始验收标准评测，不能只看用户“觉得不错”。
- 不复制：不要直接照搬文章中的“五层模型”作为上岸鸭独创框架；只提取结构化任务、双层校验、状态沉淀这几种可复用方法。
- A 的具体交付：为当前真实作品找出 3 个有 locator 的 gap，并说明每个 gap 如何进入行动卡和验收标准。

## 2. A 在仓库中的落地字段与判定规则

对每条未关闭 gap，建议按以下结构交付（字段名须与当前仓库实际 schema 对齐；如要新增字段，先补 schema 与测试，不可只在文档中宣称实现）：

```json
{
  "gap_id": "真实且稳定的ID",
  "current_artifact": {"artifact_id": "已登记ID", "artifact_version": 1},
  "current_locator": "真实页码/段落/行号/模块名",
  "current_evidence": "当前作品中可核对的事实",
  "target_result": "希望达到的可检查结果",
  "source_refs": ["已登记的source_id"],
  "reference_locator": "来源中的章节标题/视频课程节次/文档小节",
  "extract_pattern": "只提取的方法、结构或证据组织方式",
  "reason": "该方法为什么适用于当前差距",
  "applicability": "适用边界与不能照搬的部分",
  "verification_method": "怎样检查改完后真的更好",
  "verification_status": "verified | unknown"
}
```

重要：`reference_locator` 和 `extract_pattern` 只有在代码 schema/验证器已支持时才能作为生产字段；否则先在研究记录里保存并开一个实现任务，不能假装后端已经强制校验。已有 `validate_diagnosis` 对 `current_locator` 等部分字段仍允许可选，因此 A 不能只因为 JSON 合法就宣称证据充分。

### 来源等级与防伪规则

- `official`：主办方、官方产品文档、官方项目/代码仓库等可直接支持的事实。
- `user_material`：用户真实任务书、作品、数据或导师反馈。
- `reference`：同行产品/开源项目/论文/可核对的实践案例。
- `suggestion`：博主观点、教程解释、搜索摘要或未独立核验的二手材料。
- URL 存在 ≠ 内容已读取；标题存在 ≠ 原文已定位；教程演示 ≠ 我们已实现；招聘要求 ≠ 企业内部代码细节。
- 若页面访问受限、视频无法定位、引用只来自搜索摘要：保留 `unknown`，记录访问限制，改用可访问的官方文档/字幕/用户上传内容；不得伪造页码、时间戳或原文。
- 不复制整段内容、界面、图片或提示词；只提取必要方法，并注明来源与边界。

## 3. 本轮给 A 的具体执行清单

1. 先取一份团队当前真实作品 V1 与原始验收标准；记录文件名、版本、准确页/段/行/模块 locator。没有 V1 时明确写“无作品”，不能编造。
2. 每个平台至少选 1 条最相关公开来源，不求链接数量；逐条登记来源类型、标题、locator、原文能支持的事实、提取的方法和适用边界。
3. 只输出 3 个 grounded gap：每个 gap 同时包含当前作品证据与参考来源位置。若作品位置或来源位置缺失，状态为 unknown/blocked。
4. 将每个 gap 的“提取方法”交给 B，但不要替 B 代写通用步骤。B 必须据当前文件位置生成不同的 micro_steps。
5. 抽查 3 条 gap：队友不问 A，能找到当前问题、参考原文和可提取的方法；找不到就退回 A。
6. 跟踪一条真实 V1→V2：另一位成员只看行动卡实际修改，A 按原标准给 pass/fail/unknown；没有真实 V2 就不能写“闭环完成”。

## 4. 对现有仓库的优先修改建议

- P0：A 的 source registry 记录来源类别、URL、标题、定位、访问/读取状态和检索日期；不要把“搜到 URL”标为 verified。
- P0：gap 绑定当前作品版本和 locator；引用的参考材料另有 reference locator；来源不可访问时明确 unknown/blocked。
- P0：A 的每条 gap 必须写 `extract_pattern` 与 `applicability`，明确“借鉴方法，不复制内容”。
- P1：把来源引用正确性、locator 可回查率、3 条 gap 的成员独立定位成功率加入 A 的验收；它们是团队内部验收指标，不是官方竞赛标准。
- P1：将“检索/诊断失败”作为回归测试：无原文、只有搜索摘要、错版本、链接失效、参考内容不适用时都不能输出 verified。
- P1：把同条件 V1/V2、原判据复核、剩余问题变化和失败记录用于创新验证；测试数量不是用户收益，受控测试不是真人验证。

## 5. 当前证据边界

本文件是截至 2026-10-22 的定向公开资料抽取，不是对百度、小红书、抖音、B站、人人都是产品经理或程序员鱼皮所有内容的全量抓取。不同来源的证据权重不同：百度官方文档适合支持平台功能事实；小红书招聘页只能支持公开岗位要求；抖音/B站/产品文章/创作者工作流适合提取实践思路，不能当作官方规则或上岸鸭效果证据。竞品“没有某功能”的结论必须写成“本次公开资料未查到”，不能绝对化。
