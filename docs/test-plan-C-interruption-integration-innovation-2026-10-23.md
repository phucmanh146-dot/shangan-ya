# C 队长独立测试计划｜中断接续、循环机制、集成与创新验收

日期：2026-10-23
目的：**通过端到端测试定位上岸鸭在状态保存、恢复、循环、工具调用和复核门上的功能缺陷，并驱动代码/工作流迭代。** 不以“存在字段、按钮或单元测试通过”作为创新成立证据。

## 1. 当前证据与判断
根据《上岸鸭竞品拆解与过程干预方案》（2026-10-23 上传版）第 1、5–6、10–13、15–22 页、《上岸鸭新版 PRD 与任务接续和状态调度》（2026-10-17）及 GitHub Issue #7、#32：
- PR #21、PR #22 各有工程测试记录；其中 PR #22 相关 70 项测试使用受控模型响应，不能证明真实模型质量或真人体验。
- PR #21 与 PR #22 曾标记待集成；main 上部署压缩包不能证明科研增强能力已上线。
- 中断后接回原步骤、真实 V1→V2、复核和剩余项重排仍缺完整真人闭环。
- 状态按钮、论文换讲法视频、短幽默、休息计时与接续、疲惫后的局部重排等部分在材料中标为待开发。
- 结论：**创新目前属于“有明确差异化设计和部分工程基础，但未达到完整验证/落地证明门槛”。**

## 2. 主责测试范围
1. 检查 PR #21/#22 的集成状态、冲突、路由和回归测试；区分分支测试与 main/部署版本。
2. 中断前保存当前项目、版本、locator、已完成项、尝试过的方法、承诺、下一步及返回条件。
3. 关闭/刷新/新开会话后，确认项目身份，再恢复准确的原步骤。
4. 测循环：同一帮助无效后是否换法、拆小、求助或停止；有界重试，不能无限循环。
5. 测工具调用失败和复核门：失败不能记成功；V2 必须 pending_review，A 验收后才可完成。
6. 统筹 5–8 位同学试用与同任务对照，记录真实行为和效果，输出 go/revise/stop。

## 4. 五项创新的证据门
1. **人做、模型验成果闭环：** 必须有 V1、原标准、行动卡、真人 V2、逐条复核、人工确认和剩余项。
2. **精确中断接续：** 必须记录中断位置和恢复位置一致性、恢复耗时及恢复后是否实际动手。
3. **论文换讲法/冷启动：** 当前材料标待开发的功能先标未测；实现后再测是否 5 分钟内产出可检查 V0。
4. **低打扰状态分流：** 用户主动选择/页面行为只触发询问；看不懂与疲惫的路径不同，不推断心理状态，不使用摄像头。
5. **个性化帮助记忆：** 记录用户对哪种帮助有效，后续任务能否更准确选择；要有对照与用户确认，不能凭一次点击贴永久标签。

## 5. 优化与回归规则
- 状态丢失/串项目：改 state register、project confirmation、version conflict guard。
- 无限重试：改循环停止条件、换法和升级求助逻辑。
- 工具失败被记成功：改 tool result status 与证据门。
- V2 未复核已完成：改 pending_review 状态门。
- 分支功能未集成：先处理冲突与回归，再检查部署产物，不先做新功能。
- 真实体验差：依据 trace 和盲测日志改动作粒度、返回界面或状态分流。
每次修改必须记录 commit、失败用例、修复前结果、修复后结果和回归结果。

## 6. 队长交付与验收
- 集成矩阵：PR/branch/main/deployment 的实际状态。
- 每项创新假设：支持证据、反证、未测项、go/revise/stop。
- 真实用户试用数据和同任务对照表（未完成前明确标待测）。
- 至少一个端到端真实 V1→V2 记录及一个中断恢复记录。
- 修复提交和重复运行的回归证据。

**边界：** 70 项受控响应测试通过只能证明对应测试范围的工程行为，不等于真实模型、真人体验或创新性已通过。公开评测实践也建议保留 traces、评分标准与可重复数据集来定位失败和验证修复，而不是只报总通过数（参考：https://developers.openai.com/api/docs/guides/agent-evals）。
