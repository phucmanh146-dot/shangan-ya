# 上岸鸭差异化、传感器取舍与错误处理清单
复盘依据：编号资料 1–8 +《上岸鸭新版 PRD：任务接续与状态调度》（第 9 份执行依据），并对照 PR #21、PR #22、Issue #7 的文档记录。
日期：2026-10-19
状态：产品分析与实施建议；不等于新增代码已实现或真人验收已通过。

## 1. 结论先说

上岸鸭不能把“RAG、多智能体、工作流、讲题、视频、番茄钟、摄像头”写成独创。资料 1、2、3、7、8 的共同结论是：这些是成熟积木，竞品和获奖作品已在使用。我们最能站住脚的两条差异是：
1. 人做、模型验的真实成果闭环：绑定用户自己的 V1、原始判据和证据位置；由人按行动卡实际修改成 V2；A 按原判据逐项复核；B 只处理未通过/未知项。
2. 停在哪、接回哪的任务现场恢复：按项目、任务、作品版本、原文位置、卡点、已试办法、下一微动作、返回条件保存现场；回来先确认项目/版本，再回原动作，而不是重新生成一份泛化计划。

三个支撑方向：论文当前段落换讲法后回到原段落完成微动作；五分钟冷启动；用户主动选择困难/疲惫/中断原因后分流。它们要服务两条主创新，不要包装成五个彼此独立的大系统。

重要证据边界：文档里竞品“没有”的表述应理解为“我们查到的公开资料里没有看到”，不能说全世界/所有竞品都不具备。文档明确承认尚无充分数据证明独特性，也没有一条真人从头到尾完成的闭环记录。

## 2. 和同质化产品的差别

| 同质化类别 | 竞品/获奖作品已经能做什么 | 上岸鸭应该做出的差别 | 必须演示的证据 |
|---|---|---|---|
| AI 讲题、换说法 | 豆包爱学、ChatGPT 学习模式、夸克老师、千问能讲解、追问、画图或练习 | 仅当用户主动选择“听不进去”时，绑定当前作品版本和段落；讲解后回原段落做一个动作 | 原文定位、解释对照、回原位置完成一格表/一句复述 |
| 出题、测验、错题 | 多家学习产品和 NotebookLM 等有练习/测验 | 首版不把出题作为卖点 | 不投入首版核心开发资源 |
| 文档转视频/课程 | NotebookLM、秘塔“今天学点啥”能把资料转成课程/音视频 | 视频不是卖点；只把当前卡住的段落转成能追溯原文的讲解，观看后回原任务 | 实际可播放文件、字幕/旁白、原文定位、后续微动作记录 |
| 学习计划/任务拆解 | 扣子/文心提示词智能体、Goblin Tools 可拆步骤或估时 | 每步绑定具体作品版本和定位；第一步约 5 分钟内能开始；给出产物、自检和失败下一步 | 队友只看行动卡、不听口头补充，能独立做出实际修改 |
| 番茄钟/打卡/自习陪伴 | 大量自习、计时、打卡产品 | 不把计时本身当卖点；休息只是一种中断分支，核心是保存现场和接回原动作 | 刷新/重开后同一任务、版本、位置与下一动作可恢复 |
| 摄像头专注检测 | 既有产品可用摄像头判断离席/专注迹象 | 不自动判断“没听懂/不努力/累了”；首版用用户主动反馈。未来传感器只触发一句询问 | 单独同意、可关闭、有非摄像头替代；误报数据和关闭记录 |
| RAG/多 Agent/工具调用 | 获奖作品和平台均有相关积木 | 不宣称技术名词创新；用证据门、版本保护、真实 V2 和失败留痕来约束流程 | 缺定位/引用/产物时 blocked 或 unknown；工具失败绝不记成功 |
| 项目管家/DeadlineOS 等 | 项目流程操作、课程信息、可验证行动等各有侧重 | 上岸鸭定位在用户自己的作品质量与执行现场：做完交 V2、按原标准复核、卡住可恢复 | 同一任务对照测试和真实 V1/V2 证据，不靠名称或宣传语 |

### 两条主创新的答辩句

**创新一：**“普通助手能生成解释和计划；上岸鸭把计划绑定到用户自己的作品版本和原文位置，由人真正改出 V2，再按最初的验收标准逐条核验。模型自己说完成不算完成。”

**创新二：**“普通助手通常需要用户重新交代背景；上岸鸭保存任务现场——版本、位置、卡点、试过的方法、下一动作和返回条件。中断回来确认项目后，继续原来的微动作。”

不要说“竞品绝对做不到”。应说“在我们查到的公开资料中，尚未看到这些产品把上述环节完整绑定；我们会用同任务对照试验验证”。

## 3. 传感器：当前开发需要什么、不需要什么

### 首版必须做
- 用户主动反馈按钮：“听不进去”“真的累了”；保留“遇到技术困难”“临时有事”。
- 普通页面/任务事件：用户开始、保存、提交 V2、复核、暂停、返回、延长休息、结束本轮。
- 持久化任务状态：project_id、member_id、task_id、micro_step_id、artifact_version、locator、state_kind、已试办法、下一动作、返回条件、开始/计划结束/实际返回时间。
- 基本时间记录：首次真实操作时间、休息实际经过时间、返回后第一次实际动作时间。倒计时到点不自动开始任务、不自动勾完成。

这些不需要额外硬件传感器。首版最重要的是先把“用户主动选状态→保存现场→分流→回来接续”跑通。

### 可选原型 A：摄像头本地 CV（非 P0）
- 可用：浏览器 MediaPipe Face Landmarker，本地计算闭眼时长/占比、打哈欠、低头、暂时检测不到人脸等聚合信号。
- 不可推断：这些信号不能证明用户没听懂、走神、累了或不努力。低头可能在记笔记，视线离开可能在查资料。
- 文档引用的研究中，人脸视频走神识别在实验室约 F1 0.44–0.46，真实环境约 0.35，文档报告真实场景只识别出约 23% 的走神。该数字是资料引用的研究结果，不是上岸鸭实测结果。
- 触发方式：仅超过个人校准阈值时询问一句“要换个讲法、休息一下，还是没事？”最终状态由用户选择；用户选“没事”记作误报，后续调整阈值。
- 隐私：明确单独同意、默认关闭、可随时关闭、有完整替代路径；画面只在本地处理，不上传/存储人脸画面。暗光、眼镜反光、摄像头被占用或未检测到人脸时，显示“本次未能判断”，不提示状态。

### 可选原型 B：华为手表/穿戴（非 P0）
- 技术路线：若团队已有兼容真机，可在手表端 HarmonyOS/ArkTS 小应用读心率，经手机消息通道把必要的聚合信号传给上岸鸭。
- 权限和限制：文档指出实时心率读取需要真机和相应健康数据权限；手机侧直接读取手表心率/压力并非所有开发者均可使用，Wear Engine 对某些健康能力有企业开发者门槛；Health Kit 的具体权限和数据类型需到开发者后台核实。
- 只能触发询问，不能凭心率高、压力值高或久坐直接断定疲惫。运动、咖啡因、情境等都会影响信号。
- 不要把“必须接手表”列入首版验收。文档建议首版不依赖手表；答辩需要传感器展示时再做独立可选原型，并明确这是原型。

### 传感器开发顺序
1. 先完成无传感器的一键反馈和现场恢复。
2. 统计 5–8 位试点的误提醒、有用提醒、关闭次数和实际返回情况，建立基线。
3. 如果时间允许，再做本地摄像头原型；传感器仅做触发信号。
4. 只有在真机、权限、消息链路可确认时再做手表原型。
5. 不要同时做摄像头、手表、微信自动读取和课表接入，避免偏离主闭环。

## 4. 报错与失败处理：按优先级落实

所有失败统一原则：写入工具调用记录（输入摘要、工具/模型、项目和版本、时间、返回/错误、重试次数、证据引用）；失败不能算成功；保留存档点；向用户说明失败在哪里；给出可执行的下一步。不要把 API key 或敏感原始内容写进日志。

| 优先级/场景 | 必须做的处理 | 不允许的行为 | 验收用例 |
|---|---|---|---|
| P0 文件上传/解析失败 | 明确文件名、失败阶段、支持格式；保留原文件和项目现场；允许重传或改用 TXT/MD；显示“未读取成功” | 解析失败却继续诊断、显示已读取 | 空文件、损坏 PDF、扫描 PDF、格式不支持、重复上传 |
| P0 无原文定位/引用缺失 | 诊断标 unknown/blocked；指出缺的是哪个页/段/来源；让用户补资料或重新解析 | 编造引用或无证据放行 | 引用不存在、locator 越界、没有来源 |
| P0 模型超时/限流/不可用 | 超时、429、5xx、网络错误分开记录；有限重试（如最多一次），退避后失败则转 blocked；允许离线/规则演示，但明确标记演示模式 | 无限循环、伪造成功、静默切换成假数据 | 超时、429、断网、模型返回空 |
| P0 输出结构无效 | 校验 JSON/schema 必需字段；缺 micro_steps、产物、自检或 failure_next 时拒收；可修复重试一次，仍失败转人工处理 | 用通用三步填充缺失字段后假装合格 | 缺字段、类型错误、乱码、混入非 JSON |
| P0 A→B 交接缺失 | 校验 input_version、locator、evidence_refs、action、expected_change、output、self_check、failure_next；版本不一致阻断 | B 规划引用旧版本或空差距 | 旧版本行动卡、无产物标准、无依赖 |
| P0 V2 复核失败 | 复核结果按 pass/fail/unknown；校验版本、引用存在性、原判据；待人工确认；B 只处理 fail/unknown | 模型自评通过、误放行、已完成项被重排覆盖 | 错版本、引用失效、未知项、人工复核否决 |
| P0 状态存档/恢复失败 | 事务写入、幂等请求、checkpoint_id；恢复时检查项目/版本是否变更；冲突则提示重新确认 | 重复创建休息、串项目、接到过期位置 | 刷新、关页、服务重启、重复点击、旧 checkpoint |
| P1 检索无结果/资料过期 | 明确“未找到”，给求助卡/替代路径；记录来源和更新时间 | 编造链接或把旧资料说成已验证 | 无命中、链接失效、版本更新 |
| P1 视频生成失败 | 保留脚本/分镜/图文，状态标 video_failed；可人工剪映替代；只有真实可播放文件才算视频交付 | 把脚本完成算作视频完成 | TTS 失败、导出失败、画面与论文不符 |
| P1 休息计时/通知失败 | 刷新后按后端时间计算实际经过时长；回到页面显示实际状态；提供手动返回 | 承诺后台一定准时通知；倒计时结束自动执行任务 | 后台挂起、页面关闭、延长、结束本轮 |
| P1 摄像头/穿戴不可用 | 显示未能读取、权限拒绝、设备不支持；回退到手动状态按钮 | 把设备不可用当用户状态 | 无摄像头、暗光、拒权、手表断连 |
| P1 公网/API/认证错误 | 401/403/404/429/5xx 分层提示；API key 仅在后端；测试账号和用户数据隔离 | 在前端暴露密钥、把本地可用说成公网可用 | 无痕浏览器、错误账号、接口断开、跨账号读取 |

### 推荐统一错误记录字段
- error_id、timestamp、project_id、task_id、checkpoint_id
- stage（upload/parse/retrieve/diagnose/plan/execute/review/resume/video/sensor）
- input_version、locator、tool_name、model_name
- error_code、user_safe_message、retry_count、recoverable
- fallback_action、evidence_refs、status（failed/blocked/unknown）
- 用户是否重试、重试结果、是否人工接管

### 错误状态机
ready → running → succeeded
running → retrying → succeeded
running → blocked / unknown / failed

只有拿到实际工具结果并通过对应验收门，才能进入 succeeded。用户看到了卡片、看完视频、计时结束、模型回复“已完成”都不构成成功。

## 5. 当前工程状态：必须按证据分层汇报

根据第 6、7、8、9 份资料记录：
- 已有/曾通过受控工程测试：Python 后端、HTTP 接口、SQLite 项目/版本/任务/运行历史；文件接入和版本记录；证据门、有界循环、重复调用拦截、部分复核/剩余重排接口；PR #21 的现场卡/尝试/承诺与条件返回；PR #22 的项目匹配入口和部分校验。
- 仍需集成：PR #21 与 PR #22 有同名 team_recovery.py，须保留“找回项目”和“恢复任务现场”两种职责；合并路由、team.js、诊断门槛和行动卡校验后跑组合回归。
- 仍待开发/验收：state_checkin、intervention、break_session 数据与接口；两类状态按钮与页面流程；后端休息计时；D05 可播放科普视频和接续；真人 V1→V2、A 复核、B 只调剩余；真实模型语义稳定性；重开页面的准确恢复；公网多环境交付。
- 传感器：摄像头和手表均为“另行验证”，不是首版 P0。
- 不能混淆：PR 的受控测试通过 ≠ 真实模型成功率通过 ≠ 真人作品闭环通过 ≠ 公网部署通过。

## 6. 团队下一步（按依赖排序）

1. C/队长：先集成 PR #21/#22，拆开两个恢复模块职责，做错项目、错版本、重复请求和刷新恢复回归。
2. A：挑一份真实作品，准备原始判据、版本、定位、来源；输出至少一条可复核差距；再对真人 V2 按原判据复核。
3. B：只接收校验通过的差距，交付有版本、位置、动作、产物、自检、失败下一步的行动卡；另一名成员只看卡完成实际修改。
4. 全队：保存运行日志，做出一条真实闭环记录；随后加一键状态分流和接续测试。
5. A+C：用真实论文做一条短片，先人工剪映合成，核对每句与原文；短片可播并且用户回原段落完成动作才算 D05 完成。
6. 5–8 位同学试用，记录 V1→V2 通过数、误放行、重要任务返回率、恢复耗时、误提醒和用户负担。没有数据就标“未测”，不编效率提升百分比。
7. 最后再决定是否接摄像头/手表。若主闭环尚未稳定，不应把传感器作为当前里程碑。

## 7. 对外表述边界

可以说：“上岸鸭的设计重点是两条可验证闭环：人实际修改作品、系统按原判据复核；中断后恢复到准确任务现场。我们正在用真实作品和用户试用验证。”

不要说：
- “我们首创 RAG/多 Agent/摄像头识别”；
- “摄像头能准确知道用户走神/疲惫”；
- “所有竞品都做不到”；
- “已经提升效率 X%”或“真人闭环已跑通”，除非有完整可核对数据。
