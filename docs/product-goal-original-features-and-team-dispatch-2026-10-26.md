## 1. 最终目的：不是再做一个 ToDo 或问答 Agent

上岸鸭面向第一次做大学生竞赛、科研和创新实践项目、容易卡在第一步的学生。用户提供真实作品、目标、截止日期和可用时间后，系统要做到：

1. 读懂真实材料，而不是只根据一句话编通用计划。
2. 把“我不知道从哪开始”变成一个 5 分钟内可以开始、做完有可见产物的首步。
3. 每个问题都定位到原件证据，区分事实、推断与未知；资料不足时拒答或求助，不编造。
4. 将已验证的问题转成第三人也能照做的微动作，写明位置、动作、原因、输出、检查方式、依赖、估时和失败后的下一步。
5. 用户看不懂、疲惫、报错、缺资料或中断时，先解决当前卡点，再接回原任务的准确位置。
6. 用户完成真实修改后保存 V2，由非执行者按冻结的原始标准独立复核。
7. 只重排未通过、未知或阻塞项，不覆盖已完成、执行中、待复核和已锁定成果。
8. 将材料版本、工具调用、失败、耗时、V1/V2 差异和复核记录串起来，让团队能复现、比较并持续优化。

**一句话定位：帮第一次参赛或做科研的大学生，把手里的真实作品一步步做出来、做完并通过有证据的复核的 AI 作品教练。**

产品差异不是“多几个 Agent”，而是两个可实测的闭环：

- 成果闭环：真实材料 → 证据诊断 → 行动卡 → 真人产物 V2 → 独立复核 → 只调整剩余项。
- 过程闭环：用户卡住/离开 → 记录现场与原因 → 提供合适帮助 → 确认用户重新开始 → 接回原步骤 → 记录结果。

## 2. 原有功能怎么保留、怎么排期

不为了比赛临时删掉产品长期方向，也不把所有设想一次性塞进比赛版。采用“核心闭环先验收、过程干预再接入、个人版扩展保留”。

| 功能层 | 原有功能/需求 | 在最终产品中的作用 | 优先级与边界 |
|---|---|---|---|
| 真实材料接入 | Word/PDF/PPT/图片、网页/知识库材料；记录来源和版本 | 让诊断有真实依据 | P0；先确保可读取格式，并标出不支持/未解析材料。图片、扫描件、音视频不能因有文件名就视为已读 |
| 证据驱动诊断 | A 读取原件、目标标准、用户现状，输出 gap、引用和未知项 | 找到作品实际差距 | P0；每个 gap 必须有 locator、材料版本、判据、证据支持性状态 |
| 行动卡与依赖排程 | B 规划微动作、依赖、估时、截止和验收点 | 从“知道差距”变成“知道下一步做什么” | P0；保留规则规划器，不为追求多 Agent 名称额外增加模型调用；缺证/缺步骤/容量不足就 blocked 或 unscheduled |
| 版本保护与成果复核 | V1/V2、diff、expected_version、独立 review、已完成保护 | 防止覆盖成果、假完成 | P0；V2 提交后进入 pending_review，不能由执行者自评直接关闭 |
| 中断恢复 | 存档点、checkpoint、卡点、尝试、下一步、返回条件、项目确认 | 中断后回到原步骤 | P0；恢复的是任务现场，不得宣称正在进行的网络请求会自动续跑 |
| 冷启动 | 参考作品、半填空模板、3 分钟试做、5 分钟首个产物 V0 | 让零基础用户开始 | P1；先做轻量版本，不先扩建完整课程平台 |
| 资料检索与拒答 | 将大白话转成检索术语；知识库优先；给 1–3 条带定位资料；找不到时给求助卡或替代路径 | 降低检索门槛并防止编造 | P1；建立检索评测集，错误问题回流；未接入的外部渠道不能写成已支持 |
| 状态感知与干预 | 页面切后台、同一步超时、重复报错等轻量信号；询问用户当前状态 | 识别“可能掉线”，而不是给用户贴标签 | P2；先用非摄像头信号，询问用户后再决定帮助方式 |
| 个性化帮助 | 看不懂→换讲法/例子；疲惫→缩小任务/休息后续接；报错→排错/替代路径 | 让帮助适配当前卡点 | P2；最多尝试两轮，仍无法推进就求助/暂停，避免无限循环 |
| 跨会话记忆 | 项目、材料版本、准确位置、已尝试方法、卡点、下一步、返回条件、用户主动选择有效的帮助方式 | 记住“事情做到哪”，不只是“用户是谁” | P1；项目记忆与用户偏好分开；恢复前确认项目和版本 |
| 工具与可观测 | search/read/finish、文件读取、版本存储、诊断/计划/复核 trace、失败记录 | 让每个结果可追溯 | P0；记录输入、结果、错误和版本；失败不能静默伪装成功 |
| 个人版扩展 | 更丰富的课程库、网页/飞书/视频接入、休息计时、站外提醒、更多陪伴交互 | 扩展长期使用场景 | P3；保留路线图，不阻塞第一条真实作品闭环；每个连接器按实际权限逐项验收 |

### 本轮明确不做

- 不把摄像头监控作为核心差异化；默认不用摄像头判断用户是否专注。
- 不把 A、B、C 全部改成独立大模型。当前 B 的规则规划器可以保留，前提是动作可追踪、可执行、守住版本与状态。
- 不同时铺开商城、社交、习惯养成等无关功能，不能让这些功能拖住竞赛/科研作品闭环。
- 不把 URL、摘要、文件名、mock 结果或 HTTP 200 当成真实证据。
- 不把计划已生成、任务已排程、模型已返回或用户点了完成，当作作品已通过验收。

## 3. 总体技术结构：保留现有技术，补齐交接和证据门

~~~text
用户目标 + 截止日期 + 可用时间
            ↓
材料接入 / artifact_store：导入、版本、SHA256、可读内容、locator
            ↓
A：team_ai.researcher / documents
证据诊断：gap、判据、原文定位、事实/推断/unknown
            ↓
证据门：validate_diagnosis + 原件/版本检查
缺定位、来源不支持、材料未解析 → UNKNOWN/BLOCKED
            ↓
B：action_planner + team_handoff.planner
规则驱动微动作、依赖、容量、估时、自检、失败下一步
            ↓
计划门：validate_micro_steps + expected_version
缺步骤、版本过期、依赖未完成 → BLOCKED/UNSCHEDULED
            ↓
真人执行 + team_recovery / team_rescue
记录尝试、卡点、暂停现场、求助、实际产物
            ↓
V2 提交：team_orchestrator.commit/current
V1 保留、版本递增、diff/hash、状态 pending_review
            ↓
A 独立复核：team_ai.reviewer / team_handoff.review
冻结判据逐条 PASS / FAIL / UNKNOWN + 人工确认
            ↓
B：team_revision.plan_remaining
仅重排 FAIL / UNKNOWN / BLOCKED，保护已完成与待复核成果
            ↓
C/队长：trace、回归、归档、下一轮基线
~~~

这是“模型 + 规则 + 工具 + 真人”的组合，不是所有步骤都由模型自由决定：

- 大模型负责：真实材料语义分析、检索问题改写、解释/示例生成、结构化诊断建议、独立复核建议。
- 规则/后端负责：schema 校验、材料和版本校验、状态转换、依赖与容量约束、expected_version 并发保护、重复调用拦截、预算与循环上限、审计记录。
- 真人负责：选择项目与目标、确认计划、真实编辑/操作、提交 V2、对关键复核做人工确认。
- Agent 工具循环负责：在允许的工具和轮数范围内搜索、读取、观察工具返回、决定下一步或停止；工具失败不能被模型当成成功。

| 中断与求助 | team_recovery.pause/resume/attempt/context_packet、team_rescue.start/sync | 保存现场、失败尝试、上下文和下一步求助 | 保存现场不等于自动续接在途网络请求 |
| 自主工具循环 | learning_agent.run_agent | 按当前工具策略 search/read/finish，并根据工具结果决定下一步 | 技术方案记录为最多 7 轮、前 4 轮可用工具；须以目标版本代码复核 |

## 5. 过程干预与双层循环：把“用户动手”纳入 Agent 反馈

### 5.1 内循环：解决当前卡点

1. 用户在行动卡中开始一个明确的 5 分钟微动作。
2. 系统根据用户主动选择、页面轻量信号或操作错误，询问“你现在是看不懂、太累、没资料，还是遇到报错？”不自行诊断用户心理。
3. 根据选择给一个针对性帮助：换一种解释、举同类例子、把动作再缩小、检索 1–3 条带定位资料、给求助卡或替代路径。
4. 用户尝试并提交可检查的小产物/尝试记录。
5. 若仍未推进，最多换一种策略再尝试一次；两轮后仍卡住，保存现场并升级求助/暂停，不无限生成建议。

### 5.2 外循环：验证作品是否真的变好

V1 → 证据 gap → 行动卡 → 真人执行 → V2 → 独立复核 → 只重排剩余项。

外循环的停止条件不是“模型已经回答”，而是冻结判据有逐项结果、每个结果有可回查证据、关键项没有 fail/unknown/blocked、V2 与 V1 的变化可定位、非执行者完成独立复核、C/队长保存可复现证据包。

### 5.3 冷启动：第一次打开 5 分钟内产出 V0

| 时间 | 系统/用户动作 | 必须留下的结果 |
|---|---|---|
| 0–1 分钟 | 选择真实任务或上传材料，选择目标和截止期 | project_id、材料版本、目标判据草案 |
| 1–3 分钟 | 展示相近范例/半填空模板；用户做一次小试做 | 真实试做结果和卡点，不只记录自述水平 |
| 3–5 分钟 | 生成最小动作，用户完成第一格/第一处修改 | V0 小产物、耗时、是否需要帮助、下一步 |

如果材料尚未接入、用户没有授权或无法读取，不假装已完成诊断；先用明确标注的模板任务启动，并将真实作品诊断保持 blocked。

## 6. 三个真实作品的调度：先验证差异，再扩展样本

本轮优先用两个业务链差异较大的真实作品做第一条闭环，再用第三个样本检验复用性。作品名称和版本必须与原件确认；清单登记不等于原件已经可读。

| 顺序 | 样本 | 重点业务链 | 第一张行动卡的方向 | 不能通过的情况 |
|---|---|---|---|---|
| 1A | 湘匠织秀/湘秀未来 | 真实需求→访谈证据→纹样授权→报价/样品→质检→交付/结算 | 从原件定位一条真实需求/访谈，连接需求、产品、授权与履约证据 | 只输出“优化 PPT/加强调研”，无原文定位或业务证据 |
| 1B | 无界智泊 | 预约→冲突处理→入场→提前离场→结算/退款 | 选一个有版本号的状态转换，列前置状态、操作、预期状态、异常分支和日志 | 只描述功能，无法复现状态变化或异常 |
| 2 | 数智助老 | 服务发起→授权→转派→响应→办结→评价/异常 | 将效率/响应主张绑定真实基线、样本口径与履约记录 | 复用宣传数字、把规划当上线、没有基线却宣称效果 |
| 3+ | 嘉农芯生、滴水润疆、菌润乡土、文玩玉米、本草云联等 | 按原件实际业务链定制 | 由各自真实 gap 决定 | 仅替换项目名，其他 gap/动作/验收标准完全相同 |

第一轮不要求“把全部功能都做完”，而是证明同一个 Agent 能根据不同原件生成不同 gap、首步、产物和验收标准。如果原件未拿到、图像/PPT 尚未视觉复核、DOC 尚未解析，必须保留 blocked，不准用猜测填充。

## 7. 三人分工与依赖排程

A/B/C 是开发团队职责，不是要求最终用户理解多 Agent 架构。每个包按“可验收产物”交接，不能只汇报“已完成开发”。

| 包 | 负责人 | 前置条件 | 实际交付 | 放行条件 |
|---|---|---|---|---|
| C0 基线冻结 | C/队长 | 先做 | 目标分支/commit、工作区状态、输入材料清单与 SHA256、环境/命令/测试日志、旧 provenance 差异清单 | 版本和来源可复现；不覆盖原工作区与历史证据 |
| A1 原件诊断 | A | C0 + 授权原件 | 两个样本各至少 3 条 grounded gap；每条含 locator、原文、冻结判据、支持性/适用性状态、unknown | C 抽查首批 gap；伪引用/跨项目读取负例通过 |
| B1 行动卡/容量 | B | 至少一条 A1 gap 通过 | 每个 gap 对应具体微动作、依赖、估时范围、产物、自检、失败下一步；计划提案 diff | 第三人只看材料和卡即可执行；无证/无步骤/容量不足项明确 blocked 或 unscheduled |
| C1 工程状态与失败机制 | C + B | C0；可与 A1 并行 | 状态迁移表、版本冲突/重复提交/恢复/预算边界测试；run_id/trace_id 串联 | 旧版本不覆盖成果；错误不写成功；失败可追溯 |
| B2 真人执行 | 非行动卡作者 | A1+B1 通过且 C1 关键门满足 | 实际操作记录、耗时、求助次数、卡点、V2 文件/哈希、V1→V2 diff | 有真实产物，不是模型生成的“完成报告” |
| A2 独立复核 | A（不得是该 V2 执行者） | B2 + 原判据冻结 | review_id、逐项 PASS/FAIL/UNKNOWN、V2 定位、人工复核原因 | 原标准不因结果修改；UNKNOWN 不当通过 |
| B3 剩余项重排 | B | A2 已完成 | 只针对 FAIL/UNKNOWN/BLOCKED 的新行动卡；状态前后 diff | completed/in_progress/pending_review/locked 保持不变 |
| C2 试点评估 | C + 另一位复核成员 | 至少两类闭环和 G00–G10 证据 | 试用原始表、评测结果、失败样本、发布建议 | 关键门无 fail/blocked，另一成员独立复核 |

交接必须写明 case_id、project_id、code_commit、input_sha256、artifact_version、diagnosis_version、plan_version、run_id、gap_id、task_id、review_id、expected/actual、状态、日志路径、负责人和复核人。字段缺失时标出缺项与责任人，不得假装有值。

## 8. 本轮优先级与执行顺序

### P0：先让证据链不撒谎
- 冻结目标分支、commit、工作区状态和作品原件哈希。
- 对齐真实 schema 与 gap/action/review 契约，保留兼容读取，但禁止旧格式直接放行正式执行。
- 确认状态的合法迁移、失败返回和状态展示一致。
- 对缺定位、旧版本、缺 micro_steps、模型失败、复核未完成等路径加负例测试。
- 新建版本化证据 manifest，不修改旧 provenance 来“修绿”历史校验。

验收：ENGINEERING_BASELINE + ORCHESTRATION_PASS。只代表工程门通过，不代表真实模型/作品闭环通过。

### P1：做出可执行的真实诊断和第一步
- A 先完成湘匠织秀或无界智泊中原件更可读的一个样本；若均不可读，登记授权替代样本与原因。
- A 每个样本至少给 3 条可定位 gap；C 抽查来源是否支持判断。
- B 根据通过证据门的 gap 生成首张 5 分钟行动卡，写清打开哪个文件/哪一页、改什么、产出什么、怎么检查。
- 同目标输入不同真实材料，gap、首步、产物与验收标准必须随证据变化。
- 测量第一次有效动作时间和 V0 是否真实产出。

验收：DIAGNOSIS_READY + ACTION_READY + PERSONALIZATION_PASS；没有原件则 blocked。

### P2：中断接回与帮助策略
- 统一存档点字段：项目、材料版本、当前 locator、已完成项、尝试记录、卡点、下一步、返回条件。
- 重启后提出恢复候选，用户确认项目和版本后再接回；材料已更新时提醒旧定位失效。
- 根据用户主动选择/轻量信号提供帮助；默认不使用摄像头。
- 求助卡、替代路径、休息后返回与帮助偏好需可追溯，但不把一次状态永久写入用户画像。
- 内循环最多两轮；外循环以真实 V2 和独立复核为停止条件。

验收：RESUME_PASS + BOUNDED_HELP_PASS；在途模型请求是否自动续跑必须单独验证。

### P3：真实模型、浏览器与用户试用
- 在独立数据目录验证模型列表、连接测试、固定问答、文件诊断、计划、V2 复核和 401/429/超时/无效模型等失败路径。
- mock/simulated/live 标签贯穿 API、trace 和 UI；无效配置不得返回 LIVE 成功。
- 在完整前端环境运行现有浏览器脚本；保留日志、退出码和环境版本。
- 至少 5–8 位同学进行 3–5 天试用；记录失败与未完成，不删失败样本。

验收：LIVE_MODEL_PASS、BROWSER_REGRESSION_PASS 与 HUMAN_LOOP_PASS 分开判定。

### P4：评估效果后再扩展
- 在同一真实任务、材料版本、时间预算和冻结判据下，与普通 LLM 基线对照。
- 主指标：首次有效动作时间、中断后回到原步骤比例、恢复后开始动手耗时、独立完成比例、返工次数、最终成果合格比例、用户负担。
- 5–8 人只代表本轮试点，不外推为普遍优势；若要做更强对照，扩大样本、固定实验条件并盲评。
- 根据失败记录迭代检索、诊断、动作卡、恢复和复核，不以功能数量作为迭代目标。

验收：有原始数据、分母、失败记录和独立复核后，才能写“试点满足/未满足”；无数据不得写“已超越竞品”或“达到省一水平”。

## 9. 统一联调测试矩阵

| Case | 输入/操作 | 预期 |
|---|---|---|
| PGO-01 | 首次进入，仅有模糊目标 | 5 分钟内给可完成微动作并留下 V0；否则记录阻塞原因 |
| PGO-02 | 上传可提取材料并冻结目标 | 每条 gap 可回查原件、版本、判据和支持性 |
| PGO-03 | 图片型 PPT/未解析 DOC | 标注视觉复核/未解析并阻断语义通过 |
| PGO-04 | 来源 URL 存在但内容不支持 gap | 不得 verified；转 unknown 或退回 A |
| PGO-05 | 同目标、两份不同作品 | gap、首步、产物、验收标准随材料变化；只替换项目名即 PERSONALIZATION_FAIL |
| PGO-06 | 行动卡缺 gap_id、input_version、动作或输出 | 不进入可执行列表，显示缺项 |
| PGO-07 | V1 更新后提交旧计划 | 拒绝或要求重新诊断；历史不被覆盖 |
| PGO-08 | 两客户端相同 expected_version 写入 | 一个成功，另一个 Conflict；不双重提交 |
| PGO-09 | V2 已提交但无人独立复核 | 状态保持 pending_review |
| PGO-10 | 只有一项 fail，其他项 pass | 仅重排 fail/unknown/blocked 项 |
| PGO-11 | 用户暂停、关闭页面、重启后回来 | 确认项目/版本后回到正确 locator 和下一步；现场恢复与模型请求续跑分开测试 |
| PGO-12 | 看不懂/疲惫/报错/资料缺失 | 给对应帮助；两轮仍失败时有界求助/暂停 |
| PGO-13 | 无效模型、401/429、超时、无效 JSON | 明确错误、脱敏记录、不静默换模型或假成功 |
| PGO-14 | 最终 V2 反查来源 | 能从 V2 反查 V1、gap、行动卡、执行者、run 和 review |
| PGO-15 | 新紧急任务触发重排 | completed/in_progress/pending_review/locked 不变 |
| PGO-16 | 修复某个失败测试 | 重跑原失败输入、邻近负例和全量回归 |

每条记录包含执行版本、环境、命令/请求、预期/实际、四态状态、未运行时 execution=not_run、日志/产物路径、负责人和复核人。四态为 pass/fail/unknown/blocked，不允许用平均分冲掉关键门失败。

## 10. 最终放行规则

分别记账，不得互相替代：

- ENGINEERING_REGRESSION：单元/集成/浏览器回归在明确 commit 和环境下通过。
- LIVE_MODEL：真实服务商请求、响应、错误路径和结果入库有证据。
- REAL_ARTIFACT：真实原件诊断与引用支持性经抽查通过。
- HUMAN_LOOP：非编卡者实际执行、产生 V2、A 独立复核、B 只重排剩余项。
- USER_OUTCOME：冷启动、恢复和成果质量等指标有真实用户原始数据。

全部关键门通过、失败样本保留、另一成员独立复核后，才提出发布/合并建议。竞赛获奖结果、官方评分符合性和“超越某产品”属于另行核验的结论，本文件不作保证。
