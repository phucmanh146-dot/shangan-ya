# 上岸鸭：省一目标下的个性化首步与真实作品闭环总调度（2026-10-26）

> 状态说明：这是本轮新增的执行方案，不代表代码、模型、作品或用户测试已通过。所有未在指定 commit 上运行并留存证据的项目一律标记为 `not_run`、`unknown` 或 `blocked`。省级一等奖是对标目标，不是结果承诺。

## 1. 本轮唯一目标

上岸鸭要帮助正在做大学生竞赛、创新创业项目或科研任务的学生，基于**真实作品当前成熟度、目标标准、已有证据、个人可用时间与当前卡点**，生成一个能立即执行的私人定制首步，并用实际产物验证它是否有效。

不能把“个性化”做成改项目名、换语气或生成一份更长的计划。相同用户、相同目标但作品版本不同，诊断也应随证据变化；不同作品即使目标相同，第一步、交付物和验收标准也应不同。

本轮优先验证一条完整链：

`真实材料 V1 → 证据诊断 → 成熟度判定 → 5分钟首步 → 用户真实执行 → V2 → 独立复核 → 仅重排未通过项`

只有这一条可复现，再扩展到更多项目和功能。

## 2. “省一对标”不能只靠主观打分

每个项目必须先确认比赛官方规则、赛道、提交物、评分维度、截止日期与资格要求。官方要求未取得时，相关判据标为 `unknown`，不能用通用经验冒充官方评分表。

对每份真实作品建立一张差距矩阵：

| 维度 | 必须回答的问题 | 可接受证据 | 阻断信号 |
|---|---|---|---|
| 用户与需求 | 用户是谁，痛点是否真实且具体？ | 访谈记录、观察记录、原始问卷、真实工单 | 只有团队自述或模型推断 |
| 方案与创新 | 方案相对已有做法解决了什么不同问题？ | 竞品对照、功能/流程差异、测试记录 | 只写“AI赋能”“智能化” |
| 技术可行性 | 关键链路是否有真实代码和运行结果？ | 固定 commit、调用日志、测试报告、接口返回 | 静态页面、mock 返回被描述为真实上线 |
| 应用与验证 | 是否有用户试用和同条件对照？ | 原始数据、样本口径、V1/V2、独立评价 | 没有基线却宣称提升 |
| 商业/社会价值 | 价值主张是否能被验证？ | 成本、流程、交付记录、用户反馈或合规数据 | 只靠预测数字和宣传文案 |
| 交付完整性 | 作品、PPT、演示、材料是否相互一致？ | 文件版本、演示脚本、可复现步骤、来源清单 | PPT声称的功能无法运行 |

每个 gap 必须包含：`gap_id`、材料版本和 SHA256、原件 locator、原文/可核对内容、目标判据、证据来源、事实/推断/未知标签、影响等级、验收条件、负责人。缺任一关键字段，不能作为已验证 gap 进入正式执行。

## 3. 项目成熟度分层：首步由证据决定

成熟度是调度器的决策标签，不是奖项预测，也不能只由模型自由判定。

| 级别 | 当前证据状态 | 首步策略 | 不允许做的事 |
|---|---|---|---|
| M0 未定位问题 | 原件缺失、目标不清或官方规则未知 | 5分钟内找齐一个必要文件/确认一个规则/补充一个关键问题 | 编造项目差距 |
| M1 有材料、缺证据 | 有 V1，但痛点、创新或关键主张缺来源 | 定位一条原件证据，做 claim-evidence 对照 | 直接重写整份 PPT |
| M2 有方案、未跑通 | 有设计/代码，但关键路径未运行或只有 mock | 运行最小可复现用例，留下输入、输出、日志和错误 | 把设计写成已实现 |
| M3 有可运行链路、缺用户验证 | 关键功能可运行，但缺真实用户或基线对照 | 用同一任务做用户试用/基线对照，记录时间、失败和反馈 | 无样本就声称有效 |
| M4 有试点证据、缺交付一致性 | 已有用户或业务验证，但作品、PPT、数据/隐私说明不一致 | 对照原始证据修正一个最高风险主张，补可复现演示 | 只美化界面掩盖证据缺口 |
| M5 具备可复核成果包 | 关键链路、用户证据、独立复核和交付物基本齐全 | 做盲评、异常/边界回归和提交前核对 | 把局部通过宣传成必获奖 |

调度器必须保存成熟度判断的证据与不确定项；若两个级别证据不足以区分，输出 `unknown` 并先安排鉴别任务。

## 4. 私人定制首步的生成契约

每张首步卡必须包含：

- `case_id / project_id / artifact_version / input_sha256`
- 当前成熟度与判定证据
- 本轮唯一目标及截止时间
- 用户可投入时间、当前卡点与已尝试方法
- `gap_id`、原件定位、目标判据与来源
- **5分钟内可开始的动作**：打开哪个文件/页面、定位哪里、具体改/测/问什么
- 完成后必须产生的可见产物（截图、测试日志、对照表、段落、代码输出等）
- 自检方式、成功/失败判据、失败后的下一步
- 预计耗时范围、依赖、风险和需要用户确认的内容
- 执行前版本、执行后版本、实际耗时、求助次数与结果

禁止使用“继续完善”“优化一下”“加强创新性”等无法直接执行的动作，除非卡片同时拆成具体位置、操作、产物和验收方式。

### 首步质量评分（0–2分/项）

1. 证据定位准确；
2. 与当前成熟度匹配；
3. 5分钟内可开始；
4. 产物可观察；
5. 验收可客观判断；
6. 考虑用户时间与依赖；
7. 失败后有下一步；
8. 与其他真实项目有实质差异。

满分16分。低于12分不得进入正式执行；证据定位、产物或验收任一项为0，直接退回。分数只是行动卡质量门，不是作品获奖概率。

## 5. 真实作品测试：不能把所有项目跑成同一模板

首轮选两种业务结构明显不同、且原件可读取的项目；优先级按材料可用性和风险决定，而不是按项目名字决定。

| 样本 | 真实链路要验证什么 | 可能的首步类型（仅在原件支持时采用） | 专属验收 |
|---|---|---|---|
| 湘匠织秀/湘秀未来 | 需求、访谈、纹样授权、样品/报价、质检和交付证据能否对应 | 从真实访谈/需求记录选一条，追踪到产品方案或授权/履约证据 | 需求主张能回到原始记录；缺失环节列为待补证 |
| 无界智泊 | 预约、冲突、入场、提前离场、结算/退款状态能否复现 | 选择一个真实状态转换，运行前置状态、操作、预期状态和异常分支 | 日志/测试记录可复现，异常分支有明确结果 |
| 本草云联 | 产品功能、目标用户、业务流程和效果主张是否有原始依据 | 从现有材料中挑一条最高风险主张，核对来源与实际功能 | 不把方案、宣传数字或计划当成上线效果 |
| 嘉农芯生/嘉龙新生（名称以仓库和原件核对） | 真实场景、技术链路、试点数据与交付物是否一致 | 先核对项目名称和版本，再选一个可测关键链路 | 名称、数据口径、版本和证据包一致 |
| 其他科研/论文任务 | 研究问题、相关工作、方法、实验、结果是否互相支持 | 先验证一条核心结论能否被原文/实验/代码复现 | 引文定位、方法、数据和结论不越界 |

以上仅为测试方向，不是对项目现状的事实判定。拿不到原件、未获授权、无法读取或版本不明时，标记 `blocked`，不允许凭项目名生成“真实诊断”。

### 个性化差异测试（必做）

固定代码 commit、模型配置、用户可用时间和输出 schema，分别输入至少两个真实项目材料包；再对同一项目输入 V1 与更新后的 V2。对比：

- gap 的证据 locator 是否变化且合理；
- 成熟度是否由新证据驱动；
- 首步、产物和验收标准是否适配各自业务链；
- 用户时间缩短后是否缩小任务，而不是超容量排程；
- 材料更新后是否识别旧 locator/旧计划失效；
- 同一项目重跑是否可解释差异，而非随机换话术。

如果只替换项目名，其他 gap、动作和验收基本相同，判定 `PERSONALIZATION_FAIL`。

## 6. 技术路线：只接入能为闭环提供证据的能力

| 技术 | 本项目中的职责 | 放行标准 |
|---|---|---|
| Dify Chatflow（如实际接入） | 编排材料理解、检索、诊断、行动卡生成等可视化流程 | 导出配置/版本、输入输出 schema、异常分支和真实运行记录；未接入时标 `not_run` |
| RAG 知识检索 | 检索官方赛规、项目资料、技术文档与可引用范例，返回段落定位和来源 | 建立带标准答案的检索集，评估 Recall@k/引用正确率/无依据回答率；只返回摘要不算通过 |
| COS/对象存储（如实际接入） | 保存授权材料、V1/V2、测试附件和证据包 | 权限隔离、版本/哈希、上传下载、删除/过期策略通过；密钥只在后端 |
| 工具调用/Agent循环 | 按有限步骤执行 search/read/validate/plan/finish | 工具结果被读取；失败可见；有超时、预算和循环上限；不能凭模型文本伪造成功 |
| 规则调度器与 SQLite/数据库 | 依赖、容量、状态迁移、版本冲突、任务保护 | 并发/重复提交/旧版本/非法状态的负例通过 |
| Trace/评估集 | 关联输入版本、检索片段、模型/提示词版本、工具结果、V2和复核 | 同一 run 可追溯、脱敏、可重放；mock/simulated/live 明确区分 |

技术选型原则：先确认仓库当前已有实现和部署环境；没有证据时先做适配层和接口契约，不为了“技术名词更多”重写底座。Dify、RAG、COS 都不是独立的创新结论，创新必须落在“证据驱动的个性化首步 + 真人成果复核 + 状态保护”的效果上。

## 7. 三人总调度与交接门

| 顺序 | 负责人 | 任务 | 交付物 | 放行条件 |
|---|---|---|---|---|
| 0 | 队长 | 冻结分支、commit、工作区、官方赛规和两个真实样本版本；保护未提交工作 | baseline manifest、文件哈希、测试命令和环境信息 | 输入/代码版本可复现；任何不明项标出 |
| 1 | A同学 | 读取真实原件，按成熟度分层，建立证据差距矩阵 | 每个样本至少3条候选 gap，含 locator/判据/unknown | 队长抽查原文确实支持判断；不合格 gap 退回 |
| 2 | B同学 | 只消费通过证据门的 gap，生成个性化首步卡和剩余任务排程 | 5分钟首步、依赖、时间估算、产物、自检、失败路径 | 第三人可照卡执行；超容量项明确 unscheduled |
| 3 | 队长 | 集成检索/Chatflow/存储接口与规则状态门；运行回归与异常用例 | trace、测试日志、版本 diff、模型状态和失败记录 | mock 与 live 分开；旧版本不能覆盖已完成项 |
| 4 | B同学/真实用户 | 按行动卡操作原始作品，记录真实耗时和卡点 | V2、V1/V2 diff、操作记录、输入/输出哈希 | 有实际产物；不能由生成的总结替代 |
| 5 | A同学（非V2执行者） | 按冻结标准独立复核，不参考作者自评结论 | 每条 PASS/FAIL/UNKNOWN、证据定位和原因 | UNKNOWN 不算通过；原标准不能事后放宽 |
| 6 | B同学 | 仅重排 FAIL/UNKNOWN/BLOCKED 项 | remaining-plan diff | 已完成、执行中、待复核、锁定项保持不变 |
| 7 | 队长 + 另一位成员 | 盲评、汇总失败案例、决定下一轮范围 | 评估表、复现包、下一轮基线 | 至少一条完整真实闭环，且另一成员独立复现 |

A/B/C 是团队职责，不是产品里必须有三个独立大模型。每次交接必须包含 `case_id`、负责人、输入版本、输出文件、运行结果、失败原因、下一位负责人和放行/退回结论。

## 8. 执行顺序与测试闸门

### Gate 0：工程基线
记录 `git status --short --branch`、`git rev-parse HEAD`、目标分支、关键文件哈希、模型配置状态和测试命令。工作区有未提交改动时不得覆盖。

### Gate 1：已有工程回归
运行仓库当前规定的单元测试和证据复现脚本；记录退出码、测试数、失败数和完整日志。旧 provenance 与当前源码不一致时调查原因，不删除校验。

### Gate 2：个性化首步
跑两个真实样本和同一项目的两个版本；验证成熟度、gap、首步、产物、验收条件确实因证据而异。

### Gate 3：真人 V2
由未编写行动卡的人照卡执行，记录实际耗时、求助次数、失败与产物。做不到时写出阻碍，不用模型模拟完成。

### Gate 4：独立复核与剩余项重排
冻结原判据，由非执行者复核；只重排未通过项。检查完成项、版本和证据是否保持。

### Gate 5：同条件基线对照
在相同材料、任务、模型可用性和时间预算下比较：
- 普通大模型直接建议；
- 上岸鸭“证据诊断 + 个性化首步 + 执行记录 + 独立复核”。

主指标：首次有效动作时间、首步卡可执行率、原件引用正确率、V2合格率、返工次数、恢复后重新开始耗时、超容量排程率、无依据结论率。报告样本数和失败样本；小样本只能说明本轮试点结果，不能外推为普遍优势。

### Gate 6：比赛提交门
作品代码/演示、PPT、官方规则、用户测试、隐私/授权、模型说明和数据口径相互一致；所有核心主张能指向证据。任何关键项为 `fail` 或 `blocked` 时，不得声称闭环已通过。

## 9. 首轮测试用例

| Case ID | 输入/动作 | 预期 | 失败定义 |
|---|---|---|---|
| PERS-01 | 两个不同真实项目，同一时间预算 | 首步、产物、判据随业务证据变化 | 仅换项目名 |
| PERS-02 | 同一项目 V1→V2 | 识别新增/失效证据并调整 gap | 沿用旧定位且不提示 |

## 10. 当前三人立即执行清单

### 队长
- [ ] 冻结当前代码分支与 commit，确认原始作品名称、版本、授权与官方赛规。
- [ ] 选出原件最齐全的两个样本作为第一轮；其余样本先排队，不同时铺开。
- [ ] 检查 Dify/RAG/COS 当前真实接入状态，未配置就标记，不先宣称完成。
- [ ] 建立测试结果表；每个 case 记录输入哈希、预期/实际、日志和复核人。
- [ ] 只有一个样本完整通过 Gate 0–4 后，才批准扩大范围。

### A同学
- [ ] 交付两个样本的证据差距矩阵；每条 gap 必须有原件 locator、目标判据和 unknown。
- [ ] 对首步卡对应的证据与成熟度做抽查。
- [ ] 对 V2 按冻结标准独立复核，不复核自己执行的成果。

### B同学
- [ ] 根据已通过的 gap 生成首步卡；每卡必须含具体位置、操作、产物、自检、失败下一步。
- [ ] 执行一张卡并提交真实 V2、耗时、卡点和差异记录。
- [ ] 根据复核结果只重排剩余项，保留已完成成果。

## 11. 完成定义与当前结论

本轮达到“工程闭环可复现”至少要求：
1. 一个竞赛/创新项目和一个科研/论文项目，或两个业务链明显不同的竞赛项目，均使用真实原件；
2. 至少一条完整 V1→gap→行动卡→真人 V2→独立复核→剩余项重排；
3. 个性化差异测试通过，不是同一模板换名；
4. 关键异常、版本保护和恢复用例有真实日志；
5. 普通大模型基线与上岸鸭方案在相同条件下完成对照；
6. 另一位成员可以按证据包复现结论。

当前结论：**方案可执行；工程、真实模型、私人定制效果和省一水平仍须按上述闸门逐项实测。** 先把一条真实作品链路跑通，再扩展，不以增加技术名词代替工程结果。
