# 上岸鸭 Agent｜创新计划（2026-10-16）

## 1. 创新方向
本方案不再把产品定义成“待办事项 + RAG + 摄像头识别”的简单叠加，而是围绕真实创新实践/科研项目中的持续推进，建立“目标—能力—证据—行动—受阻—恢复—复核”闭环。
核心问题不是“帮用户列任务”，而是：当真实项目因为能力不足、资料不足、步骤不清、临时安排或等待外部条件而卡住时，Agent 能否根据项目证据判断卡点，给出下一步可执行动作；中断后保留现场并恢复；最后用实际成果而不是自述判断是否完成。

## 2. 为什么不是普通 ToDo
普通 ToDo 只回答“今天做什么”。本项目增加三层真实项目状态：
1. 为什么现在做不了：结合项目要求、已有作品/材料、成员能力和历史尝试定位具体差距。
2. 下一步到底怎么做：把差距转成可以立即执行、能够留下证据的动作，而不是泛泛给通用三步建议。
3. 做完以后是否真的有效：记录尝试、观察、耗时、材料版本和成果，由复核环节判断是否达到要求。
任务不是孤立 checkbox，而是一个带上下文、证据和恢复状态的项目节点。

## 3. 三 Agent 分工
### A｜诊断研究 Agent
读取比赛要求、科研/创新计划、已有作品、参考资料、成员能力与历史尝试，输出目标要求、已有能力/成果、缺口与风险、判断依据及优先补齐的关键能力。
### B｜行动排程 Agent
接收 A 的差距结果，结合截止日期、依赖关系、剩余容量和已认领任务，生成最小可执行动作、所需材料、预计投入、后续依赖以及受阻后的恢复入口。无法形成可靠步骤时标记 blocked 并保留原因。
### 总调度 Agent
负责串联：目标 → 诊断 → 能力差距 → 行动 → 执行记录 → 卡点 → 保存现场 → 条件等待 → 恢复 → A 复核 → B 只调整剩余任务 → 成果验收。

## 4. 核心创新
### 4.1 项目记忆
保存任务位置、已完成内容、下一动作、阻塞原因、尝试记录、观察结果、材料版本、耗时和最终证据。下一次从真实现场继续，而不是重新问一遍。
### 4.2 受阻—恢复
临时任务发生时先保存现场；记录中断原因；外部条件未满足时不假装完成；条件满足后进入恢复入口；A 重新复核必要上下文；B 只重排剩余任务。
### 4.3 尝试证据
每次卡点记录“动作—尝试—观察—证据—失败原因—下一次动作”。求助时自动带入当前动作对应材料摘录和近期失败记录，减少重复试错。
### 4.4 成果验收
“我学会了”“我完成了”不能直接作为完成依据。系统优先检查是否产生要求的文件/代码/方案、是否满足项目要求、是否经过 A 复核、是否留下可追溯证据以及关键缺口是否仍存在。

## 5. 真实使用流程
拿到模糊目标 → Agent 读取项目要求与已有材料 → A 判断能力和成果差距 → B 拆成最小行动 → 用户执行 → 遇到具体困难 → Agent 读取当前现场和失败尝试 → 给出针对当前卡点的下一动作 → 临时安排打断 → 保存现场 → 完成临时任务 → 恢复原项目 → A 复核 → B 调整剩余任务 → 真实作品/材料验收。

## 6. 明确不做
- 不把待办清单作为核心创新。
- 不把普通 RAG 问答作为核心创新。
- 不为了展示 AI 强行叠加摄像头识别。
- 不用通用三步模板解决所有困难。
- 不用模型自述代替真实成果验收。
- 不用工程测试结果冒充真实用户效果或获奖证明。
摄像头、普通 RAG 等能力可以作为外围工具，但不承担核心创新点。

## 7. 技术落地
继续沿用 Python + SQLite 以及现有 A/B 交接与总调度基础，保留承诺记录、尝试/失败记录、现场保存、条件返回、求助上下文、候选任务解释、版本保护、动态重排和实际操作轨迹。
下一阶段重点是做真实项目流程验收，而不是继续堆功能：真实比赛/创新计划输入 → 真实材料检索 → 真实卡点 → 真实中断 → 真实恢复 → A 复核 → B 调整 → 最终成果验收，并与普通 ToDo/普通 RAG 方案做对照。

## 8. 比赛展示的一句话
上岸鸭不是替你列一张待办清单，而是记住你正在做的真实项目：知道你为什么卡住、下一步该做什么，临时被打断后还能从原现场继续，最后用真实成果验证有没有真正推进。
