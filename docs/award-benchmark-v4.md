# 参照最高奖公开作品的改版 v4

更新：2026-10-11。目标是提高“比赛任务规划 Agent”的参赛质量，争取全国二等奖；下面的门槛是团队内部目标，不是官方满分评分表，也不是获奖保证。已检索到公开获奖介绍，未取得这些作品的满分成绩、完整答辩材料或本届评审权重。

本日增补：[扣子获奖案例与三人任务交接](coze-benchmark-tasks.md)。本轮不增加泛化功能，重点验证“真实试做判断能力 → 给出能留下成果的动作 → 新成果复核 → 调整受影响步骤”。v2 已要求细步骤和能力证据，本增补把它们落实为可检查的文件与交接，不宣称这是首次提出，也不代表新增功能已经接通。

## 产品定位与本轮范围

服务对象：三人竞赛团队里领到任务、已有一部分材料，却不知道下一小步怎样做到目标的成员。

一次核心流程：用户提交任务、当前作品、目标或优秀参考、DDL 和能力证据；A 找出有出处的差距；B 给出材料位置明确、可以照做且能自检的小步骤；总控让用户确认安排、提交新版成果、逐条验收，变化时保留进度并调整余下时间。

产品价值要用实际成果前后差异证明：哪段内容被修订，哪项证据补上，哪个缺口通过核验。PPT 是其中一个例子；文档、数据表、代码和演示也适用。首轮只支持可提取文字的材料和明确的位置，扫描件、视频、原生 PPT 自动编辑留到后续。

## 旧版和新版的具体变化

| 原来 | 现在的验收要求 | 当前实现边界 |
| --- | --- | --- |
| “优化作品”“学习相关能力” | 指定材料版本与章节/行列/函数，描述现状、目标、原因及验证方法 | 队长已接收和展示；A 必须读取真实材料后生成 |
| 有 steps，但用户仍不知道怎么动手 | 每一小步有 action、reason、output、self_check、failure_next 和 capability_basis | 队长已校验和展示 micro_steps；真实生成与能力判断由 B/A 完成 |
| 来源与位置藏在完整 JSON 里 | 任务旁可直接查看差距、材料版本、具体位置和来源类别；缺项明确提示 | 队长已实现；引用关系校验不等于事实核验 |
| 一条验收意见就可通过 | 精细任务逐条核对验收条件，写所见证据，绑定已提交的成果版本 | 队长已实现人工验收；自动内容复核仍由 A 接入 |
| 一般排程和功能数量代表成果 | 同一任务在时间占用变化前后能解释调整；已完成与锁定成果保留 | 队长已有周期调整；团队共同 3 小时容量需 B 联合排程联调 |
| 目标是“功能多”“Agent 多” | 用相同输入比较泛化规划与本产品：依据、可执行性、修订质量、实际用时 | 实验尚未执行，不填写虚构提升率 |

## 三人的任务、产物与验收

| 成员 / 分支 | 本轮必须交付 | 完成判据 |
| --- | --- | --- |
| A / `feature/diagnosis-research-agent` | 材料读取适配；两份真实 Diagnosis；页/章节/行级来源与版本；一份新版成果复核结果 | 每个结论能回到输入材料；未知明确保留；材料变化后指出哪些差距受影响；不靠模型猜造位置 |
| B / `feature/action-planner-agent` | 两份真实 Plan；每项任务的 micro_steps；能力不足时的最小补充练习；30/90 分钟和突发占用后的安排对照 | 陌生成员能按动作动手；产物与目标对应；无时段冲突；不可安排的任务说明原因；不重写完成成果 |
| 你：队长 / `feature/orchestrator-agent` | 接收、版本校验与可读展示；人工验收；A/B 真实模块适配；联调记录与答辩演示 | A → B → 用户确认 → 执行 → 提交新版 → 逐项验收 → 时间调整能连通；失败和重启保留记录；Demo 与真实结果分清 |

截至本次修改：队长接收、展示、人工验收已经实现；A 的真实诊断与复核、B 的真实领域指导、三个分支的集成仍未完成。A 分支未见新的独立提交只能说明仓库现状，不能推断没有线下工作。A/B 的真实账号仍待核实。

## 每天合计 3 小时的最小交付安排

按全队合计 3 人时/天规划，不自动当作每人各 3 小时。每天安排三个 45 分钟产物块，留下 45 分钟机动；10 月 11—19 日共有 20.25 小时计划容量。下面是建议安排，不是队友已认领的承诺。

| 内部日期 | 当天三个产物块 | 当天必须留下的证据 |
| --- | --- | --- |
| 10/11 | 队长接收展示与验收改动；确定两个真实任务的输入清单；核对报名赛道与规则 | 已提交代码、输入材料目录、规则链接和未知项 |
| 10/12 | A 读取第一组材料；登记版本与位置；生成第一份真实诊断 | Diagnosis JSON 与逐项来源定位 |
| 10/13 | B 写第一组细动作；补一段最小能力练习；安排 30/90 分钟对照 | Plan JSON、动作产物、自检条件及日程差异 |
| 10/14 | 队长接入真实 A；接入真实 B；跑通一次调用到预览 | 可复现的调用记录，失败点与待修项 |
| 10/15 | 成员照步骤修订；A 对新版复核；队长保存人工验收与退回记录 | 修订前后文件、复核证据、版本记录 |
| 10/16 | 第二组任务走同流程；加入突发占用；验证恢复和锁定成果 | 第二份诊断计划、前后安排与成果保留记录 |
| 10/17 | 跑开发集与保留集；对比普通规划基线；记录质量和时间 | 原始案例结果、失败清单、可重现输入与环境 |
| 10/18 | 真实用户试用；修前三个主要卡点；整理反馈 | 用户同意后保存的匿名操作记录和修改说明 |
| 10/19 | 冻结演示版本；录制完整流程；逐项核对提交清单 | 演示、说明书、测试记录及正式提交前检查结果 |

某天排满：当天未完成块移入剩余机动时间，保留完成产物。A 受阻时队长先用人工夹具测试交接，不能把它标成真实诊断；B 受阻先保留可解释的规则排程，不能标成领域指导完成。机动耗尽后优先砍第二场景、花哨界面和自动编辑；保留第一场景的真实证据、细步骤和成果验收。若连这个流程都无法完成，说明实际缺口和延期选项，不伪造进度。

## 冲奖前需要拿出的证据

以下均为内部质量门槛；尚未测量的项目保持待测。

1. 两个真实任务都有当前作品、目标和有出处的差距；至少一个任务产出可复核的新版成果。一个可以是 PPT 导出的文字 PDF，另一个可以是文档/数据任务，不能把产品写死为 PPT。
2. 20 个案例划分 12 个开发、8 个保留；涵盖缺来源、矛盾数据、无法定位、材料版本变化、能力未知、日程不足、卡点及模型失败。保留集验收前不据其答案调整提示词。
3. 保留集中所有“已核验”结论都有可找到的出处；发现虚构定位、错误版本导致完成状态或执行进度被覆盖，均视为阻断问题。资料本身不足时允许明确拒绝下结论。
4. 与相同材料和目标下的普通规划回答比较。盲评差距准确性、动作可执行性、产物质量；记录实际耗时、失败次数、调用费用和人工改动量。先报告真实结果，效果不足就继续修改。
5. 邀请 5—8 名真实目标用户试用，记录第一次动手的位置、卡点、成果变化和解释能力。小样本只提供改进线索，不外推为普遍有效或论文结论。
6. 演示包含：真实输入 → 有出处的差距 → 具体动作 → 新版成果 → 逐项验收 → 临时占用后的局部调整；同时展示失败状态和未实现边界。评委能自行复现核心流程。

完整的旧研究与开发任务见 B 分支的 [调研](https://github.com/phucmanh146-dot/shangan-ya/blob/feature/action-planner-agent/docs/agent-award-readiness-research.md)、[实施路线](https://github.com/phucmanh146-dot/shangan-ya/blob/feature/action-planner-agent/docs/implementation-roadmap-v3.md) 和 [验收清单](https://github.com/phucmanh146-dot/shangan-ya/blob/feature/action-planner-agent/docs/agent-v3-acceptance-checklist.md)。本文件收紧本轮范围；并未将这些分支自动合并。
