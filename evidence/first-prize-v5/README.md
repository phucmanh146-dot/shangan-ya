## 复现已执行结果

在仓库根目录，用本轮提交的固定源文件运行：

```bash
python evidence/first-prize-v5/prove_existing.py --output /tmp/shangan-v5-engineering-results.json
```

脚本核对`provenance.json`所列源码SHA，使用临时SQLite，不发起搜索/模型请求，也不改用户正式状态。代码以后变化时会明确报快照不一致；应在固定版本复现历史证据，或为新代码另外更新证据，不能静默沿用旧结果。

已执行的[结果JSON](engineering-results.json)保存实际输入、函数输出和测试日志：

- 真实项目修复：此前固定4条其他比赛/获奖来源，并预填目标和截止；当前固定赛事来源为0、目标和截止为空，用户赛事上下文检查通过。历史文件在`before/`，原Git blob SHA与不可变提交在`provenance.json`。
- 排程：剩余60分钟，首日少30分钟后两日分别安排30分钟；已完成记录保留。若截止限定首日，则明确缺30分钟。
- 交接：4项现有交接保护+5项赛事上下文检查通过，共9项；实际调用B已交付规则，其样本计划未生成micro_steps，保留这一实际缺口。
- 数据样例：原CSV6行，1条重复、1条缺分母、1条零分母；有效唯一记录合计42/60=70%。此算术只校验人工参考，不证明A自动诊断能力。

这些是受控输入下的工程证据。测试中的A包与模型/网络回答包含人工夹具，不能换算为三人真实模型闭环成绩；`live_model_evaluation`与`user_study`明确为`not_run`。

## 模拟场景S01：把模糊方案改成有依据的报告

输入：[方案v1](report/input-report.md) + [五条访谈片段](report/interviews.md)。

现状：“80%的大学生”“所有人不会用工具”“一定消除拖延”都缺充分依据。目标：定位第2.1节，核对具体原文，保留不同意见、修改断言并补需求→产品动作→验证表。

已给出[具体人工v2](report/reference-report-v2.md)、前后差异和[验收条件](report/acceptance.json)。下一步由A实际读取、B生成可执行动作、成员制作自己的v2、A实际复核；人工v2不能作为生成器的预写回复或用户真实成果。

## 模拟场景S02：把数据分析任务改成可复算结论

输入：[CSV](data/input.csv) + [任务及口径](data/input-analysis.md)。

现状：重复、缺失和零分母未处理，草稿称回收率100%。目标：定位原行号，记录去重/排除理由，算清有效记录分子分母，再修订结论。

[人工参考核对表](data/reference-analysis.md)明确70%的适用范围，脚本独立复算。数据全部人为构造，不是用户问卷、实际蒙牛方案或真实回收记录。真实材料中的同ID冲突等情况需另核实。
