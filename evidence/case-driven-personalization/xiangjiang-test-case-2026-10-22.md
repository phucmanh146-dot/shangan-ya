## 0. 本次验证到底测什么

不测能否生成经济/学习路线，也不测能否写出漂亮商业计划书。要测的是：面对一个已经有项目材料、但结果尚未验证的真实项目，Agent 能否从案例中提取可迁移机制，识别当前项目的真实缺口，结合当前资源，给出一项最值得先做的动作；执行后再根据证据调整方案。

测试项目：用户自己的《湘秀未来(1).pptx》及其项目文件夹。当前材料中可见的方向包括湘西织绣/传统文化产品、手工艺培训、校企合作、就业帮扶、跨境电商等。当前主张“功能覆盖较广、核心闭环尚需收敛”属于对现有材料的产品分析，不是已被用户调研证明的市场事实。

## 2. 给 Agent 的真实测试输入

我有一个名为“湘匠织秀”的项目，现有 PPT 同时涉及织绣产品、传统文化、培训、校企合作、就业帮扶和电商渠道。我还没有拿出足够的用户访谈、真实订单、交付或复购证据。请不要给我制定学习路线，也不要马上重写整份商业计划书。请阅读我提供的项目材料和能成功读取的参考案例，判断我现在最值得验证的一个项目假设；指出参考案例中可迁移的方法及不能照搬的条件；结合当前缺失的证据，给我一个最小、可执行、低成本的下一步，并明确交付物、验收标准和失败后的替代方案。若材料不足，请先问最影响决策的一个问题或标记未知，不要编造用户需求和数据。

## 3. 预期的 Agent 输出合同

Agent 必须输出以下内容；任何一项没有证据时应说明未知：
1. 当前项目定位（暂定）：一句话描述目标对象、当前问题和拟解决机制。
2. 已有证据 / 未知项：分开列举；明确哪些只来自 PPT，哪些来自真实执行记录。
3. 参考案例抽取：每个案例给出文件定位、可核对内容、提取的方法、适用边界。无法读取的 PDF 不得用于具体创新论证。
4. 个性化差异判断：说明案例条件与本项目的差别，为什么不能直接照抄。
5. 唯一优先验证假设：例如“目标购买者是否有意愿为某一类织绣产品付费”，但须由 Agent 根据材料与用户回答选择，不能把示例预设为事实。
6. 第一歩行动卡：输入材料版本与定位、具体动作与顺序、先做原因、所需人/工具/预算、交付物、验收标准、预计耗时及估算依据、失败出口与下一步触发条件。
7. 一个必要澄清问题：仅当目标用户、产品范围或资源条件确实影响行动选择时提出，不要一次问十个问题。
8. 可追溯性：所有关键结论标明来自项目材料、参考案例、用户回答，还是 Agent 推断。

## 4. 一个合格的第一步示例（仅作为验收参照，不是已发生事实）

若 Agent 判断最大未知项是“目标用户是否真有购买需求”，它可以建议先做小样本验证，而不是直接开发平台：
- 先选择一种具体织绣产品与一种目标购买者群体；
- 访谈 3–5 名目标用户，询问实际使用场景、现有替代品、预算区间、购买阻碍和可接受交期；
- 如条件允许，展示一个真实样品或清晰样图；区分口头兴趣与实际付费/预订意愿；
- 产出匿名访谈记录、需求假设表和反例；
- 验收：记录真实原话、样本筛选条件、反对意见和结论；没有足够证据就调整问题或缩小范围，不把小样本当作市场规模证明。

这个例子只有在用户确认能接触到相关受访者、且该假设确实是当前关键未知时才适用。若当前最大问题其实是纹样授权、制作成本、工艺一致性或团队能力，应选择不同的第一步。

## 5. 怎样判断 Agent 的创新机制是否真的起作用

与“普通聊天助手只写一份通用方案”进行同任务对照。给两种系统相同的项目材料、时间限制和用户条件，隐藏输出来源后请独立评审打分。

| 指标 | 记录方式 | 通过条件 |
|---|---|---|
| 证据准确性 | 关键陈述是否能定位到实际材料/案例 | 不得编造数据或把未知写成事实 |
| 案例迁移质量 | 是否说明可借鉴机制及不可迁移条件 | 不能只总结案例或照搬获奖作品 |
| 个性化程度 | 动作是否依据项目当前缺口、资源与限制 | 不是换了项目名称的通用模板 |
| 可执行性 | 用户是否能按行动卡独立开始 | 操作、产物、验收和失败出口齐全 |
| 选择质量 | 第一动作是否针对当前最关键未知 | 说明为什么先做它，其他事为何暂缓 |
| 结果闭环 | 执行后是否依据真实产物复核并重排 | 保留已完成项，只调整剩余问题 |

至少保存原始输入、Agent 输出、使用的材料版本、执行者的实际用时、卡点、产物、复核结果和对照评分。一次试跑只能发现问题，不能证明普遍优于竞品。

## 6. 对现有仓库实现的核验点

从当前可读的仓库代码来看：
- learning-agent/action_planner.py 明确说明它是 evidence-linked deterministic plan drafts，且不伪造模型调用；缺少 grounded micro_steps 时会把生产任务阻塞。
- learning-agent/team_orchestrator.py 已包含版本冲突保护、材料版本引用校验与项目历史状态结构。
- README 明确说明受控工程夹具通过不等于真实用户收益；真人 V2、效果对照仍需验收。

因此本试点不能只把人工写出的优秀方案放进报告就宣称 Agent 通过。应先在实际运行环境提交上述输入，保存真实响应；如果 A 的材料诊断、B 的细动作或复核没有真正被调用，记录为未运行/blocked，并指出缺少的接线或输入字段。
