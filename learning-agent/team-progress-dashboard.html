高含金量 Agent 技术栈 · 当前差距

原则：不靠“多 Agent 数量”制造复杂度，而是把真实材料、工具调用、状态、证据、评测和失败恢复做实。

P0 · 现在必须补

  • 真实 V1→V2→复核→局部重排：至少一例由另一成员照卡独立完成。
  • Tool Contract：把 read_artifact / diagnose_gap / generate_micro_steps / review_artifact / replan_remaining 定义成清晰工具输入输出。
  • Trace：每次模型调用、工具调用、handoff、人工确认都可回放。
  • Evals：记录引文错误、漏检、误放行、首次照做成功率、返工次数，而不是写未经测量的提升百分比。
  • CC Heartbeat：三个真实执行窗口持续上报阶段和 blocker；当前接口已补，真实客户端接入后才算 live。

P1 · 主链稳定后补

  • MCP / Tool 标准化：GitHub、网页检索、桌面和文件工具用统一适配层，不在业务逻辑里硬编码。
  • 检索 provenance：官方规则、参考案例、建议分层，搜索摘要不能冒充已读正文。
  • 多用户 / 公网隔离：当前核心是本机回环服务；比赛若要求公开体验，再补账号、项目隔离和部署恢复。
  • Observability：成本、调用次数、失败类型、重试和人工介入次数进入看板。

P2 · 暂时别为了炫技堆

  • 没有大量历史知识检索前，不急着上向量数据库。
  • 没有明确模型瓶颈前，不急着做微调。
  • 当前自研状态机能满足主链时，不为了“技术名词”强制迁移 LangGraph；复杂度上来再迁移。
  • 不再增加无关 Agent 角色，先把 A诊断、B行动、C总调度的责任边界和证据闭环做深。

三人批注 · 具体怎么改

A · 诊断 / 复核

批注：现在最容易掉回 Demo 的地方，是把“诊断”写成通用建议，比如“加强调研、补充数据、优化逻辑”。这种话谁都能说，不能体现 Agent 价值。

必须这样改：
  • 每个 gap 强制绑定：文件版本 → 原文位置 → 当前证据 → 目标判据 → 差距原因 → unknown。
  • 同一个模糊需求必须因材料不同给出不同动作，禁止统一模板。
  • 对 V2 复核时，不看“任务是否完成”，只看成果内容是否满足判据。
  • 没有证据就保留 unknown，不补猜比赛规则、不把参考案例冒充官方要求。
  • 至少做 1 个错误版本、1 个虚构引用、1 个缺材料样例，证明 A 会拒收。

放行标准：随机抽 3 个 gap，队友能从 gap 一键回到真实原文；V1/V2 同条件复核能明确给出 pass / fail / unknown 和 remaining_issue。

B · 行动 / 排程

批注：不要把所有问题都拆成“搜资料→分析→修改”。那只是把 To-do list 写细，不是高含金量 Agent。

必须这样改：
  • 每个动作卡都包含：操作位置、具体动作、原因、预期改变、产物、自检、失败下一步、能力依据。
  • 能力未知时先做最小试做；试做失败才补当前所需课程/文档/练习，不能先让用户学一大套。
  • 不同 gap 必须产生明显不同的路径：数据清洗、PPT结构、用户访谈、接口联调不能共用同一三步模板。
  • 加入失败分支：打不开文件、API 401、数据缺失、访谈回答过泛，各自有不同下一步。
  • 让另一成员完全不问 B，照卡独立做一项真实任务，记录第一次卡住点和实际用时。

放行标准：另一成员拿到卡后 5 分钟内能开始；首次执行不需要作者口头补充；完成后能生成真实 V2 和实际耗时记录。

C · 队长总调度

批注：不要把总调度做成“把 A、B、C 三个 Agent 串起来”的大页面。真正含金量是：系统知道现在处于什么状态、下一步该交给谁、失败后从哪里继续。

必须这样改：
  • 把状态明确成：MATERIAL_READY → DIAGNOSING → PLAN_PREVIEW → EXECUTING → WAITING_REVIEW → REPLAN。
  • 材料不足时禁止调用 B；能力未知时禁止直接进入制作；上传成果后只能进入待验收，不能自动完成。
  • A 复核失败后，只生成 remaining issues，不重建整套计划，不覆盖 completed / in_progress / locked。
  • 所有关键变更先预览：Agent 给出“会改哪些任务、为什么”，用户确认后才生效。
  • 把每次模型调用、工具调用、handoff、人工确认、失败和重试串成可回放 Trace。
  • CC 看板不能只显示 derived；最终必须让三个真实窗口注册和 heartbeat，窗口卡住时自动形成 reminder。

放行标准：断服务再启动后能回到同一任务阶段；旧版本复核会拒绝；目标变化只影响相关任务；看板能指出 A/B/C 各自真实窗口当前正在做什么、卡在哪里。

下一轮只做这 4 件事

  1. A：拿一个真实作品 V1，输出 3 个有原文出处的 gap。
  2. B：基于这 3 个 gap 生成 3 条明显不同的具体行动路径，并让另一成员照卡做。
  3. 执行者：做出真实 V2，保存修改文件、实际用时、卡点和失败。
  4. C：组织 A 复核 V2，再让 B 只对 remaining issues 重排；完整保存 Trace 和 CC 心跳。

这轮结束前不要加新 Agent、不要做微调、不要为了炫技换框架。先把这条真人闭环做成比赛最强证据。

三人当前放行标准

A · 诊断/复核

不是“建议加强调研”，而是 文件版本 → 原文位置 → 当前证据 → 目标判据 → gap → unknown。V2 必须逐条件复核。

B · 行动/排程

不是“搜资料/分析/修改”三步模板，而是 位置、动作、原因、产物、自检、失败下一步、能力依据，让另一成员不问作者也能开始。

C · 总调度

不是简单串三个 Agent，而是按状态决定下一步；保留版本、人工确认、失败恢复和剩余问题，只改受影响部分。
